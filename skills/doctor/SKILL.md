# Doctor（本机环境体检）

依赖缺了不在开单时报，而在任务中途以一句 traceback 出现。实测：缺 PyYAML 的机器上点「导出交接包」，
面板只回一句「导出脚本没有给出 JSON 结果」。根因在 traceback 的最后一行，读者要自己认。
全仓有一批脚本在 import 阶段就依赖 PyYAML，缺一个包会同时断掉几条流程。

本 skill 的动作一件：**跑体检器，然后按它给的顺序修一项、重跑一次**。

## 何时触发

- 用户问「这台机器能不能用」「装了什么」「为什么报缺依赖」；
- 流程中途出现 `ModuleNotFoundError`、`command not found`，或面板报「没有给出 JSON 结果」这类只有结果没有原因的错误；
- 换机器、换解释器、内网新部署第一次用；
- 修完一项要复验。

## 只跑一条命令

```bash
python3 scripts/doctor.py          # 人读五段：结论 / 能力 / 检查了什么 / 有问题 / 下一步
python3 scripts/doctor.py --json   # 面板或脚本消费
```

退出码：`0` 无阻断、`2` 有阻断项、`3` 不在 ascend-sleuth 检出里、`4` 命令行参数写错。

不要自己另写探测命令。手敲 `python3 -c "import yaml"` 只验一个包，也漏掉解释器不一致这一层。
体检器扫的是 `scripts/` 下全部脚本的 import，新增第三方包会被它自动发现；能力表写错 id 时它会自报。

## 怎么读输出

每段各回答一个问题。

| 段 | 回答 | 用法 |
|---|---|---|
| 结论 | 多少项检查、几项正常、几项降级（其中几项已接受）、有没有阻断；第二行是与上次比 | 第一屏转述这两行，不让用户自己读全表（排法见「会话里的返回格式」）。与上次不一致时先停，见「修复循环」第 5 条 |
| 能力 | 哪些流程可用、哪条降级、缺的是哪个检查项 | 「这台机器还能干什么」看这一段；降级的能力后面直接写着缺什么 |
| 检查了什么 | 正常项与它们的值，按工具 / 包 / 仓库与数据 / 部署声明分组 | 问「装了什么」时照这一段答；完整值仍以 `--json` 为准 |
| 有问题 | 每项一行：缺什么、还等哪个前置（「依赖：」）、影响哪条能力、不修的后果（「后果：」）、修法命令（「修：」）、安装备注（「备注：」）；已接受项标「状态：」并排在最后 | 「依赖：」说明这项要等另一个检查项先修好；「影响：」是从能力表反查出来的，没有能力依赖它时会直说；修的时候只复制「修：」后面那一整行 |
| 下一步 | 按影响面排序的修复动作，只列命令 | 一次只做第一条 |

「修：」是可直接执行的一条命令，「备注：」是同一件事的其他装法（离线 wheel、替代路径），
不要把它当第二条命令跑。

「与上次比」读的是 `.local/doctor-last.json`（本机，不进 git）。加 `--no-record` 时既不读也不写它，
结论照出，只是没有这一行。

报告末尾那行「体检用的解释器」要带上。面板与终端可能不是同一个解释器：Windows 上按 `python3` →
`python` → `py -3` 的顺序探活。把包装到另一个解释器上，体检结论不会变。

解释器低于 3.10 时，Python 那一行会标降级：标准库名单在那个版本不存在，依赖判定只能按路径推断，
可能多报。先升级解释器再判结论。

## 会话里的返回格式

对话里照下面的格式排，不要把脚本输出整段贴进对话。终端、管道与 `--json` 的读者照旧读脚本原文。

- 第一行写「体检：」加脚本结论段，把开头的「结论：」换掉，数字与措辞不动。
- 接着是一张四行表，列为「分组 | 状态 | 内容」，行序固定为工具、包、仓库与数据、部署声明，
  组名在对话里统一用这四个。状态取该组里最差的一项：✔ 正常、! 降级、✘ 阻断。内容只写项名与版本，
  正常项不展开。
- 有问题时在表后逐项一行：`- <名字>（<分组>，<状态>）：<影响>；修：<命令>`。阻断项再补一句脚本里的
  「后果」；已接受的项在括号里补「已接受」，不给修法。项与项的顺序照「下一步」，不写「依赖：」，
  「备注」留在脚本输出里。
- 修法命令只写在「修：」之后，用行内代码，整行可复制；表里不放命令。
- 倒数第二行写下一步：有待修项时给第一条动作；没有时照脚本的收尾句（「环境齐了」或
  「没有待修项（N 项已接受不修）」）接复验命令。
- 末行给体检用的解释器。
- 与上次不一致时，在第一行下面先说变化；一致时不写这一句。

格式示例（数值以脚本输出为准）：

```markdown
体检：<脚本结论段>

| 分组 | 状态 | 内容 |
|---|---|---|
| 工具 | ✔ | Python <版本> · git <版本> · Node.js <版本> · gh <版本> |
| 包 | ! | PyYAML <版本>；<包名> 未装 |
| 仓库与数据 | ✔ | <正常项，用 · 分隔> |
| 部署声明 | ✔ | 演进角色 <取值> |

- <包名>（包，降级）：<影响>；修：`<命令>`

下一步：<第一条动作>。
体检用的解释器：<路径>
```

阻断项不止一处时，表后每项一行，顺序与「有问题」段一致。

## 修复循环

1. 读结论段，记下第一条阻断项。
2. 只修那一项，命令照抄「有问题」段里「修：」那一整行（不含「备注：」）。
3. 重跑同一条命令。
4. 阻断项清零后，再处理降级项。已接受不修的项不会出现在「下一步」里，也不要去动它——要恢复成待修，删 `.local/settings.json` 里 `doctor.accept` 的对应一条。
5. 结论与上一次不一致时先停。同一台机器两次跑出不同结果，说明环境在变（PATH、解释器、代理），
   先查这个再继续修。

## 硬规则

- 没跑就不许说「环境没问题」。结论只从脚本输出里取。
- 不许为了让检查变绿去改体检器或绕开它。它是判据，不是待办清单。真正修不了的项写进 `.local/settings.json` 的 `doctor.accept`（见下节），不要改体检器逻辑。
- 阻断与降级的判据不同。缺 Python 包是**阻断**：相关脚本在 import 阶段退出。缺 `node`、`gh`、
  `git` 是**降级**：对应流程退化，其余照跑。先修阻断项。
- 修不了的项照实说。内网装不了包就给出带 wheel 的离线装法，不再给一条本机执行不了的联网命令。
- 降级项不挡流程时不要顺手修。一次只动一项，修完重跑，否则下一轮分不清是谁改好了。
- **「演进角色」那一行是部署声明，不是缺陷**。`signal-only` 属于正常项（只做内容沉淀的部署的
  预期形态：只记信号不产卡），不要为了让它变绿去改成 `maintainer`。声明写坏时它报降级，修的是
  `sleuth.config.yaml` 里的 `evolution.role`，不是体检器。

## 把一项标成已接受

确实不打算修的降级项（内网装不了、这台机器用不到那条流程）写进本机配置，它就从「下一步」消失：

```json
{"schema": "ascend-sleuth-settings/1", "doctor": {"accept": ["zstandard"]}}
```

写进主检出的 `.local/settings.json`（该目录不进 git；同一克隆的 worktree 共用一份）。
只对降级项生效：阻断项标了也不生效——缺包时脚本在 import 阶段就退出，接受它等于让结论说谎。
接受不等于消失：能力段和「有问题」段仍写着它降级、影响哪条能力，只是不排进下一步。

## 交互修复（agent 代修，仅限白名单）

体检器不改仓库内容；动手的是你，而且每一项都要先问用户。它自己只写本机两个运行时文件：
settings 里的 `doctor.accept`（人写）、`.local/doctor-last.json`（供「与上次比」）。流程：

1. 读 `doctor.py --json` 的 `checks`，取 `state` 不是 `ok` 的项。
2. 按 `fix_auto` 分组：`true` 是安装类（可逆、无凭据、命令已给出）；`false` 是必须人做的（登录、配置、sudo、代理/CA）。没写 `fix_auto` 的按 `false` 处理。
3. 逐项问用户「这项要我现在执行吗」，只执行 `fix` 里给的命令（JSON 里 `fix` 是命令、`fix_note` 是备注）；
   **不换包源、不加 sudo、不改 shell 配置**。
4. `fix_auto: true` 的项执行完立即重跑 doctor 复验；失败就停在这项，把命令和报错末几行交给用户，不试第二种装法。
5. `fix_kind: login-web`（如 `gitcode auth login --web`）：在**可见终端**里启动，让用户自己在浏览器建 token 并粘贴。不要读取、记录、代填 token；用户完成后跑一次 `gitcode auth status --json`，再重跑 doctor。
6. 一次只推进一项；阻断项清零后再处理降级项。

代修不等于改判据：命令只来自 doctor 的 `fix`，复验仍以重跑 doctor 的结论为准；不要在修不通时去改体检器或跳过某项就宣布修好。

## 它不负责什么

- **内容门禁**：索引新鲜度、结构校验、面板契约由各自的检查脚本判，体检器不碰内容。
- **一次跑完所有 CI 命令**：那是 `python3 scripts/rehearse_evolve_loop.py`（逐条复跑 CI 的 `run:`）。
  体检器只在「下一步」里指出该跑哪一条，不抄那份清单。
- **装包与改配置**：体检器不改仓库内容、不装包、不写 `knowledge/` 与 `traces/`。装法由它给出；执行是 agent 在用户逐项同意下代跑（见「交互修复」），或人自己跑。
