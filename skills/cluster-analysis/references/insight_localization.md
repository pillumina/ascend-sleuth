# Insight 关键瓶颈定位

本文件规定 P6a 的分析口径与对用户的输出形态。无分步时沿用 [whole_prof_step.md](whole_prof_step.md) 的整段单 step 规则，位置显示“整段 prof 汇总 step”，事件归入整个已提供范围。聚合 recipe 用于筛选线索；卡级原始时间线用于定位与验证。`scripts/insight_locator.py --help` 是命令参数的事实来源。

## 输出契约

首段说明模型主要问题：到达不齐、下发空隙、计算热点或证据不足。然后依次展示通信、计算、Free。每部分最多三个关键点；无可确认异常时给出一句原因，不用全量算子清单填充。

每条只展示四列：

| Insight 定位 | 主要问题 | 影响程度 | 可能原因与处理方向 |
| --- | --- | --- | --- |
| 迭代、卡号、泳道、精确起始时间、完整算子名 | 最关键的劣化 | 时间及同卡同迭代占比，注明测量口径 | 简短归因及优先核查位置 |

界面列名使用中文，保留完整原始算子、Thread/Stream 名称便于搜索。正文不叙述从哪个文件取得证据。内部 JSON 可保留关联证据供复核；不把这些路径渲染到诊断表。

默认主交付是原有完整 `performance_report.html`。在原“结论与建议”章节内，“瓶颈定位与解决”复用这组条目；集群总览、Advisor、进阶分析、双卡比对、泳道统计、子报告和附录保留。`insight_bottlenecks.html` 是附加的离线定位摘要，`.md` 为同内容文本，`.json` 为机器契约；摘要不能代替总报告或完整流程验收。文件产出成功与分析证据充分是不同条件；读取每部分的原因和结论范围。

## 时间与泳道

- 原始纳秒时间先用整数相减，再转显示单位。**DB 导入**的共同起点是所有已导入卡 `SESSION_TIME_INFO.startTimeNs` 的最小有效正数；**JSON 导入**按 Insight 的 slice/counter（X/C）最早时间规则另算。不能用最早通信或每卡 Step 起点替代。输出形如 `2438ms768us160ns`，附迭代与卡号；记录原点的导入方式及原始纳秒。
- Insight 若导入不同卡集合，或启用手动时轴偏移，显示起点可能不同。报告注明采用的已采集卡集合，不能对每卡分别归零后比较。
- `COMMUNICATION_OP.groupName` 经 `STRING_IDS` 解码得到原始 `group_name_*`；`parallel_group_info` 提供 `dp/tp/pp` 等语义。集群 `CommunicationGroupMapping` 可将分析 hash 对应到 `group_id` 与 `pg_name`。以已解析的真实组为身份，不把 hash 当作 UI 泳道名，不以成员集合相同合并不同组。
- 通信定位给 `dp:Group group_name_1 Communication / Communication (HCCL) / 主机标识`。同名多进程的 Host 线程同时给进程与 Thread；设备给 Stream。Plane 子事件用于证据，不作为另一条通信问题。

## 通信：实例对齐、慢卡与原因

1. 以**迭代、真实通信组、完整通信实例**对齐参与卡；同实例每段只出现一次，该行同时给最晚到达卡与代表等待卡。完整名称中的序号不能被归一化抹去。重复导出/Plane 事件不增加实例数。
2. 按最大单卡等待或到达跨度筛选，而不是将跨卡等待之和当成模型损失。通信最短耗时只给慢卡候选；最晚设备起点、最早起点、结束时间收敛及 wait/transit 数据用于交叉验证。
3. 对齐组的期望成员与已采成员。缺失卡时称“已采集卡中最晚到达”，不确认全域慢卡，也不归因到未采集卡。时钟/偏移未经校验时降低置信度。
4. 由 `connectionId` 找 CANN 下发，再通过 `PYTORCH_API/CONNECTION_IDS` 找 Host 操作。优先比较 Host 开始与结束时间差、设备起点差、排队/前序依赖。Host 下发晚支持下发差异；Host 已提前完成但 Device 晚，更可能是流依赖或队列积压；起点基本齐而传输残差/同链路同负载带宽异常时，才提出纯通信差异。
5. 回溯慢卡与快卡的同名同序 Host 锚点，比较锚点后到通信下发之间的间隙、调用数量和耗时。重复名称要结合序号/上下文；时间相邻不等于调用关系。找不到可靠锚点时说明尚未定位最初分叉点。
6. wait 与 synchronization 可能描述同一段等待，依据 schema 分别呈现，不直接相加。到达跨度、等待差、通信耗时差、未掩盖损失是不同量，说明所报数值是哪一种。

影响用“到达跨度/单卡额外等待/通信耗时差”，有可靠未掩盖区间时给实际可见影响。除以同卡同迭代 Stage；缺少相同窗口时仅报告绝对值。并行通信与跨卡重复等待不累计为可节省时间。

## 计算：只选可解释热点

优先匹配同迭代、同名称、同输入形状、数据类型、格式、加速器核及必要的 Block 配置，比较跨卡耗时。单次长算子与同类累计热点分开；高总耗时可能只是次数多。无同负载基线时报告“热点候选”，不能直接说算子实现劣化。

- AI_VECTOR_CORE 看 AIV，AI_CORE 看 AIC，混合核分别解释。另一种核计数为零不是异常。CSV `*_time(us)` 为微秒；DB 指标要按其导出 schema 识别单位。
- MTE2 说明向核内搬入数据的占用，MTE3 说明搬出占用，vec/mac 说明计算管线占用。这些管线可并行，比例不是互斥分解，不能相加为总利用率。
- 高 MTE 占比、低 vector/mac 占比支持访存热点候选；带宽劣化还需要实际字节量、时间、同类基线或设备带宽证据。输出少量有解释力的值。
- 例如 `Mul` 的 `596049920` 个 FLOAT 元素，一次读与写约 4.77GB（十进制）。若 MTE2 约 99.7%、vector 约 3.6%，可说“大张量读写占主导，考虑与相邻更新操作融合”；不能仅凭比例认定慢卡或异常带宽。
- 实测频率使用 `AICORE_FREQ`。累计多核 cycles 与平均核时间直接相除会生成虚假的几十 GHz；没有实测频率则该能力记未知，不推断降频。

没有可证实计算劣化时，仅保留关键计算热点候选与原因，或说明未发现异常以及采集指标的局限。

## Free：最多三个可定位区间

从 Device 空闲区间读取或重建**所有相关设备执行泳道的忙区间并集之补集**；单条 Stream 空闲不等于整卡 Free。按完整迭代裁剪，排除采集边界/Preparing；不能把 Host 线程空闲或通信等待再次计入 Free。

优先展示最大区间；若一簇规律的小间隙累计影响更大，给其所在时间窗、间隙次数、累计 Free 与占比。聚合簇与单大段保留不重叠证据，最多三条；每条含起止时间和卡号。

将 Free 结束后首个 Device 任务关联到 Host 下发。Free 期间 Host 仍在发起必要任务，或最后必要下发结束显著晚于 Free 起点，支持下发受限候选；Host 早已完成且存在流依赖/同步支持依赖候选。缺少关联时写“Host 下发或依赖等待待核实”。单有 Free 大不能确认 hostbound。

## 验收

合成测试覆盖共同原点精度、通信组同成员不同身份、实例去重、部分通信域、最短耗时误判、Host 与设备迟到区分、Free 聚合、AIV 指标与实际频率。再用真实样例检查目标通信时间与泳道；记录缺失卡与无法确认的根因。任何正文数值都能追溯到内部证据，正文只呈现定位和主要结论。
