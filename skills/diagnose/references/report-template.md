# 诊断定位报告（人读件）——结构与行文规范

> **本文是 diagnose 产出面的契约之一**，与 trace（过程轨迹）、对话输出（现场答复）并列。
> 报告写给**人**看：让读者能在不重读 trace 的前提下复述结论、核对证据、自己判断对错，并从中学到机制。
> 读者画像决定规格：报告**一律按深度排查写**，不设"短版报告"。

## 1. 三份产出各管什么（先分清，避免互相抄）

| 产出 | 位置 | 读者 | 管什么 | 不管什么 |
|---|---|---|---|---|
| **对话输出** | 会话里 | 现场工程师（当下） | 立刻能行动的答复：结论 + 依据 + fix + 可靠度 | 不追求完整；关掉会话即散 |
| **trace** | `traces/<session_id>.yaml` | agent / 面板 / 回放 | 过程可回放：每步动作、决策依据、证据落盘、沉淀候选（机器可读） | 不适合人从头读到尾 |
| **定位报告** | `traces/<session_id>.report.md` | 人（复盘 / 评审 / 交接 / 学习） | 完整逻辑链：现象 → 证据 → 源码 → 机制 → 修复 → 下一步 → 可沉淀什么 | 不替代 trace；不替代 postmortem（知识草稿的入口仍是 to-postmortem） |

三者内容允许**结论一致**，但**不互为副本**：报告不抄 trace 的逐条交互，trace 不为报告而膨胀。

## 2. 产出与维护：报告是**活件**，不是一次性的交付物

诊断会继续（用户回报结果、resume 续接、新证据到达、结论被推翻、沉淀动作发生），报告必须**跟着长**——
否则它会在第一次交付后开始说谎，比没有报告更糟。规则三条：

- **同一份文件改到底**：始终是 `traces/<session_id>.report.md`，不另起 `report-v2.md`。读者手上永远只有一份。
- **修订留痕，不静默改写历史**：每次修订在元信息里更新"最后更新"，并在「修订记录」追加一行
  `- <日期> 依据 <来源>（回报/resume/新证据）：改了什么`。旧结论被推翻时**不要删掉旧结论**——
  降级标注（"初判 X，因 Y 已推翻"）并写清分歧，读者要看得到判断是怎么变的。
- **同步两侧**：报告第 8 节与 trace 的 `sediment_candidates` 同源，改一侧必改另一侧；每次修订往 trace 追一条
  `{action: report, ...}`（续接时 step 递增），让"报告被维护过"这件事可观测。

各触发点改哪几节：

| 触发 | 改哪几节 | 特别要求 |
|---|---|---|
| 首次产出（诊断步骤 6） | 全部 | 即使命中已知 case 也要写清机制（见下条"深度"） |
| 用户回报 fix 结果（解决/没解决/部分） | 1（可信度行）、6（生效验证的实际结果）、7（待回报 → 已回报）、8（候选状态） | 把"回报原话的要点"写进 7 或附录时间线；没解决要写明分歧与下一步 |
| `resume-diagnosis` 续接 | 7（当前状态与下一步）、3（新证据并入对应强度段）、必要时 4/5、修订记录 | 不许重写整份（保留原有依据链，只增补） |
| 新证据推翻原结论 | 1、3、7、修订记录 | 留痕（见上一条），并在 3 里标注"该结论已由 <证据> 推翻" |
| 沉淀动作发生（to-postmortem / to-reference） | 8（`proposed` → `drafted` → 已沉淀 case id） | 同步 trace 的 `sedimented` 与 `sediment_candidates[].status` |
| 报告已闭环（问题解决或转上游） | 0（状态）、7（收尾）、修订记录 | 状态词与 `trace-status.yaml` 一致 |

- **深度**：固定按深度排查规格——**即使根因已由命中 case 确定**，也要写清"为什么是这个根因"（机制、判定顺序、可核对锚点）。
  理由：读者的目的是**判断与学习**，不是接受一个结论。
- **不做的事**：无源码分析时**不删**第 4、5 节，如实写"本轮未做源码分析 + 原因（无源码/无网络/属配置层）"。结构可比内容完整更重要。

## 3. 结构契约

必需的节（缺哪个都算不合格）：

| 节 | 内容 | 写法要点 |
|---|---|---|
| 0 元信息 | session id、问题来源（issue/工单/现场）、诊断日期、**最后更新**、环境四件套（框架·CANN/驱动·平台·部署形态）、状态、severity | 报告被单独转发时，靠这一节自证出处与前提；"最后更新"让读者知道这份是初判还是已闭环 |
| 1 **TL;DR** | 现象 / 根因 / 该动哪个开关，三行内；末尾一行写"可信度 + 前提" | 不含内部词表；读者只读这一段也能决策 |
| 2 背景与现场材料 | 现象、复现条件、影响面、已提供材料清单、**缺什么材料** | 让读者判断"结论是否被现场条件限死" |
| 3 依据链 | 分三段：`已验证`（本轮实际查到）/`推测`（依赖推断）/`数据`（历史积累）；命中 case 或候选排除链写在这里 | 每条结论后面都能指到一条证据 |
| 4 源码分析 | 仓库 + ref（tag/commit）+ 文件:行 + 关键片段 + 由此得出的因果链；附可复现命令 | 这是"可复核"的落点，也是知识库只留代码指针的地方 |
| 5 机制图 | mermaid（1–3 张）+ 图注（这张图讲什么、按什么顺序读） | 形态与配色见第 5 节；图不承担正文没说过的信息 |
| 6 修复方案 | 第 0 步核验（前提未验证时先核验）→ 分支动作 → `rollback` / `side_effects` → 如何验证生效 | 具体到命令或 diff 要点 |
| 7 当前状态与下一步 | 停在哪一步、待回报什么、feedback 债、**未验证的假设清单** | 这一节为 resume 服务：只读报告即可接上现场 |
| 8 沉淀建议 | 结构化条目：`类型`（case / reference / triage）/ 一句话内容 / 证据出处 / 建议 skill | 与 trace 的 `sediment_candidates` **同源**，不写两套 |
| 9 附录 | 时间线（只放可观察事实）、命令清单、**环境备注**（影响后续复核的环境事实）、外部链接 | 跨轮排查时，时间先后本身是判据；环境备注防止下一个人重复踩同一个坑 |
| 10 修订记录 | 每次修订一行：日期 + 依据来源 + 改了什么 | 报告是 gitignored 的本地件，没有 VCS 历史——**它得自己带变更记录**。初版写一行"初稿" |

## 3b. 质量基线（对标已通过人审的样本）

"结构齐全"只是及格线。下面这些是**被读者认可的那份报告**实际做到的，逐条对照：

机械项（`report_lint.py` 能钉）：

- 第 0 节含"最后更新"；第 9、10 节非空；其余必需节非空且达到各自的最小篇幅
- 机制图每个代码块成对闭合、带 `classDef` 语义配色
- 报告点名的 `traces/` 路径真实存在
- 报告有第 8 节 ⇔ trace 有 `sediment_candidates`（双向）

人审项（判断，不做硬门）：

- **TL;DR 自足**：只读它就能决策"改什么地方"；它给的是判断，不是目录
- **有排除链**：不只说"是什么"，还说"为什么不是别的"（候选逐条给排除理由与版本匹配）
- **源码分析是可复核的**：仓库 + ref + 文件:行 + 片段 + 可复现命令，任何人能重跑一遍得出同样结论
- **机制图讲因果不讲清单**：至少一张图承担"为什么会这样"（现象链或判定顺序），并配一句读图顺序
- **修复方案带前置核验**：前提没验证时第 0 步是核验，不是直接开方
- **未验证的写"未验证"**：假设清单显式列出，不许把"看起来像"写成"是"
- **读者能据此学到东西**：机制、判定顺序、为什么这句报错会误导人——这些是报告存在的理由

## 4. 行文规范（专业、细致、严谨、可读）

**底线**：不删机制。去"读起来像机器写的"痕迹，不等于把原理压平；术语不是删掉，是**第一次出现时用因果白话解释一句**。

适配自去 AI 痕迹指南（humanizer-zh，翻译自 blader/humanizer），但**剔除了面向叙事写作的条目**（注入个性、幽默、第一人称抒情、允许跑题）——本报告要的是严谨，不是有人味的故事。

禁用的模式：

- **AI 词汇堆砌**：此外、至关重要、深入探讨、赋能、格局、彰显、持久的、宝贵的、充满活力。替换成具体动词或直接删。
- **系动词回避**："作为/代表着/充当一个"→ 直接说"是"。
- **否定式排比**（"这不仅仅是 A，而是 B"）。**例外**：诊断里的排除是事实内容，允许"根因在 B，不在 A"，但必须紧跟证据；纯修辞性的对仗删掉。
- **三段式法则**：手上有两条就写两条，别凑三条。
- **同义词循环**：同一个东西从头到尾用同一个词（"自研算子包"不要一会儿叫"custom op 包"、一会儿叫"算子库"）。
- **虚假范围**："从 X 到 Y"只在 X 与 Y 真在同一尺度时使用。
- **破折号滥用 / 粗体滥用**：破折号改逗号句号；粗体只给**读者要执行的东西**（开关名、命令、阈值）。
- **内联标题垂直列表**（连续多段"**小标题**：正文"）→ 改成小标题或自然段。
- **填充短语与过度限定**："值得注意的是数据显示"→"数据显示"；"可能潜在地"→"可能"。
- **通用积极结论**（"后续将持续优化"）→ 删，或写成第 7 节的具体 follow-up 项。
- **模糊归因**（"有观点认为"）→ 写明出处（issue 链接、维护者原话、文件行号）。

要做到：

- **结论可核对**：每个结论都能指回一条证据（文件:行、命令输出、issue 链接）。指不回去的，标成推测。
- **诚实退化**：没验证就写"未验证"并写清怎么验证；不许把"看起来像"写成"是"。
- **节奏有变化**：句长与段落收尾换着来；避免连续同构句式（读起来像模板）。
- **篇幅服务读者**：推荐 150–500 行。超过 500 行先自查是否把 trace 抄了一遍。短于 100 行的"深度报告"通常意味着某节在敷衍。

## 5. mermaid 规范（现代、精致、可读）

直接给 mermaid 代码块（` ```mermaid `），不要贴图片。约定：

- **图型选对**：现象→根因链用 `flowchart LR`；判定/分流顺序用 `flowchart TD`；时序（谁先谁后、谁发了什么）用 `sequenceDiagram`。
- **节点文案 ≤ 12 字**，长解释放正文；节点里不要塞句子。
- **配色按语义**，别用默认灰：
  ```
  classDef prob  fill:#FEE2E2,stroke:#DC2626,color:#7F1D1D
  classDef evid  fill:#E0F2FE,stroke:#0284C7,color:#075985
  classDef concl fill:#DCFCE7,stroke:#16A34A,color:#14532D
  classDef mute  fill:#F1F5F9,stroke:#94A3B8,color:#334155
  ```
  语义固定：`prob` 现象/故障、`evid` 证据/检查、`concl` 结论/动作、`mute` 背景。
- **主因链要看得见**：关键那条边用 `==>` 或 `linkStyle` 加粗上色，别让读者自己找。
- **规模**：单图 ≤ 15 个节点，超了拆图。三类图各司其职，按现场有什么选：
  **现象链**（`flowchart LR`：从一次调用走到那句报错，回答"怎么发生的"）、
  **判定顺序**（`flowchart TD`：解析/检查按什么顺序走、在哪一步落空，回答"为什么这句报错会误导人"）、
  **判别-修复分支**（`flowchart TD`：核验输出 → 分支 → 对应动作，与第 6 节的第 0 步一一对应）。
  有源码分析就要有前两类中的至少一类；修复方案有分支就要有第三类。
- **每张图配一句图注**写"这张图讲什么、按什么顺序读"。
- **不装饰**：不用 emoji；标签里有 `()`、`:`、`/` 时用引号包住，避免语法错。

## 6. 沉淀建议怎么写成结构（与 trace 同源）

报告第 8 节与 trace 的 `sediment_candidates` 是**同一份内容**的两种呈现：报告给人读，trace 给机器与 resume 读。一条候选写四件事：

```yaml
sediment_candidates:
  - kind: reference          # case | reference | triage
    summary: 一句话说清可复用的结构事实（跨事故稳定，不绑定本次个案）
    evidence: 本轮的哪条证据支撑它（trace 事件 / 文件 / issue）
    suggested_skill: to-reference   # to-postmortem | to-reference | knowledge-groom
    status: drafted          # drafted（本轮已起草）| proposed（建议做，未做）
```

判断"值不值得沉淀 reference"的口径：**换个事故、换个客户还成立吗**？只对本次个案成立的，不要写成 reference；那是 case 的活儿（走 to-postmortem）。

## 7. 交付前自检

机械项（`python scripts/report_lint.py traces/<session>.report.md`，本仓库脚本；**刻意不进 CI**——报告是判断性产出，硬门会逼出套话）：

- 必需节齐全且非空（0–8 节 + 第 9、10 节）
- 元信息含"最后更新"（读者要知道这是初判还是已闭环）
- TL;DR 不超过 3 行正文
- mermaid 代码块成对闭合，且带至少一个 `classDef`
- 报告点名的证据文件在仓库里真的存在
- 报告有第 8 节时，trace 必须有 `sediment_candidates`（不写两套）

修订时另加三条（详见第 2 节）：

- 第 10 节追加了一行（日期 + 依据来源 + 改了什么），且旧结论没有被静默删除
- 改动涉及第 8 节时，trace 的 `sediment_candidates` / `sedimented` 已同步
- trace 追了一条 `{action: report, ...}`（让"报告被维护过"可观测）

人审项（判断性，不做硬门）：

- 一个不了解本问题的工程师，只读报告能否说出"哪里坏了、为什么、下一步动什么"？
- 每个结论是否都能指到证据？推测是否显式标了推测？
- 有没有为了显得完整而凑数（三段式、通用积极结论、抄 trace）？
