# 大日志处理策略与脚本使用规范

现网日志的核心矛盾：**日志量大（MB~GB 级）vs 分析上下文有限**。解决思路：脚本把日志加工成"小而准"的中间产物（manifest/hits/stats/context 片段），上下文里只放加工结果，不放原始日志。

## 一、Step 0 启动信息清单

分析开始前逐项核对，按下表判断缺失项处理方式：

| 类别 | 清单项 | 阻塞性 | 用途 |
|---|---|---|---|
| 现象 | 什么任务（训练/推理）、什么模型、什么报错/怎么失败的 | **阻塞**（完全没现象无法分析） | 确定排查方向 |
| 时间 | 问题首次发生时间（精确到分钟）、持续时长、频率（必现/偶发/一次性） | **阻塞**（当日志覆盖数天且无法从分布反推时） | 时间窗收敛，量级决定分析效率 |
| 范围 | 单卡/单机/多机？哪些节点/卡受影响？是否所有任务都受影响 | 非阻塞（可从日志反推，需标注假设） | 缩小日志范围 |
| 环境 | 硬件型号、驱动/固件/CANN/框架版本、组网、是否容器 | 非阻塞（版本类问题强相关，缺失时建议用户补充 dump） | 根因匹配 |
| 已采取措施 | 是否重启过、是否已恢复、近期有无变更（升级/改配置） | 非阻塞 | 避免把处置痕迹误判为根因；"近期变更"是高频根因线索 |
| 复现 | 能否稳定复现、复现步骤 | 非阻塞 | 决定"建议复现采集"还是"只能靠存量日志" |

**批量提问模板**（阻塞性缺失时使用，一次性问完，每项注明用途）：

> 为准确定位，需要补充以下信息：
> 1. 问题发生的大致时间点（精确到分钟，用于在跨 X 天的日志中锁定分析窗口）
> 2. 是训练还是推理任务？哪个模型？（用于匹配故障模式）
> 3. 影响范围：单卡、单机还是多机？（用于决定是否做跨机时间对齐）
> 4. 日志包中未包含 dmesg，建议补充：`dmesg -T > dmesg_<时间>.log`（用于排查硬件/内核级事件）

## 二、四层处理管线

### L0 清单扫描（必做第一步）

**目的**：搞清日志包里有什么、覆盖什么时间段、缺什么。

```
python log_analyzer.py scan --dir <日志包根目录> --out analysis_out/manifest.json --md analysis_out/manifest.md
```

输出：每文件 {路径, 类型, 大小, 行数, 首末时间戳, host, device, 是否二进制} + 总体统计。

**决策规则**：
- 日志不覆盖问题时间窗 → 停止下钻，向用户索取对应时段日志（铁律 3）
- 缺 dmesg/框架日志且现象指向该侧 → 索取（列出采集命令）
- 覆盖良好 → 进入 L1

### L1 错误提取

**目的**：全量错误面扫描，产出带 `file:line` 的命中清单。

```
# 默认 18 个内置模式（ERROR/FATAL/timeout/OOM/ECC/watchdog/core dump/昇腾错误码等）
python log_analyzer.py extract --dir <根目录> \
  --since "2026-08-28 10:00" --until "2026-08-28 10:40" \
  --keywords "hccl,rank,断卡" \
  --out analysis_out/hits.json --md analysis_out/hits.md
```

要点：
- **有时间窗必加 `--since/--until`**（±10 分钟起）；无时间窗且日志跨度大 → 回 Step 0 提问（铁律 3）
- 场景关键字从 `fault-patterns.md` 对应场景章节复制叠加
- `--top`（默认 500/文件）防单文件噪声淹没全局；`--no-default` + `--patterns name:regex` 处理特殊格式
- stdout 会打印按模式/文件/小时的分布摘要——**先看摘要再决定读哪些 hits**

### L2 聚合分布

**目的**：从命中清单看"错误在哪个文件、哪个模式、哪个时段集中"，决定下钻顺序。

```
python log_analyzer.py stats --hits analysis_out/hits.json --bucket 10m --md analysis_out/stats.md
```

**决策规则**：
- 错误集中在一个 device 文件 → 优先下钻该卡
- 错误在多机同时段爆发 → 通信/上游公共依赖方向
- 错误集中在拉起时段 → 拉起失败路径（版本/资源/初始化）
- 某模式命中数巨大（如上万条 timeout）→ 属于连锁反应噪声，找最早的少数关键命中

### L3 聚焦取证

**目的**：对重点命中行取上下文，形成可引用的证据片段。

```
# 按行号取证
python log_analyzer.py context --file <日志文件> --line 1234 --before 15 --after 15
# 按正则第 N 次命中取证
python log_analyzer.py context --file <日志文件> --regex "EE9999" --nth 1 --before 15 --after 15
```

要点：
- 上下文默认 ±15 行；栈类错误加大 `--after`（栈可能很长）
- **只有 L3 产出的片段（含行号）才允许进入上下文/报告**，这是控制上下文长度的关键
- 逐个证据记录到 `analysis_out/evidence.json`（格式见第四节）

### 直读例外

- 文件 <2MB 且 <10000 行：可 Read，但建议仍先 scan 拿时间范围
- 小文件直读时引用证据同样必须带行号，同样要回验

## 三、时间窗口收敛策略

| 已知信息 | 策略 |
|---|---|
| 精确到分钟的问题时间 | `--since/--until` 取 ±10 分钟；未命中再扩大到 ±30 分钟 |
| 只知道日期 | 当天全量 extract → stats 按小时桶看分布 → 收敛到异常时段再 context |
| 完全不知道时间 | 若 stats 分布有明显的"错误爆发点"，以爆发点为假设窗口（标注假设）；分布平缓无法判断 → 阻塞，回 Step 0 提问 |
| 偶发问题（无明确时间） | 提取全窗口内的 ERROR/FATAL，按"首个异常"原则逐个下钻 |

## 四、证据登记与回验规范（Step 5）

### evidence.json 格式

```json
[
  {
    "id": "E1",
    "file": "plog/host-192-168-1-10/device-3.log",
    "line": 1234,
    "quote": "[2026-08-28 10:20:05.000] [ERROR:DEV] device 3 ecc error ...",
    "note": "device-3 发生 ECC 错误",
    "conclusion_ref": "根因-1"
  }
]
```

规则：
- `file` 使用**相对日志包根目录**的路径（正斜杠），`line` 为脚本输出中的行号，`quote` 从 hits/context 输出**逐字复制**（可截断，截断处标 `...`，不得改写）
- 每条证据登记时同步登记它支撑的结论（`conclusion_ref`），保证报告里每个结论都能追溯到证据

### 回验命令

```
python log_analyzer.py verify --evidence analysis_out/evidence.json --root <日志包根目录> --md analysis_out/verify_result.md
```

判定规则（脚本自动执行，空白归一化后比较）：

| 结果 | 含义 | 报告中的处理 |
|---|---|---|
| PASS | quote 与实际行逐字一致 | 该证据支撑的结论可标 `[已验证]` |
| PARTIAL | quote 是实际行的子串或超集 | 可标 `[已验证]`，但需在附录注明部分匹配 |
| FAIL | 内容不一致/文件不存在/行号越界 | 证据作废，相关结论降级为 `[推断]` 或 `[待确认]`，报告说明原因 |

**回验不通过时的处理**：重新定位正确行号 → 更新 evidence.json → 重新 verify；找不到对应证据则承认"证据不成立"，禁止为了报告好看而放宽比对。

## 五、输出控制约定

| 场景 | 约定 |
|---|---|
| hits 进入上下文 | 只取 stats 摘要 + 每文件/每模式前几条代表性命中；全量 hits 留在 JSON 里按需查 |
| 单行长度 | 截断 300 字符（`--max-chars` 可调），截断标 `...` |
| context 片段 | 单次取证 ≤31 行（±15），需要更长时分段取证 |
| 阶段同步 | 每步结束给用户 1~3 句关键发现，附最关键的 1~2 条 `file:line` 证据，**不暂停等待** |

## 六、脚本定制扩展规范

预置脚本覆盖不了的格式（如特殊分隔符、多行日志条目）：

1. 优先用 `--patterns name:regex` 参数解决（不改代码）
2. 参数解决不了时，可在工作目录复制脚本后修改（**不修改技能原始脚本**），修改原则：
   - 保持输出 JSON schema 不变（file/line/ts/patterns/text）
   - 保持流式读取（禁止一次性读入大文件）
   - 保持 `file:line` 必须出现在每条输出中
3. 定制脚本与预置脚本产出统一进 `analysis_out/`，报告附录注明用了哪些定制规则
