# 九类文档的骨架

> 「小节」列里的名字就是标题原文，照抄，不要改写、不要省、不要调整顺序。某一节没有内容时，在那一节里写一句「无」并说明为什么没有。
> 每类后面有一行「反例」，指向 `anti-patterns.md` 里对应的条目，提交前对着看。
> 每类的骨架都建立在这里不重复的九条硬规则上——见 `SKILL.md`「跨类型硬规则」。

所有类型共用的两条顺序与归属约定。**一般信息在前，例外与条件在后**：先说通常怎么运作，再说"什么情况下不是这样"。
**只有操作指南有「步骤」一节**：机制说明、规范条文、决策记录、参考词条里写"怎么做"就是走错了类型——要指导动作就改成规则，
或者另开一篇操作指南并链过去；这几类允许全文没有可执行步骤。

术语的引入权按类型分：决策记录与机制说明可以引入新术语，但要在首次出现处给一句定义；操作指南不引入新术语，读者必须懂的概念用一句话加一个链接带过。

类型名不跨规范搬运。"Tutorial"在 Diátaxis 指新手课，在 Kubernetes 指端到端走查；同一个词在别处是什么意思，与本规范无关。
引入一个新类型名之前，先写清三件事：读者当时是在学还是在做、这份内容作用于理解还是判断、颗粒度是一篇还是一节。

## 1 导览

读者读完能做什么：知道这套系统在做什么，接下来该读哪篇。

| # | 小节 | 写什么 |
|---|---|---|
| 1 | 这是什么 | 一段话，不超过三句，不用本文档才定义的词。第一句要能不靠后文单独读懂——它会被摘出去当仓库描述、列表里的一行 |
| 2 | 它解决什么问题 | 读者能对号入座的现象，不写抽象价值 |
| 3 | 由哪几块组成 | 组件表或一张图；每一块一句话 |
| 4 | 从哪读起 | 按读者的角色或任务给两到四条路径，每条写第一站是哪个文件 |
| 5 | 不覆盖什么 | 本导览不负责的东西，以及该去哪找 |

导览不超过三屏。它是入口，不是百科。写法参考：`docs/README.md`。

反例：开篇是杂物间（`anti-patterns.md` 1）、标题看不出要做什么（2）。

## 2 规范条文

读者读完能做什么：判断某个设计或改动合不合规。

| # | 小节 | 写什么 |
|---|---|---|
| 1 | 管什么 | 这份规范覆盖哪一类文本或行为 |
| 2 | 不管什么 | 明确划出去的部分，以及它们归谁管 |
| 3 | 条目 | 编号条目，一条只说一件事。每条给「要求 / 怎么判定 / 反例」三列，并标明强度：硬要求（必须）、建议（应当）、还是留给实现决定。强度不写，评审只能逐条问 |
| 4 | 有意保留的例外 | 看起来违规其实必须保留的值：原始字段名、路径命令、已成本行话的说法、证据原值 |
| 5 | 哪几条能机检 | 分「已进 CI」「能写但没进」「只能人审」三类；只能人审的不要写成条目 |
| 6 | 与相邻规范的关系 | 单向指路，说清谁是判定口径的权威、谁在什么情况下覆盖谁 |
| 7 | 引用 | 分两处列：**规范性引用**（照它执行，本文档的效力依赖它）与**资料性引用**（只作参考）。混在一起，读者不知道哪条必须遵守 |

条目的编号一旦发布就不要重用；删掉的条目留号并标注已废弃。

写法参考：`docs/spec/writing-norms.md`。

反例：一页兼两职（3）、有要求没判定方式（等于没写，读者只能凭感觉）。

## 3 机制说明

读者读完能做什么：说清某个机制怎么运作、边界在哪，够判断改它会不会撞到别处。

| # | 小节 | 写什么 |
|---|---|---|
| 1 | 解决什么问题 | 这个机制要解决的问题，以及它明确不解决的问题 |
| 2 | 最小可执行模型 | 先给一个能跑通的最小模型，读者读完这节就能理解后面所有细节 |
| 3 | 完整机制 | 按执行顺序或数据流分节；每节开头一句结论 |
| 4 | 边界与失败模式 | 超时、降级、并发、重复执行、数据缺失时的行为 |
| 5 | 现状 | 分「已落地」「蓝图」「已否决」三块，各自标状态，绝不混排 |
| 6 | 代码与文档入口 | 关键文件与脚本的路径，带行号 |
| 7 | 外部参考 | 与其他项目、论文、方法的对比，放最后一节 |

第 1 节要能单独成立：范围、不覆盖什么、外部接口、主要构件。读者读完这一节就该知道这个机制坐在哪里，后面每一节都不得引入第 1、2 节没出现过的构件名。

第 2 节是这类文档的关键：没有最小模型就直接铺开完整机制，读者会在第五节放弃。完整机制里的每个术语，要么在第 2 节出现过，要么在它首次出现的那一句里当场定义。

「完整机制」内部先分解再流程：构件、数据结构与接口写一节，随时间变化的流程另写一节，两者不交错。流程只写少数与结构相关的场景，场景里的每个动作都要落到分解里已有的构件名上，不出现新名字。横跨多个构件的机制（超时、重试、降级、留痕）集中写一处，不在每个构件下各抄一遍。

取舍（为什么选这个做法）写进决策记录并链回来，本节只写这个机制现在怎么运作。

图只在两三句话说不清关系时用。图必须配文字说明，正文不复述图里的每一格。

反例：状态腐烂（`anti-patterns.md` 10）、开篇是杂物间（1）、术语轮换（6）、图脱不开正文（16）。

## 4 操作指南

读者读完能做什么：按步骤把某件事做出来。

| # | 小节 | 写什么 |
|---|---|---|
| 1 | 做完得到什么 | 一句话说清终点状态，让读者判断这是不是他要的那件事 |
| 2 | 前置条件 | 环境、权限、依赖、必须先完成的步骤；缺一条就说清报什么错 |
| 3 | 步骤 | 编号，一步一个动作。命令整段可复制，路径写绝对路径或用已定义的变量 |
| 4 | 怎么确认做对了 | 可观察的输出或状态。不要写「应该没问题」 |
| 5 | 出错了怎么办 | 常见失败现象 + 处置。至少写一条 |
| 6 | 怎么退回去 | 回滚或清理，做不到就明说做不到 |

这一节里不解释概念。读者必须懂的概念用一句话加一个链接带过，链到机制说明。指南允许不完整——覆盖最主要的路径即可，剩下的说清哪些没覆盖。

命令与输出照原样保留，不要为了排版改写。参数值、环境变量、错误原文都属「有意保留的例外」。

步骤里提到的 skill、脚本、命令、字段都必须是仓库里真实存在的名字，能直接 grep 到。写「调用相应脚本」「按需配置」等于没写。

反例：一页兼两职（3）、为求短删掉安全条件（14）。

## 5 计划

读者读完能做什么：知道下一步做什么、什么时候算做完。

| # | 小节 | 写什么 |
|---|---|---|
| 1 | 目标与完成判据 | 达成时世界是什么样，怎么验证 |
| 2 | 现状 | 已经到哪一步，哪些前置已具备 |
| 3 | 工作项 | 每条给「做什么 / 完成判据 / 状态 / 依赖」。状态取值固定 |
| 4 | 顺序与理由 | 为什么这个顺序，以及哪些项可以并行 |
| 5 | 明确不做 | 这次不做的事，写清为什么不做 |
| 6 | 风险与触发条件 | 什么信号出现时应该停下来重新评估 |

计划会过期，所以每条工作项自带状态，读者不必靠日期判断哪条还成立。**不要在正文里写死条目数**——数量从清单生成。

反例：没有「不做什么」（`anti-patterns.md` 7）、状态腐烂（10）。

## 6 决策记录

读者读完能做什么：知道当初为什么这样选，还能不能推翻。

| # | 小节 | 写什么 |
|---|---|---|
| 1 | 状态 | 头部一个字段，取值：提议 / 已接受 / 已否决 / 已被取代。如果已被取代，写清被哪条取代 |
| 2 | 背景 | 促成这个决定的事实与约束。只写事实，不写倾向 |
| 3 | 决定 | 用完整句子写「我们决定……」，一句话说完 |
| 4 | 被否决的替代方案 | 每个方案写清它好在哪、代价是什么、为什么不选。列不出代价的替代方案不算写 |
| 5 | 后果 | 分条，每条写成「好，因为……」或「坏，因为……」 |
| 6 | 关联 | 取代了谁、被谁取代、依赖哪条提案或哪个代码入口 |

已接受的记录**不改写**。要变就新开一条，新条写取代了哪条，旧条补一行被哪条取代，两头都写全。被否决的记录**不删**，要写拒绝理由，否则下一个人会把同一个方案重新提一遍。

「已在主干生效」和「已接受」不是一回事：标了「已落地」的，必须同时给出一条可执行的确认方式（跑哪条命令、看哪个文件、grep 哪个字符串）；给不出来的，只能标「已决定」。

反例：改写已经接受的决策（`anti-patterns.md` 11）、只列好处不列代价（9）、状态腐烂（10）。

## 7 提案

读者读完能做什么：判断这个改动该不该做，代价是什么。

| # | 小节 | 写什么 |
|---|---|---|
| 1 | 状态 | 头部一个字段，取值固定。区分「已批准」与「已落地」；批准后补一条决议链接——决议写在哪、谁批的、评审记录在哪 |
| 2 | 动机 | **只讲问题与当前代价**，一个字都不要提方案。以「别的项目也这么做」作动机不算动机 |
| 3 | 目标 | 做完之后能观察到什么变化 |
| 4 | 非目标 | 本来可以是目标、本次明确不做的。每条写清为什么不做 |
| 5 | 方案 | 怎么做。到文件、到函数、到数据结构 |
| 6 | 替代方案 | 每个写清代价对比与不选的理由。只列明显更差的方案等于没写 |
| 7 | 代价与缺点 | 分条写。写「没有明显缺点」的，按未完成处理 |
| 8 | 依赖与新增的运维工作 | 需要谁先做什么；上线后多了哪些要人盯着的事 |
| 9 | 未决问题 | 集中放这里，节首写一句「本节不构成实现依据」 |
| 10 | 先例 | 别的项目怎么做的。放最后一节，只作参考，不作动机 |

第 2 节和第 4 节是这类文档最常缺的两节，也是评审拉扯最多的两处。

反例：方案先行（`anti-patterns.md` 6）、没有「不做什么」（7）、替代方案是稻草人（8）、只列好处不列代价（9）、已决与臆测同段（12）。

## 8 复盘

读者读完能做什么：知道一次事件里发生了什么，下次怎么避免。

| # | 小节 | 写什么 |
|---|---|---|
| 1 | 头部 | 一行字段：时间、记录人、状态（调查中 / 已完成 / 行动项待办） |
| 2 | 结论 | 一段话：发生了什么、影响多大、现在什么状态 |
| 3 | 影响 | 谁受影响、范围多大、持续多久。用数字，没有就写「无法量化」 |
| 4 | 时间线 | 时间 + 事实，一行一件，按发现时间排。每行末尾给数据来源（trace 路径、命令、日志片段） |
| 5 | 根因 | 分两层写：直接触发的原因，和让它能发生的条件。不要合成一句 |
| 6 | 怎么被发现的 | 靠哪条检查、哪个信号，还是客户报的；以及发现得算早还是算晚 |
| 7 | 处置与恢复 | 当时怎么处理的，什么让它恢复的 |
| 8 | 做得好、没做好、侥幸 | 分三档写。只写没做好，下次不会有人愿意上报 |
| 9 | 行动项 | 表：做什么 / 谁 / 怎么算完成 / 状态。不写日期，写判据；每条要能执行、范围有界 |

用词不得比事实更强：不是全面不可用就不要写「全站不可用」，只是一次误诊就不要写「系统故障」。

第 5 节和「是谁干的」无关。复盘写的是系统为什么允许这件事发生，归因只到机制与内容，不到个人。本仓另有一条：要分清是这一类 case 归错了，还是执行这条 case 时错了，两者改法不同。

定位报告（`traces/*.report.md`）有自己的模板（`skills/diagnose/references/report-template.md`），以模板为准，本节不覆盖它。

反例：复盘用词比事实更强（`anti-patterns.md` 17）、时间线没有数据来源（18）、已决与臆测同段（12）。

## 9 参考词条

读者读完能做什么：查到一条事实、一个字段、一条命令。

| # | 小节 | 写什么 |
|---|---|---|
| 1 | 这是什么 | 一句定义 |
| 2 | 字段 | 表，像词典条目。字段名、类型、取值、默认值、含义 |
| 3 | 适用范围与限制 | 它在哪些版本、哪些平台成立；什么时候不适用 |
| 4 | 来源与验证状态 | 来自官方文档还是实践归纳；验证到什么程度 |
| 5 | 相关词条 | 链接，不重复内容 |

参考只描述，不指导、不解释。要写「怎么做」就另开一篇操作指南并链过去。同一份内容不要在词条和指南里各写一遍——能链就不抄。

反例：一页兼两职（`anti-patterns.md` 3）、零信息小节与纯链接页（4）。

## 附录：图

图属于机制说明、导览、复盘三类，其他类型原则上不放图。

- **只在两三句话说不清关系时用**。线性步骤、字段清单用表或列表，不用图。
- **图必须配文字说明**。说明写清这张图在讲哪一层、哪些元素被省略了。
- **正文不复述图**。图里已经逐格画出的内容，正文只写结论。
- **节点名称与正文用词一致**。图上叫「候选」，正文不能叫「备选」。
- **图与它所描述的对象放在同一节**，不集中放文末。
- **标题写明图的类型与范围**，例如「诊断主流程（不含采集）」。图上每个元素显式写出类型与一句职责；关系线单向，写清传什么、调什么，只写「调用」两个字的线等于没画。
- **必须有图例**，说明颜色、线型、缩写各是什么意思。
- **图后跟一段「这张图里值得注意的地方」**，只说图没直说的事，不重复已经画出来的内容。读者只看图不看正文也能读懂，才算合格。
- **用 Mermaid 写在 Markdown 里**，图源与正文同进版本库，改动能在 PR 里逐行 diff；不要提交二进制图片。
- **不要为了完整把所有层都画出来**。画得下才画；一张图超过十来格就该拆开，或者降级成表。
- 图源文件放 `docs/assets/` 一类已豁免登记的目录，正文里链到图片；具体的豁免目录见 `repo-anchors.md`。
