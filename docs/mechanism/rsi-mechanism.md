# 自演进机制：设计与实现

系统在做内容工作的过程中改自己，改出来的东西在下一轮工作中生效。本文是这套元机制的技术说明，也是它唯一的技术入口，覆盖三件事：这套机制怎么运转、哪一步需要人、哪一步可以交给 agent。

为什么值得读：要改这套机制本身，先要分清三条环路与两个学习层面分别落在哪，否则一处改动会挡到另一处。

范围：本文覆盖机制怎么运转、哪一步需要人、数据落在哪、验证怎么闭环、现状与缺口。不含单个流程内部的执行规则（`skills/<name>/SKILL.md`）、演进流水线的状态机与卡 schema（[pipeline.md](pipeline.md)）、评测池与交互面评测的口径（[eval-arena.md](eval-arena.md)、[ixn-replay.md](ixn-replay.md)）。

读者与前置：先读 [demo-walkthrough.md](../demo-walkthrough.md)，它能说清系统整体在做什么。正文不用内部简称；改脚本、查数据文件之前，先用第 11 节的[代码与文档入口](#11-代码与文档入口)把正文用词换成代码与文件里的名字。本文不写会过期的数字，需要时现算：知识库条数用 `python3 scripts/index_counts.py`，改进项状态用 `python3 scripts/ev_measure.py --audit`，指标读 `metrics/timeline.yaml`，判据阈值读 `proposals/gates.yaml` 与 `metrics/gates.yaml`。

何时不必读：只想知道系统整体在做什么的人读 [demo-walkthrough.md](../demo-walkthrough.md) 即可；按现有流程跑日常诊断与沉淀的人不必读本文。要改机制本身，先看第 13 节的权威归属表，它说明每件事由哪篇文档说了算。

## 1 解决什么问题

系统在做内容工作的过程中改自己，改出来的东西在下一轮工作中生效：修复结果回写单条知识的置信度，内容工作留下的记录攒成对知识库与流程的改动。

演进不需要人单独发起。每次内容工作收尾时，系统检查这一轮有没有改进信号。改进项是 `proposals/ideas/` 下的一张卡，记方案、可验证的预期、判定结果。有信号就记录、立改进项、执行、验证；没有信号只留一行记录。每周批审收尾时同样自动检查一轮。另外两个入口（人显式要求的全库体检、体检报出的判据越界）仍要人触发，原因见第 2 节末，退出条件见第 6 节。

系统里有三条环路，区分它们是读懂后文的前提。

| 环路 | 什么时候发生 | 谁发起 | 产出 |
|---|---|---|---|
| 诊断 | 每次出问题，分钟级 | 工程师贴日志 | 修复建议 + 一份诊断记录 |
| 沉淀 | 定位结束，或每周批量导入 | 定位的人，或例行拉取 | 待审草稿，审核后进入知识库 |
| 演进 | 上面两环产生数据之后 | 系统自动，或人显式要求 | 改进项 → 改动 → 验证 → 合并送审 |

三条环路构成一个闭环：诊断环与沉淀环产生数据，演进环读数据改机制，改完的结果回到前两环。这个闭环的每一段都要能给出可核对的改进证据，见第 5 节。

## 2 什么时候会发生演进

演进有四个入口。前两个由系统自动触发，后两个由人跑一次体检触发。

| 入口 | 谁发起 | 覆盖什么 |
|---|---|---|
| 内容流程收尾时的检查 | 系统自动，不需要人说改进系统 | 这一轮工作产生的数据：新沉淀、未命中、重复动作、流程摩擦 |
| 每周批审收尾时的检查 | 系统自动 | 知识库的覆盖缺口与结构问题 |
| 人显式要求做一次全库体检 | 人 | 跨轮聚合：归因聚类、容量、重跑未做的条目、指标漂移 |
| 周期性体检报出的判据越界 | 人跑一次体检 | 机制自身的读数越界：改进项积压、引用失效、判据缺失、外部验证停摆 |

第四个入口目前仍由人触发：判据越界能报出来，但还没有固定动作去读它，体检眼下挂在每周的例行工作里。这个入口的退出条件见第 6 节。

## 3 最小可执行模型：两处学习与一条改进项链路

读懂这套机制只需要抓住一件事：系统在两个层面上更新自己，两个层面的作用对象与周期都不同。

知识层更新单条知识的置信度。一条知识被使用后，工程师回报修复结果，该条知识的置信度随之更新，下一次选候选时的顺序也跟着变化。这一层的周期是分钟到天。

机制层改知识库或改流程。内容工作留下的记录累积起来后，系统判断这次的错在知识还是流程上，据此改动，结构随之变化。这一层的周期是周到季。

知识层的输入来自工程师回报，而这条通道目前没有数据，因此命中率、误诊率、校准都只能标为不可解读。体检器把零误诊与无人回报分开显示，避免把前者读成结论。这是第 8 节第 1 项缺口。

机制层不依赖现场回报，它读的是工作过程中已经留下的记录：诊断记录、重放结果、流程摩擦。上游 issue 沉淀这条路线因此有价值：这些问题的答案在沉淀时已经拿到。

最小链路是一条改进项的完整生命周期：收尾检查留下信号，立改进项，写下可验证的预期，执行改动、验证结果，判定采纳、换方向还是不采纳，合并送审后回写合入记录。这条链路的每一步在第 4 节展开，护栏在第 4.3 节。演进能改的对象只有五类：置信度、知识条目、知识库或流程、目录路由与容量、活跃索引的成员。

## 4 从触发到落地

### 4.2 每一步的判据与落点

| 步骤 | 怎么算数 | 数据落在哪 |
|---|---|---|
| 收尾检查 | 有没有触发信号、收尾记录有没有落。跑了但没有信号与根本没跑必须可区分 | 执行记录（运行时文件，同一个克隆共享） |
| 立改进项 | 每一处都要能追到出处；预期必须写成一条命令加期望值，或者写明为什么不可度量 | 改进项文件（进 git） |
| 执行与验证 | 改哪里就测哪里，检查手段按第 5 节选 | 预期实测记录（运行时文件） |
| 判定 | 改进项是一条有过程的档案：提出、执行、验证、判断。缺一环就是记录不完整，CI 会报错 | 改进项内的追加式决策记录 |
| 合并送审 | 批量的边界明确；每一项独立提交，可以单独撤回 | PR，合入后回写指针 |
| 落地回读 | 回写指针之后，判据读数才反映已合入的实现 | 判据读数 |

两条纪律不能违反。只有想法、没有可执行方案的不立改进项。评分口径与指标定义只有人能改，agent 不能改自己的评分标准。

### 4.3 五类演化动作与对应的护栏

演进能改的对象只有五类，每一类都配了护栏，防止改动引入退化。

| 动作 | 作用对象 | 什么时候发生 | 护栏 |
|---|---|---|---|
| 置信度校准 | 单条知识的置信度 | 每次收到现场反馈（该通道目前没有数据，见第 8 节第 1 项） | 只按已回报的结果回写；同一条连续两次未解决就转人工，防误诊级联 |
| 知识注入 | 知识库条目 | 定位结束，或每周批审 | 人审队列、语义校验、高风险双签，防错误知识入库 |
| 误诊归因 | 知识库或流程 | 每次误诊 | 先读诊断记录判断错在哪一侧，防止在执行出错时误改本来正确的知识 |
| 结构演化 | 目录、路由、容量 | 数据触发，例如容量到上限 | 由数据触发而不是预先规划；改动走高风险双签 |
| 退休与复活 | 活跃索引的成员 | 每周 | 只退休版本过期或长期无效的条目；从没被选中的罕见条目不退休，防止过早删除正确的罕见知识 |

另有三条护栏适用于全部五类动作：

- 自动化只产出建议与证据，采纳由人执行。
- 升级由数据触发，不按日历排期。
- 对照标准不能由被检查的一方修改。

### 4.4 一次现场反馈的完整数据流

一次反馈涉及四个写入点，每个写入点是否进 git 单独决定。

| 写入点 | 写什么 | 进 git | 为什么 |
|---|---|---|---|
| 诊断记录 | 过程，加一条等待回报结果的待办 | 否 | 含客户现场信息；定位结束后留在本地 |
| 知识条目 | 置信度：命中、误诊、分数、最近命中 | 是，走知识修改 PR | 这是知识层的持久状态。命中加一必须入库，才能改变下次候选排序 |
| 索引 | 分数 | 是，生成物 | 条目变了就重建索引，随同一个 PR 走，CI 强制同步 |
| 指标源文件 | 每期一条观测 | 是 | 周节奏、人复核：脚本产出骨架，人看过分母再落期 |

反馈直接写入的是知识条目，它是知识层的持久状态。指标文件是周期性汇总，不随每次反馈写入。必须入库不等于每一单都开 PR：结算与入库按周批量处理一次。

## 5 验证怎么闭环

演进的结论容易停在没有证据的判断上。下面四层检查从弱到强，逐层挡住这类结论。

| 层次 | 手段 | 挡住什么 | 谁来判 |
|---|---|---|---|
| 记录不陈旧 | 观测账本进 CI（`scripts/eval_scorecard.py --check`，账本记回归样本跑过什么） | 回归样本改了而账本没重建，被读成已经跑过 | 机械 |
| 预期可复现 | 改进项里的一条命令加期望值 | 只写在文字里、无法证伪的改进 | 机械，任何评审一条命令就能复核 |
| 前后无回归 | 改前改后对照 | 改坏了原来能命中的场景 | 机械 |
| 对照标准不可自改 | 冻结的对照样本按内容哈希固定 | 同一方既改被测对象又改对照标准 | 机械判定；重新冻结仍需人，见第 6 节 |

检查必须能报错才算检查。从来没红过的检查与没有检查在观测上无法区分。硬性检查因此都配了负例断言：故意改坏被检查的对象，看检查是否报错。这些断言由 `scripts/rehearse_evolve_loop.py` 逐条执行。这条准入标准来自外部研究，见第 13 节的 Falsifiable Release Gates 一行。

已知例外是体检器的判据：它们还没有负例断言，现在通过，但没有证据表明它们能报错。这是第 8 节第 2 项。

数据源缺席时，判据只报无法判定，不写 0 当作满分。体检器带 `--check` 时退出码分三态：0 表示判据全部评过且无越界，1 表示有判据被违反，2 表示有判据未被评估；不带 `--check` 时退出码恒为 0。这样没触发与没检查过不会混在一起。

## 6 哪一步需要人，哪一步可以交给 agent

本节回答哪些步骤以后不需要人做。下表「可退出条件」一列写的是：还缺什么才能把这一步交给 agent。该列的条件都可以核对。

| 步骤 | 现在谁做 | 为什么现在是人在做 | 可退出条件 | 判定 |
|---|---|---|---|---|
| 发起全库体检 | 人 | 系统不知道业务上现在该关心什么；全库体检的自动发起已关掉 | 需要不依赖人的触发源。判据越界已经能机械读出来，缺的是固定去读它的动作 | 部分可退 |
| 立改进项、执行、验证、判采纳 | agent | — | — | 已交给 agent |
| 审查合并 | 人 | 当一项的验证出自自定口径时，评审是仅有的外部约束 | 这个面有能报错的硬性检查，并且预期由外部来源判定 | 部分可退：有硬性检查的面可退，只能自证的面不能退出 |
| 结构性改动：骨架、路由、新 skill 立项 | 两人双签 | 影响面无法局部验证 | 无。设计上不由 agent 单独决定 | 不可退 |
| 重新冻结对照样本 | 维护者 | 对照标准不能由被检查的一方改 | 把对照标准交给独立的第二方持有；代码所有者机制落实后即可退出，退出后由第二方持有，不是交给 agent | 可退，换持有人 |
| 指标口径与评分定义 | 人 | 系统不改自己的评分标准 | 无 | 不可退 |
| 指标源文件落期，复核分母 | 人 | 分母为 0 时读数会被读成没有问题 | 需要现场反馈通道的自动化替代，目前没有 | 现在不可退 |
| 现场反馈回报 | 工程师 | 只有工程师知道修复在自己的环境里是否生效 | 没有机械替代：外部对照只能判断内容对不对，判断不了现场是否解决；严重性语义与环境特异性只有现场能提供 | 不可退 |
| 触发信号表的维护 | 维护者 | 实测表与真实信号族脱钩，多数改进项落不进设计表 | 先要决定是扩表覆盖真实信号族，还是收窄行为、把表外信号归一 | 待决策 |

发起体检缺的是固定去读判据的动作：体检器能报出哪条判据被违反、该执行什么动作，但没有东西定期调用它。可以把体检挂到已有的收尾动作上，让判据越界本身成为触发入口。前提是判据本身能报错：报不出问题的体检器，自动运行也不会产生信号。

## 7 边界与失败模式

机制在缺输入、失败与重复面前的行为集中在本节：能判的判，不能判的报无法判定，不拿 0 或通过顶替。每一条的细节在表里指出的节号。

| 情形 | 机制的行为 | 细则 |
|---|---|---|
| 现场反馈通道没有数据 | 命中率、误诊率、校准一律标成不可解读；捕获计数为 0 时拒绝给出无异常的结论 | 第 8 节第 1 条 |
| 判据没有数据源 | 只报无法判定，不写 0 当作满分 | 第 5 节 |
| 体检器有判据未被评估 | `--check` 的退出码为 2，结论不可用 | 第 5 节 |
| 一项预测无法度量 | 声明不可度量是合法退化路径，计为无法判定，不冒充通过 | 第 4.2 节 |
| 判据点到的仓库文件已蒸发 | 该项预测计为无法判定，不把噪声当信号 | 第 4.2 节 |
| 某个评测面没有判据 | 冻结对照样本的覆盖报告报出有知识却没有样本的格子 | 第 8 节第 7 条 |
| 触发信号表与真实信号族脱钩 | 多数改进项落不进设计表，改表这件事留给维护者决定 | 第 8 节第 5 条 |
| 阈值是未校准的估计 | 越界线按估计值执行，全部通过只证明没有越过猜出来的线 | 第 8 节第 6 条 |

| 情形 | 机制的行为 | 细则 |
|---|---|---|
| 收尾检查跑了但没有信号 | 留一行记录，与根本没跑可区分 | 第 4.2 节 |
| 改进项积压量超上限 | 只记信号，不立新项，停产 | 第 4.1 节、第 13 节 Safe Harness Self-Evolution 一行 |
| 预期不成立 | 记不采纳，保留结论 | 第 4.1 节 |
| 验证过程中出现更好的方向 | 记换方向，新项替代本项 | 第 4.1 节 |
| 人审打回 | 记不采纳 | 第 4.1 节 |
| 同一条知识连续两次未解决 | 转人工，防误诊级联 | 第 4.3 节 |
| 检查从来没红过 | 与没有检查在观测上无法区分；硬性检查都配负例断言 | 第 5 节 |
| 同一轮反馈要多次写入 | 反馈直接写知识条目；结算与入库按周批量处理一次 | 第 4.4 节 |
| 一项改动要撤回 | 每一项独立提交，可以单独撤回 | 第 4.2 节 |

上表之外的行为落在第 8 节：那里列的是机制现在做不到的事，不是做错的事。

## 8 已知缺口

按危害排序。每条都带可以自己核对的判据。

1. 知识层的输入是空的。现场反馈回报通道没有数据。判据：指标体检器把命中率、误诊率、校准一律标成不可解读。它由现场反馈捕获计数驱动，计数为 0 时拒绝给出无异常的结论。补它的动作不在机制侧，在让真实工程师跑完一次诊断、回报结果。

2. 体检器的判据没有被证明会报错。闭环演练对冻结样本、改进项规则、执行记录都有负例断言，体检器的那几条判据一条都没有。它们现在通过，但没有证据表明它们能报错。

3. 外部验证还没有产出第一条独立记录。通道已经建好，选样纪律也写清楚了：样本既不能是这条知识的来源，也不能在这条知识的正文里被引用。但至今没有一条来自另一个现场的独立验证。

4. 对照样本集的规模不够做判定。池子小到配对检验（在同一批样本上逐条比较两侧的命中差异）够不到判定线，实测结论只能落在证据不足。它是验证样本通道，不是判定池。扩容有两条路，代价不同。手工重选会换掉整套对照样本，池内容哈希随之变化，复用计数归零，必须重跑基线。从历史抓样本只在其答案尚未进知识库时有效，而沉淀闭环会持续吸收已验证的答案。样本是否已被吸收，必须在评估运行时按 case 实名逐行重判，不能只信抓取那一刻的读数。分流与运行期重判都已落地：`--build-pool` 把答案已进知识库的样本拆进回归池，`--gate` 拒绝回归池（卡 EV-2026-167）。判定池文件记逐行吸收状态指纹 `absorption_rev`，它与 trace 层那个等于检出短 sha 的 `kb_rev` 不是同一个值，跨机比对会读错值。`--stats` 每次重算，把结论写进 stats。`--gate` 在判定时刻按 stats 记下的逐行样本 id 再算一遍，对不上就拒绝出判词（退出码 3、不写账本）。没有该字段的旧池按未校验放行，读数里写明无法校验。判定池 9 条里 8 条重放完，池中有逐条向量，配对检验有了输入（读数见 [eval-arena.md](eval-arena.md) §3）。选样侧也收成了机械判据（卡 EV-2026-173）。仍要人工做的是新增未吸收样本：从候选中挑样本，标注 expected、`ground_truth` 两项。

5. 触发信号表与真实信号族脱钩。多数改进项落不进设计表：这张表既不是枚举，也没有覆盖真实的触发空间。这属于设计决策，等维护者决定是扩表覆盖真实信号族，还是收窄行为、把表外信号归一。

6. 判据阈值都是没校准过的估计。越界线的数值都是估计值，标注为接受实测重校，至今没有一条被实测校准过。全部通过只证明没有越过猜出来的线，不证明线画在对的地方。

7. 部分评测面没有判据。性能类问题的数值断言、平台键控分支、修复正确性、严重性行为（高危不给修法）这几面目前没有自动判定。判据：冻结对照样本的覆盖报告会报出有知识却没有样本的格子。

|---|---|
| 全库体检的自动发起 | 已关掉：系统不知道业务上现在该关心什么。要重新放开，先要有不依赖人的触发源（第 6 节） |

三块之间不混排：一条机制只能待在一个表里。状态变化时改表，不另起一段叙述。

## 10 明确不做（防过度设计）

- 不把系统做成无人全自动。自动化只产出建议与证据，采纳由人执行（第 4.3 节）。
- 不为尚未出现的问题预建机制。改动由数据触发，不按日历排期（第 4.3 节；原则十一见 [design-principles.md](../spec/design-principles.md)）。
- 不改诊断与沉淀两个环内部的执行规则。它们的规则在各自的 skill 正文里，本文只覆盖机制层（第 1 节）。
- 不让 agent 单独决定结构性改动。骨架、路由、新 skill 立项走两人双签（第 6 节）。
- 不让系统改自己的评分口径与指标定义，也不让被检查的一方重新冻结对照样本（第 4.2 节、第 6 节）。
- 不把判断性规范硬化成 CI 检查。只有机械可查、后果确定、复发至少两次三条都满足才进 CI（第 13 节 Agent Skills Can Be Harmful 一行）。
- 不用改进项数量当进度指标。积压量超上限即停产新项（第 13 节 Safe Harness Self-Evolution 一行）。
- 不用向量检索替换词法召回（第 13 节 大 skill 库检索比较 一行；决策记在 `docs/adr/`）。

| 外部研究 | 它证明了什么 | 本仓库对应的设计 |
|---|---|---|
| [Knowledge-Centric Self-Improvement](https://arxiv.org/abs/2607.19592) | 自我改进的持久对象应当是受治理的知识库，不是 agent。这样的改进可审、可迁移，能迁到未见任务和不同模型家族 | 知识库是资产、agent 可弃这条总的论题；三级知识与 skill 自包含 |
| [RSEA](https://arxiv.org/abs/2606.28374) | 在独立对照集上严格更好才留下，是递归自演化保持单调安全的条件。它用无检查的在线策展做对照：一个基准接近最优，另一个崩到 0.14 | 冻结对照样本按内容哈希固定；此前通过的不许变为失败 |
| [PACE](https://arxiv.org/abs/2606.08106) | 短板在接受规则，不在提出方案的一方。分数涨了就收，重复多次相当于对自己做多重检验；有真改进时也有三到四成的假接受 | 对照评分改成同批题配对比较加复用折减；判定三态，只有接受算通过 |
| [Ratchet](https://arxiv.org/abs/2605.22148) | 判定器把失败误判为通过时，任何样本量都退不掉一条坏知识。自写内容的增益接近 0，人写的增益显著为正 | 来源自报与独立命中分开计数 |
| [Library Drift](https://arxiv.org/abs/2605.19576) | 不维护的知识库会漂移到注入了反而更差。过早退休同样有害 | 命名空间容量上限、软退休；罕见但正确的条目不退休 |
| [StarHarness](https://arxiv.org/abs/2608.24804) | 把演化用的样本分成三方：方案方可见、对方案方隐藏、另留泛化，增益在被排除出演化过程的任务上仍然保持 | 候选样本与冻结对照样本分离；对方案方隐蔽的选样集等池子规模达标后再评估 |
| [Falsifiable Release Gates](https://arxiv.org/abs/2607.13070) | 不能报错的检查与没有检查在观测上不可区分。作者要求故意弄坏被检查对象，看检查器会不会给出最短反例 | 闭环演练里的负例断言：改冻结样本必红、删除必红、重新冻结需打标签 |
| [大 skill 库检索比较](https://arxiv.org/abs/2608.06196) | 用关系图或嵌入替换词法召回会显著更差。作者自己写的查询会把命中率高估最多 44 点 | 检索不上向量库；评测查询必须来自真实记录 |
| [Agent Skills Can Be Harmful](https://arxiv.org/abs/2608.11888) / [SkillsBench](https://arxiv.org/abs/2602.12670) | 更大更全的 skill 反而更差。最大的效率退化来源是过度验证，也就是把验收清单变成必须执行的工作 | skill 保持聚焦、行为规则内联；判断性规范不硬化成 CI 检查 |
| [Safe Harness Self-Evolution](https://arxiv.org/abs/2609.08175) | 生成与认证是两个不同的约束。评估受限时，多产候选并不提高成功更新的保证 | 不以改进项数量作为进度指标；积压量超上限即停产新项 |
| [Dream-RSI](https://arxiv.org/abs/2609.14858) | 一条完整的历史是精确的重放模拟器：换策略在同一棵决策树上走不同分支，结果已在盘上，评估零执行；前提是策略为可重算的代码。把历史抽象成方向性洞见注入提示词，同预算下一致地不如不注入 | 探索策略里机械化的那一半（同时展开几个候选、顺序、并行分组、停止点）可以用历史树离线打分，语义判断留给在线。<br>历史进系统用可检索的锚点形态，不用叙述形态。<br>历史覆盖面靠跨机汇集：知识库版本号 `kb_rev` 写进诊断记录 |

这张表给的是背书与准入标准，不能直接照搬：外部系统的对象与数据规模与本仓库不同。每一条落到本仓库都要过一次适用性判断，判断结果与落地状态记在调研物料里，被否决的替代方案记在 `docs/adr/`。
