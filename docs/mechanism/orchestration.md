# 编排与治理：自演进会话、目标函数、token 预算

> 给谁读：要改自演进会话协议、目标函数或预算的人。
> 什么时候读：你要改会话怎么开始、一轮的边界与停止条件、token 预算怎么算时。
> 读完能做什么：说出一次自演进会话的边界，即读什么、何时停、花多少。
> 本文属论证层，日常执行不必读。执行规则与机制地图见 [rsi-mechanism.md](rsi-mechanism.md)。

> 三份文档的分工：[pipeline.md](pipeline.md) 是机制总览（三层闭环、分级授权、状态机、落地节奏）；[execution.md](execution.md) 是单条 proposal 的执行契约（记录什么、follow-up 怎么验证、沉淀效果怎么度量）；本文是编排与治理层，回答把自演进当成会持续运行的自动化系统时的问题：人一开始怎么下指令；一轮的边界与目标是什么；token 预算与停止条件怎么设；token 使用效率本身是不是优化项；系统改自己的 skill 时怎么防止自我确认偏差。把一轮轮会话装配成长期持续运行，见 [run.md](run.md)（长期任务、issue 评测循环、执行记录、可视化）；面向使用者的指令、报告与干预语言，见 [evolution-user-guide.md](../guide/evolution-user-guide.md)。
> 推导依据：原则五（建议与决定分离）、七（变更可逆）、八（可观测先于改进）、九（资源预算）、十（诚实退化）、十一（数据触发）。理论见 [design-theory.md](../spec/design-theory.md) §4.2–4.4（元层信念、自演进闭环、演化即假设检验）与 §6（token 是预算资源，有价格）。本文自身的修订属于 L3 结构，走 methodology PR 加体系维护人审。
> 文中 G1 到 G8 是从自动化与演进流程视角审视前两份文档时发现的治理缺口编号：G1 会话层缺失、G2 无目标与停止、G3 自我指涉、G4 同轮冲突、G5 无全局上下文、G6 无成本侧、G7 无稳态降频、G8 无暂停重启。补上缺口的小节在标题里标出编号。

## 1. 会话模型：一轮自演进是一个有状态会话

### 1.1 为什么需要会话

pipeline.md 与 execution.md 定义了「一轮里每一步怎么走」，但没有定义「一轮」本身的边界。没有会话边界会出现三种问题：没有入口协议，人不知道从哪开始；没有轮间衔接，每轮从零开始；没有恢复点，被打断就丢进度。

会话就是自演进的一次可审计运行：有 state 文件、可以 resume、有报告，与 diagnose session 同构。

### 1.2 会话生命周期与启动协议

自演进是隐形执行策略，用户不必复述机制。下指令时只说目标与必要边界；机制细节（观测什么信号、走 S2 评测、feedback loop、proposal→action→eval、授权分级、停止条件）由系统的默认执行策略自动装载，就像用户让「跑一次诊断」不需要复述 triage 流程。要求用户每次说「要 xxx 观测数据加自演进」是把实现细节强加给人，违背原则九（注意力预算：人的输入成本要低）。

演进评估默认是内容执行的收尾动作，不构成独立目标。用户下的是内容目标（沉淀、补 case、诊断）时，该内容流程收尾自动执行 evolve-check（见 `/skill:evolve-check`），把「新数据能否让系统更好」的信号（同族 case 可归纳、miss 暴露缺口、流程摩擦、可复用链路）转成候选卡并自行验证。用户不必为改进单独立目标，也不必为改进单独开轮。只有深度全库体检（没有内容目标）才走本节会话协议。

| 步骤 | 谁 | 做什么 |
|---|---|---|
| ① 目标 | 人 | 一句话给出范围、意图与可选的预算上限，例如「提升 vllm-ascend interrupt 命中率」「降低最近的回滚」「看 verl 有什么可沉淀的」。机制一律不说 |
| ② 装载默认策略 | agent | 从目标推断 scope、goal 类别、数据前提（S2 池够不够、feedback 有没有），自动带出观测信号集、候选生成、授权分级、停止条件与预算分层（本文的全部默认值） |
| ③ 对齐 | agent 给人 | 回显理解，例如「我理解为：范围 X、目标 Y，将按默认策略跑一轮（约 Z token）」，同时请人确认运行模式（`approval_policy`，pipeline.md §6.3a 定义介入度） |
| ④ 计划 | agent | 产出执行计划：候选 proposal 清单、预计 token 与轮次、依赖顺序 |
| ⑤ 确认 | 人 | 批准或调整（建议与决定分离在会话层的形态） |
| ⑥ 执行与报告 | agent | 轮内按计划执行，产出报告，存档，可以 resume |

第 ③ 步要人选的运行模式有两种，介入度不同：

- 全自动（`hands-off`）：改到目标完成，一次性交一个聚合 PR 给人审。每笔改动都有 proposal 记录、独立验证门与独立 commit。这个模式需要用户明确要求，不是默认值。
- 关键人审（`default`）：自动跑，关键改动攒到轮末一个聚合 PR 给人审。`auto` 级即时合入，`review` 与 `dual` 级攒批。

以下情况先澄清再执行，不边跑边猜：

- 范围或目标有歧义（如「优化系统」）。要问清是哪一层、哪个 namespace；
- 数据前提不满足（如目标提命中率但 S2 池还没建）。要说明先建池，或改用现有数据；
- 目标互相冲突或与现状矛盾（如「零人工」但目标含生产变更，而自演进不改生产）。冲突需要澄清；
- 用户表述含糊（「感觉没想清楚」）。给 2 到 3 个候选目标让用户选，不代用户决定。

对齐这一步必须有。自演进是隐形策略，系统主动性强，一旦跑在错误目标上，浪费比人工还大：一轮就是几十 K token。对齐的成本只是一句回显加至多 2 到 3 个问题，换来整轮跑在用户真实意图上。对齐确认的是目标本身，不是让用户补机制描述（机制是默认的）。这也是原则五在会话入口的形态：agent 提出理解，人校准目标，然后才授权执行。

对齐要说用户的语言（UX 规格见 [evolution-user-guide.md](../guide/evolution-user-guide.md)）。回显与提问不使用内部术语（S2 池、结构层、授权分级、观察窗），一律翻译成使用者领域的说法：说「需要先拉一批历史 issue 当测试集」，不说「S2 池未建」；说「涉及路由或流程本身的改动会先请你确认」，不说「结构层走 dual」。术语解释放在可展开处（tooltip、details），不占主对话。对齐的输入是领域目标，输出也应是领域语言，否则对齐本身就带来新的理解负担。对齐还要说清冷启动的预期路径：数据基础不足时（如没有测试集或没有反馈记录），明说「当前数据基础是 X，第一轮先建测试集，预计第 N 轮起才有真正的 X 判断；期间会产出覆盖缺口清单这类可用结果」，避免用户期待改进却只收到基建报告（见 [evolution-user-guide.md](../guide/evolution-user-guide.md) §3）。

机制参数（观测信号集、S2 池口径、授权分级阈值、预算分层、停止条件）都有文档默认值，用户不必说。用户只需覆盖自己关心的部分：范围、意图、预算上限、特殊约束（如「这轮不许动 triage」）。覆盖是例外而不是常态，绝大多数指令走到第 ③ 步对齐即可，第 ⑤ 步确认一键放行。

会话状态落 `proposals/sessions/<SESSION-ID>.yaml`，内容含 session id、参数、计划、每卡进度、已耗 token、停止原因与报告引用。它是运行时状态，本地留存并写进 .gitignore（.gitignore:67 的 `proposals/sessions/*`），与仓库对 `traces/` 和 inbox 草稿的处理一致：逐轮变化的进度与账本不进 git，避免噪音与跨机断链；稳态结果以报告与采纳卡的形式进 git。会话可以 resume：中断后重新加载 state，未完成的卡继续，已完成的卡不重跑（幂等，与 issue-ingest 的 processed 排除同一做法）。

## 2. 目标函数与停止准则

### 2.1 每轮判读框架（G2）

用户 goal 决定本轮做什么，包括候选排序权重与停止条件；「做得怎么样」由判读框架衡量。两者不冲突时，判读框架是选择依据；冲突时用户 goal 优先，用户明确的意图不被覆盖（原则五：用户是损失承担者）。判读框架有两个用途：

- 候选排序：同一个 goal 下多个候选都符合时，增益高、成本低、风险小的先做；
- 报告判读：衡量本轮增益是否盖过成本。

判读用三个定性问题，不做公式计算：

- 效果增益：`predicted_effect` 的达成率（归因事件簇回落、S2 对照命中率提升、命中率上升）；
- 成本：本轮 token 消耗（没有记账环境时用估算，并标 `source: estimate`）；
- 风险：回滚与误诊的代价，把高风险区域压向更保守的授权级别。`dual` 是门禁不是否决：结构类候选由数据信号触发，风险权重不压制它。若某类结构改动长期被数据指向却始终不做，季度自评要复核这是流程阻碍还是风险权重的问题。

每轮报告按这三个问题给出判读：产出 `validated` 卡 X 张、耗 token Y、回滚 Z 次，增益是否盖过成本。框架是给人读的，不是可计算的公式。

### 2.2 停止条件（G2）

任一条件满足即停。停止后出报告，不硬断，state 保留可恢复。

| 条件 | 触发 | 含义 |
|---|---|---|
| 预算耗尽 | `token_budget` 用尽 | 本轮边界，最常见 |
| 产出达标 | `validated` 卡达 N 张（默认 3） | 已产出足够，不再贪多 |
| 信号误报 | 连续 M 个候选被否决（默认 3） | 信号质量差，停比继续堆好 |
| 收敛 | 本轮没有新候选，或全部卡进入 `rejected` 与 `validated` | 数据已榨干 |
| 人中断 | 人在任一步打断 | 优先级最高 |

### 2.3 稳态降频（G7）

这一节是蓝图，触发条件是 scope 真实收敛；[pipeline.md](pipeline.md) §11.1 把它列在「触发后实现」一列。在那之前，停止条件里的「收敛」已经够用。

某 scope 连续两轮满足四个条件时标记为 `steady`，并进入降频池（默认停 4 轮再复检）：没有新信号；没有 `rejected`；没有降级态积压（`unconfirmed_valid` 与 `unconfirmed` 卡为 0）；`validated` 效果达标。降频的目的是不在已经收敛的区域继续烧 token。降级态积压不算收敛：还有未决的存疑卡说明这个区域仍有待处理项，降频会把它们掩盖。`steady` 状态记录在 session state 或索引里；新信号（新 issue 类型、新 trace 模式）或新降级态出现时自动解除。稳态是数据触发的暂停，不是永久关闭（原则十一）。

### 2.4 候选积压治理

候选 idea 每天由信号产生，但消化受轮次预算与人审节奏限制。没有治理，候选池会积累过期候选、重复候选与低质卡。治理沿用仓库 inbox 的纪律：队列不是档案。

第一条（水位读数）已经落地。启用依据是数据而不是日历：设计定的启用条件是「候选积压真实发生（池内超过 20 张）」，实测该条件早已满足，积压从 0 单调升到数十张；而 skill 正文那句「水位超限时只记信号不产卡」既没有数值也没有读数，规则只写在散文里。落地形态是可机械读取的读数加退出码：

- 候选水位上限是 `proposals/gates.yaml:41` 的 `backlog_over` 判据，默认值 20。口径是「已验证且没有合入指针」的卡数，也就是该判据的分子。超限时停产新候选，优先消化积压；信号继续记录，但不产卡。
- 读数与动作：`python3 scripts/ev_proposal.py --waterline`（默认上限 20 见 `scripts/ev_proposal.py:244`，超限退 1）。产卡前先读它，超限时本轮只记信号。
- 先回写再判：读数里含「合入指针没有回写」的成分。超限时先跑 `python3 scripts/ev_proposal.py --mark-merged --from-prs` 把指针补齐（按已合入 PR 逐卡匹配，匹配不上的报出，不做猜测），再看剩余量。否则会把已经合入的卡当成未合入，把动作引向「暂停产卡」这个错方向。实测同一时刻两处读数不等（8 张与 0 张），差的正是指针没有回写。
- 候选过期（蓝图）：候选停留超过 8 周（参数待校准）且从未被采纳时，status 标 `stale`，季度自评批量转 `rejected` 并记理由「长期未采纳」。`stale` 与 `rejected` 都不删除记录，与 rejected 留痕纪律一致。这一条还没有出现「停留 8 周从未采纳」的实例，[pipeline.md](pipeline.md) §11.1 把它列为蓝图；在那之前先用 inbox 式标红。
- 重复候选：起草时若同一个 trajectory 或同一个 target 已有在池候选，合并而不是新建。起草 agent 检查在池卡，与 §5.2 的冲突检测同源。
- 信号误报反馈：候选积压率高，说明信号产卡的速度超过消化能力，要下调该信号的触发权重（参数级自校准见 [pipeline.md](pipeline.md) §5.1），不是无限扩池。

## 3. Token 预算与成本侧

### 3.1 会话级预算分层（G6）

| 阶段 | 默认占比 | 说明 |
|---|---|---|
| 观测 | 10% | 跑信号脚本。脚本本身的开销应当接近 0，大头是读聚合结果 |
| 起草 | 30% | 读卡、归因事件聚合、先例，加起草 proposal（分层供给：先聚合后全文） |
| 实验 | 50% | 占比最大：执行 validation，包括 replay 与复测 |
| 报告 | 10% | 会话报告，加季度自评的输入 |

占比是执行参数，由实际用量实测校准（进 timeline，季度复核），不是定额。

### 3.2 卡的成本侧字段（G6）

成本字段已经并入 [pipeline.md](pipeline.md) 第 7 节的 schema，那处是唯一事实源。本节只重申语义：

```yaml
predicted_effect: {metric: "...", from: X, to: Y}   # 质量预期（execution.md 第 2 节）
predicted_effect.measure: {command: "...", expect_exit: 0}   # 预测的出处（可复现，execution.md 第 2、7 节）
actual_cost: {tokens: 9500, source: estimate}       # 写回后必填，缺失即审计缺口
```

`actual_cost` 随 `decisions` 一起写回，并进 timeline。没有实际成本记录的 proposal 不可审计，强度与「无实验证据不合入」相同。成本字段只有一个：旧的 `estimated_cost` 已废弃（仓库里还有 6 张旧卡带着这个字段），在没有 token 记账的情况下它只是文书。

### 3.3 Token 效率作为指标

- 每张 `validated` 卡的平均 token。趋势上升说明演进变贵，触发效率审查；
- 阶段占比漂移。某阶段占比异常上升说明该环节退化；
- 候选到 `validated` 的漏斗。起草大量卡而 `validated` 很少，说明起草或信号质量差，token 花在无效候选上。

这三个指标回答一个决策问题：演进系统本身是否在变贵，该在哪一环省。这也是 roadmap.md 里 groom token 治理（groom 单次全量扫描知识库与 references）从一个一次性修复变成持续目标维度的形态。

### 3.4 Token 效率作为优化项

归层上它属于 L3（编排层），也可以算 L2 的流程维度；优化的是系统产出的成本，不是知识内容。

可以自动触发候选的信号有三类：

- 每张 `validated` 卡的 token 连续两轮上升；
- 某阶段占比超过预算占比的 1.5 倍（如起草长期超过 45%）；
- 同一组件重复提案。归因事件聚合显示该组件被改过并且回滚过，又出现新卡，先查是否可以直接复用教训、省掉分析。

典型提案见下表。

| 提案 | 例子 | 验收判据 |
|---|---|---|
| 信号脚本瘦身 | 让 `scripts/trace_metrics.py` 直接输出候选卡骨架，起草 agent 少读原始聚合 | 同一输入集下，输出卡与脚本化前的输出逐张一致，且起草阶段 token 低于改前实测值 |
| 分层供给调优 | 决策点先给聚合、判定前才展开全文（execution.md 第 7 节已有），调「展开阈值」 | 判定准确率不降（抽审发现率不升）且 token 下降 |
| prompt 精简 | 起草与实验 prompt 去掉冗余指令 | golden 回放无回归且输出一致性达标 |
| 先例复用 | 同组件已有 `rejected` 或教训时，直接把教训附给 agent，不再重新分析 | 重复提案率下降 |

token 优化提案有一条验收硬规则：不得牺牲供给完整性（execution.md 第 7 节说明信息不足会损害执行质量），验收必须是「A/B 同质量省 token」，即 golden 无回归、抽审发现率不升、输出一致性达标。用 token 换质量是把成本转移到没有预算科目的地方，违反原则九（design-theory.md §6 的评审纪律）。

## 4. 自我指涉治理（G3）

演进对象（skill 与知识库）与演进引擎（agent）同源，最危险的失效是系统改了自己的 skill，然后用自己定义的指标证明改对了。对抗机制都是已有的零件，这里显式列出来。

| 机制 | 对抗什么 | 落点 |
|---|---|---|
| 客观评分源优先 | 自评指标漂移 | follow-up 判定优先用 S2（issue 的外部 resolution）与 golden，S1 工程师反馈优先于归因事件自评（execution.md 第 5 节的观察窗已按此排序） |
| 独立评审 | 起草 agent 自我背书 | `review` 与 `dual` 级合入由 reviewer 或双签人审；`auto` 级月度抽审，授权可撤销（pipeline.md §6.3） |
| 回滚率入指标 | 错误合入被掩盖 | 回滚率是授权级别校准的输入（execution.md 第 6 节），上升即收紧 `auto` |
| 归因教训复用 | 重复犯同一个错 | 归因事件记教训，新提案必须引用先例（execution.md 第 7 节） |
| 季度自评审视指标本身 | 指标定义被演进「优化」掉 | 自评审的对象不是卡，而是流程与指标是否还在测对的东西（pipeline.md §6.6） |

自演进有一条显式红线：提案不得修改评分与指标定义本身，也就是不得让指标更容易达标。指标口径的变更只能由人走 methodology PR 发起（L3 结构级，双签），agent 只能建议，不能执行。这条红线是自我指涉治理的闸门：违反它，被评的一方就能改写评分标准。

## 5. 全局上下文页与执行编排规则（G5、G4）

### 5.1 全局上下文页（G5）

agent 执行自演进前要加载一页系统运行状态，替代每轮从零摸索，也控制重复读取的成本。下面两部分的生命周期不同，分开存放：

```yaml
proposals/sessions/<SESSION-ID>.context.yaml    # 会话级快照（运行时状态，gitignore）
  每个会话开头由观测 agent 生成，控制在约 2K token 内：
  - 当前知识库规模（python3 scripts/index_counts.py）与覆盖缺口
  - 处于观察窗或实验期的组件与卡（谁在动，避免冲突）
  - 最近 N 轮会话结论（采纳、回滚、稳态标记）
  - 当前授权白名单（哪些类目可用 auto）
  - 指标快照（四层，最近 2 期）

proposals/strategy-memory.yaml                  # 策略记忆（跨会话累积的资产，人确认后进 git）
  结构级教训的持久层，随季度自评追加，不随会话重新生成
```

策略记忆属于蓝图，触发条件是季度自评跑通至少一轮（[pipeline.md](pipeline.md) §11.1）；在那之前，结构级教训并入 session context 即可。归因事件记的是「组件失败」这类单点教训；结构级教训，例如「这个 namespace 用 category 轴拆比 platform 轴好」「该 issue 池里 workaround 类 resolution 占比高，应当降权」，需要跨轮累积，否则季度自评的结论会随会话结束而丢失。做法是：季度自评的结构性结论追加进 `proposals/strategy-memory.yaml`，每条带日期与依据的指标引用；后续会话的 context 快照引用它作为决策上下文（对应 SkillOpt 的 meta-skill 思路，载体是词法文本，可 diff 可审）。记忆条目由人确认后写入（季度自评产出），agent 只建议，不直接写。策略记忆是资产（进 git），会话 context 是快照（写进 .gitignore），两者不混放，避免策略记忆随会话重新生成而丢失，或被运行时状态覆盖。

生成成本计在观测阶段。执行 agent 只读这一页加自己卡的证据，不重复全量扫描；token 预算与 groom 的脚本先行纪律同源。

### 5.2 执行编排规则（G4）

| 规则 | 内容 | 理由 |
|---|---|---|
| 同组件串行 | 同一个 `target_component` 的卡不并行实验，排队 | 并发改同一个组件就无法归因 |
| 冲突检测 | 计划阶段检查候选改动范围的交集：相同文件、相同 namespace 的写入都算冲突，冲突卡降级为串行或合并。当前靠读卡判断，没有机械检查：`affected_paths` 这个字段还没有进卡 schema | 防修好 A 弄坏 B 且无法回测。粒度不止组件：不同组件可能改同一个 case 文件（git 同文件并发写会冲突），冲突检测要覆盖改动的文件集与 namespace 目录 |
| 依赖排序 | 有依赖的卡先执行，例如先补 case，再改引用它的 triage | 实验基准有效 |
| 变更集原子 | 一轮内对同一组件的多次小改合并为一次合入加一次回测 | 回滚粒度清晰 |

## 6. 原则追溯

| 设计元素 | 服务的原则 | 说明 |
|---|---|---|
| 会话协议（目标→对齐→确认→执行） | 五（建议与决定分离） | 人给目标与边界，agent 装载默认策略并回显对齐，人批准后执行 |
| 目标函数与停止条件 | 十一（数据触发）、九 | 没有目标就无法判定达成；没有停止条件就无法审计 |
| 稳态降频 | 十一、九 | 已经收敛的区域不再空转烧 token |
| token 预算分层加 `actual_cost` 写回 | 九（资源预算） | token 是预算资源，使用必须可审计 |
| token 效率提案的 A/B 同质量验收 | 九 | 预算优化不得把成本转移到质量上 |
| 指标口径只能由人改（红线） | 十（诚实退化）、二 | 被评的一方不得改写评分标准 |
| 客观评分源优先 | 八（可观测先于改进） | 外部 ground truth 优先于自评 |
| 同组件串行、变更集原子 | 七（变更可逆） | 归因与回滚粒度清晰 |
| 全局上下文页 | 九、二 | 每轮加载最小充分状态，避免重复扫描 |
