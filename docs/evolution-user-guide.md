# 自演进用户指南：一句话开始，全程可看可干预

> 这是**使用侧的 UX 规格**（面向"用自演进系统改进诊断"的工程师），不是机制文档。机制在 [evolution-pipeline.md](evolution-pipeline.md) / [evolution-execution.md](evolution-execution.md) / [evolution-orchestration.md](evolution-orchestration.md) / [evolution-run.md](evolution-run.md)。本文回答使用时的五个问题：**我能说什么？一句话后会发生什么？怎么知道它在跑？怎么知道它跑得对不对？中途想改怎么办？**
> 状态：**第一批能力已可用**（self-evolve skill + 工具链已落地：产卡/校验/攒批聚合 PR/补 case 沉淀）——见下文"当前可用"标注；标"蓝图/待数据"的能力（长期任务层、token 效率、可视化面板等）是设计目标，触发条件到才实现（evolution-pipeline §11.1）。

## 1. 你能说什么（指令示例菜单）

自演进是**隐形执行策略**——你只说目标与必要边界，机制（观测什么、怎么评测、谁审、何时停）由系统默认承接。下表是常见指令；**"当前可用"列 ✅ = 现在就能用，⚠️ = 设计目标（部分能力待蓝图/数据）**。不确定时直接问"我能让它做什么？"——系统会展示当前可用的菜单。

| 你说 | 系统理解为 | 触发 | 当前可用 |
|---|---|---|---|
| "跑一轮自演进" / "看看有什么可改进的" | 目标未定 → 先对齐（给候选目标你选），再按目标执行 | 一轮自演进 | ✅（self-evolve skill） |
| "我想做 reference 沉淀" | 目标=沉淀先验 → 问清类别/源 → 抓文档/case 归纳 → 草稿待审 | reference 沉淀轮 | ✅（fetch_docs + to-reference） |
| "从 vllm-ascend 的 closed issue 补 case" | 目标=补覆盖，**数据源=用户指定 vllm-ascend** | 拉指定源 → replay 测缺口 → 补 case | ✅（auto_fetch --source + 链路） |
| "持续改进 vllm-ascend 的诊断命中率" | 范围=vllm-ascend，目标=提命中 | 拉该仓 issue + S2 replay + 补 case | ⚠️ 一轮可做，长期任务待蓝图 |
| "这周有哪些值得沉淀的 verl issue？" | 范围=verl，目标=补覆盖，单轮盘点 | 一轮盘点 + 沉淀候选 | ✅（issue-ingest + to-postmortem 链路） |
| "自演进最近变贵了，查一下" | 范围=编排层，目标=省 token | token 效率诊断轮 | ⚠️ 蓝图（token 记账未落地） |
| "把最近的回滚分析一下" | 范围=全库，目标=降回滚 | 回滚归因轮 | ⚠️ 待数据（当前无 rolled_back 卡） |
| "暂停/停一下" "方向不对，改重点看 performance" "这条改动有问题，回滚" | 见第 5 节 | 中途干预 | ⚠️ 部分（暂停/停可；回滚需卡已合入） |
| "全自动跑，做完给我看" / "关键改动攒着，轮末给我审" | 运行模式选择（见下） | 设置 approval_policy | ⚠️ 机制已设计，执行层随批提交落地 |

**目标不清晰时系统会先问清（grill），不猜着跑**：你说"做 reference 沉淀"它不会自作主张去拉 issue——会先问沉淀哪类、从哪个源。**数据源由你指定**：系统不默认拉所有仓库/爬所有文档，只说你要的（"用 vllm-ascend 的 issue""爬 CANN 环境变量文档"）。目标模糊没关系，说出来后系统给候选目标让你选。

**运行模式（介入度，你选）**：第一次跑或明确要求时，系统会问你偏好哪种：
- **全自动**（默认）：agent 改到目标完成，一次性给你一个 PR 审；每个改动有记录 + 验证 + 独立 commit，高风险项会标注——适合你信任的常规优化；
- **关键人审**：自动跑，但需要判断的改动攒到轮末一个 PR 给你审——适合你想把关的场景。

## 2. 一句话后会发生什么（用户视角）

你下指令后，系统按六步走，但**你只需参与其中三步**：下目标（第 1 步）、确认理解（第 3 步）、批准计划（第 5 步）——其余（装载默认策略、产计划、执行）由系统自动完成：

```
① 你说目标 → ② [系统装载默认策略，不用你管] → ③ 系统回显理解请你确认
→ ④ [系统产计划] → ⑤ 你点批准 → ⑥ [系统执行，你在面板上看进度] → 你收报告
```

- **你确认的那一步**：系统会用大白话回显"我理解为：改进 vllm-ascend 的命中率，本轮约花 X，涉及路由/流程的改动会先问你"。**听不懂的术语会翻译**——例如"需要先建测试集"而不是"S2 池未建"；若仍不清楚，点术语旁的解释展开。
- **你只需要批准**，不需要补任何机制描述。
- **你什么时候需要审（取决于运行模式）**：全自动模式下，改动全部攒到**目标完成时的一个 PR** 给你审（每个改动有记录 + 验证 + 独立 commit，高风险项标注，你可按卡打回）；关键人审模式下，需要判断的改动攒到轮末一个 PR 给你审。**两种模式都不会每个改动单独开 PR 打断你**。低风险改动在面板可见、无需你逐条操作。
- 如果系统觉得你的目标没说清（太宽、互相矛盾、数据还不够），它会先问至多 2–3 个问题**再开始**，不会自己猜着跑。

## 3. 怎么知道它在跑、跑到哪了

执行期间面板显示（或对话里简短播报）：

- **进度**：当前阶段（拉数据 → 评测/沉淀 → 提改进 → **验证（合入前完成）** → 攒批 → 合入）+ 预计剩余（按会话 token 预算与已耗的线性推算，是 UI 呈现行为，非机制承诺——实际停止以机制停止条件为准）。**验证发生在合入前**（用历史 issue/回放检查改动是否真有效）；只有依赖真实场景的改动（如新 case 是否在现场命中）合入后才进入跟踪回测——进度里会显示它在观察窗内等待真实使用确认，不是合入即算完。
- **关键节点通知**：有新候选、有改动等你看/批、本轮结束——**需要你的时候会叫你**，不需要你盯屏；
- **长期任务节奏**：若开的是"持续改进"，会告诉你预期节奏（按 issue 增量，预计本周 X 轮）。

第一轮如果是在"打基础"（建测试集、接记录），系统会在开始时就说清：*当前数据基础是 X，第一轮先建测试集，预计第 N 轮起才有真正的命中率判断；期间会同步产出覆盖缺口清单这类可用结果*——不会等你期待改进时只收到基建报告。

## 4. 怎么知道它跑得对不对（读报告）

报告**首行回答你最初的目标**，机制细节折叠在后面：

> 目标：提升 vllm-ascend interrupt 命中率。
> 本轮：新增 case 2 条，覆盖此前未命中的启动参数类问题；在 20 条历史 issue 上回测 3/7 → 5/7。验证依据：真实 issue 对照（非系统自评）。
> [展开] 卡明细 / token 消耗 / 待你审的改动

每条结论标注**证据强度**，你可据此判断信多少：

| 标注 | 含义 | 可信度 |
|---|---|---|
| 真实 issue 对照验证 | 在已解决的 issue 上验证通过（外部答案对照） | 高——可点开看是哪几条 issue |
| 工程师反馈确认 | 现场工程师回报解决了 | 最高——但目前很少（需要你回报） |
| 仅回放无回归 | 系统自评 + 旧样本不回退 | 中——作为下限保障 |
| 观察窗超时降级 | 没等到现场反馈，按现有证据降级结算（"检索有效未确认"或"存疑待重审"） | 低-中——见标注，不冒充已验证 |
| 系统推断 | 无外部验证 | 低——仅供讨论 |

注：报告里若出现"检索有效未确认 / 存疑"类标注，意思是系统等了一段时间没等到现场反馈，按诚实规则降级结算了——**不是验证通过**。若你希望它升级为真验证，回报一次现场结果即可（见第 5 节干预）。

任何一条都可**点开证据**（哪条 issue、改了什么、前后指标）——你不必只信系统自评。

## 5. 中途想改怎么办（三种干预）

| 你说 | 发生什么 |
|---|---|
| "停一下" | 本轮停止，出已完成的中间报告，状态保留 |
| "方向不对，改重点看 X" | 当前方向终止，未完成项保留，按新方向继续 |
| "这条改动有问题，回滚" | 该改动回滚到改动前，记录留痕（可查为什么改、为什么回） |

暂停后可随时恢复，恢复时会先跟你对齐新目标再继续（不原样硬跑）。

## 6. 边界：系统会改什么、不会做什么

**先说清"self-evolving 改什么"——它覆盖三层，全都改**：

| 层 | 系统会做什么 | 何时给你看 |
|---|---|---|
| 知识内容（case/reference） | 补 case、修 typo、调版本区间、沉淀新知识 | 每个改动有记录 + 验证，攒进最终 PR（全自动模式）或轮末 PR（关键人审模式） |
| 流程/skill（diagnose/groom 等实现、triage 分支、脚本） | 提出改动、实验验证、按数据驱动推进 | 同上——每个改动源于一张 idea 卡、有独立验证与 commit |
| 工作流本身（机制、指标口径） | 提出演进 idea、实验 | **永远你审**（双签）——指标口径只能人改，这是红线 |

**所以"不会改 skill"是误解**：系统**会**改 skill——组件台账反复指出某流程步骤出错时，它会起草改进、过验证门、进 PR 经你批准后合入。self-evolving 的"self"指**系统自己提出并验证改进**（数据驱动、可追溯、有实验证据），不是指"无人监督地乱改"。

**真正的边界（也请你别期待）**：

- **人审是最终闸点，不是没有**：无论哪种运行模式，改动最终都通过一个 PR 合入——全自动模式是"改到目标完成一个 PR"，不是"永远无人看"。每个改动有 idea 卡记录 + 验证 + 独立 commit，你可按卡打回；
- **指标口径只有人能改**：系统不能改自己的评分标准（防止"给自己改考卷"）——这条任何模式下都不破；
- **不会碰客户现场**：诊断与改进都基于你贴的信息与公开 issue，不改生产环境；
- **不会承诺"全自动永远对"**：自动改动的正确性靠验证门 + 后续跟踪回测确认，发现错了会回滚并告诉你——验证确认"真的解决问题"是合入后的必做步骤，不是假设它一定对。

## 7. 术语对照（机制语言 → 用户语言）

| 机制语言（文档/日志里） | 用户语言 |
|---|---|
| S2 issue-replay 校准 | 用真实 issue 对照验证 |
| selection/test 分离 | 用没练过的 issue 做最终验收（防"记住答案"） |
| candidate → validated | 提改进 → 验证有效 |
| 观察窗 / follow-up | 改完跟踪一段时间看是否真有效 |
| auto/review/dual 授权 | 自动合入（低风险，有抽审）/ 请你审 / 双签 |
| 回滚率 | 放错的改动比例 |
| 稳态降频 | 这块已经收敛，先不折腾它 |
