# Skill 改动评估（golden 回归套件）

知识库的变更有指标反馈：confidence、命中率、误诊率都会随使用记录下来。对 skill 本身的改动（流程措辞、步骤顺序、输出格式）没有这样的反馈通道。这套 golden 回归套件用于补上这个缺口：在改动前后各跑一遍固定的诊断输入，确认原本能正确命中的场景没有被改坏。

## 机制

每个已解决的诊断可以转化为一个测试夹具（fixture，见 `eval/golden/`）：固定输入（症状、框架、日志片段）加上期望输出（namespace、case、fix 关键内容）。多数夹具来自 Tier 2 命中的 case；Tier 2 未命中但最终解决、随后升格的 case 同样适用。

评估时以 replay 模式运行 `/skill:diagnose`：喂入固定输入、不做交互，对照期望断言三件事：

1. 是否路由到正确的 namespace；
2. 是否匹配到正确的 case；
3. 输出的 fix 是否包含期望的关键内容。

## 怎么跑（v1 手动）

套件规模按周 append 在 `metrics/timeline.yaml`（数据，搜 "golden_suite"），机制文档见 [metrics.md](metrics.md)。本节只讲结构与机制，fixture 形态两类：①**真实 case 投影**（可运行，来自已解决 postmortem，脱敏后入仓；多数真实 fixture 是这种），②**构造示例**（`example.fixture.yaml` 等，演示格式 + 困难路径，按需保留）。**强度分层**：检索/路由/候选选择面与交互/指引面仍是"约定"；**输出契约/交互形态**这类主观成败的改动，门禁是"盲辨对照"（同上表）——同样**不进 CI**（判断性规范，硬门化＝假硬化），但要在 PR 里附对照或说明为何不需要（见 methodology 模板）。本机制在 git 门控中的强度是"约定"：CI 不执行 replay，依赖改动人自觉执行（见 [git-workflow.md](git-workflow.md) 门控映射表；replay 本身脚本化并入 CI 属 roadmap 里「fixture replay 半自动化」一项）。**但"跑过什么"的记账侧已进 CI**：观测落 `eval/scorecard.yaml`，夹具改了不重建账本即红（下节）——门控的是记录不陈旧，不是命中率达标。路由与匹配的判别力随真实 fixture 规模扩展。

1. 改动 skill 之前，按**影响面分级**（见下表）确定门禁；需要 golden 的面先跑相应子集记录基线（**基线缓存**：复用上一次干净运行的结果文件，不重复跑改前侧）；
2. 实施改动；
3. 改动后跑改后侧，与基线对照。判定标准只有一条：此前通过的条目不能变为失败；
4. 把改前与改后的报告附在变更摘要里，交 owner 审阅。

### 观测账本（`eval/scorecard.yaml`：跑过什么、上次跑到第几名）

回放结果此前只写在 fixture 的头注散文里（形如「本条回放结果：candidates=Y rank=2 path=primary」），完整报告落 gitignore 的 `eval-reports/`。于是「夹具改过而没人重跑」与「跑过了、结果就是这样」在数据上不可区分，仓库里也没有「当前命中构成」这个数。账本把观测搬进结构化字段，一条命令可读：

```
python3 scripts/eval_scorecard.py --check   # 覆盖 + 夹具哈希 + 断言冲突（红）；case 漂移只提示
python3 scripts/eval_scorecard.py --list    # 只打印聚合（命中第一 / 前三 / 未命中 / 未记录）
python3 scripts/eval_scorecard.py --build   # 重建账本（写文件）
```

**记账流程**：跑完回放 → 更新该 fixture 头注的「回放结果」行 → `--build` → 连同夹具一起提交。

**强度分层（如实标注，同 holdout 的写法）**：

- **硬门（CI `eval-scorecard`）**：①每条 fixture 必须入账本（新夹具没跑过就记 `not_recorded`，别空着）；②夹具字节哈希与账本不符 → 红——夹具就是量尺，被改过就该重跑一次；③`assertion` 要求命中（不含 `or-miss-documented`）而账本记着 miss → 红（这是夹具自述期望与观测的矛盾，放宽哪一侧都要人决定）。过期由 `--build` 一条自动命令修，不需重跑回放。
- **软信号（不红）**：目标 case 的内容哈希变了 → 进「待复核」清单。case 的合法内容变更不该阻塞无关 PR（改 `fix`/`symptoms` 是 groom 的日常动作）。
- **不判准确率**：账本记的是**上次观测到什么**，不是**现在能不能命中**。准确率仍要 agent 跑回放——本门不假装它是准确率门（不硬门化不确定的东西）。
- **已知上界（不掩盖）**：账本读的是 fixture 头注与 `expected` 块。重跑了回放却没更新头注，账本发现不了——观测与现实的差在头注那一层就丢了。这是「先更新头注、再 `--build`」这条流程存在的原因。

### 按侧覆盖：路由分侧之后，"哪一侧没有量尺"要能现算

路由从"一个分支同时记住哪一侧与什么性质"拆成两层之后（侧由工程师的事实确定、性质在侧内判），
**侧成了量尺单位**：夹具的 `expected.namespace` 第一段就是侧。此前这件事只能靠人肉数，
而读出来的结论容易被误读——`eval/holdout.py --list` 报的"有 case 却没有夹具的格子"是
(namespace × 性质) 的结果格子，读不出"训练侧 0 条"（量尺单位）。数字一律现算，别在文档里写死。

```
python3 scripts/eval_side_coverage.py                  # 按侧覆盖报告（人读）
python3 scripts/eval_side_coverage.py --check          # 侧层：某一侧量尺归零即红
python3 scripts/eval_side_coverage.py --check-cells    # 格层：任一格缺夹具也当门（默认只报）
python3 scripts/eval_side_coverage.py --check --require-side training   # 只要求点名的侧不归零
python3 scripts/eval_side_coverage.py --nature-evidence                 # 附加：哪几条夹具钉着词表
```

口径（几个数别混起来读）：**夹具覆盖的 case** = `expected.case_id` 指向的、且确实在库里的 case；
**构造示例**（`example.*`）与**指向未入库 case 的夹具**都不计入覆盖——前者是格式演示，
后者不可运行（`case_id` 不在索引里）；两者都在报告里**点名列出**，只印一个数字看不出谁被剔了。
**覆盖格子是 (侧 × 性质)、不含框架**：同一侧同一性质下的所有框架共用一格（`training/<任意框架>/interrupt`
算同一格），所以 `inference 22/124` 不是"逐框架覆盖"。`common/` 是框架无关的共享池，
不判侧，单列不计入缺口。
`--root` 指错地方时报读取错误（退出 2），**不静默报绿**——`glob` 对不存在的根返回空，
不拦就会把"根够不着"印成"每侧 0 条 case ✓"，那正是这份报告要消灭的那类误读。

**强度分层（如实标注，同 holdout 的写法）——两层判据，两个开关各管一层**：

- **侧层（`--check`，CI 跑的就是这一层）**：某一侧**一条真实夹具都不剩** → 红。
  它防的是"整侧量尺归零"。`--require-side <侧>` 把这一层限定到点名的侧。
- **格层（`--check-cells`，默认只报不拦）**：某个 (侧 × 性质) 格子有 case、没有任何真实夹具 → 红。
  **为什么默认不做成门**（这是取舍，不是遗漏）：本仓对"有 case 却没有夹具"这类缺口的既定动作是
  **如实报出**，不是拦下——补夹具需要真实来源、凭空造不出来（同 `eval/holdout.py --list`
  对空缺格子的处理）。把它做成硬门等于要求"新 case 落到尚无夹具的格子必须先补一条夹具"，
  而那时确实拿不出。需要它当门时显式加 `--check-cells`（审计轮写成 `--check --check-cells` 即可）。
- **默认只报不拦的代价要写清**：格级缺口与"某格的非最后一条夹具被删"都不会自动喊，
  只在**有人主动跑报告**时才可见。要换来那一层保护就加 `--check-cells`，
  代价是"新格子加 case 会被拦下"——两个代价必须选一个，别以为能同时不要。
- **夹具钉住词表的程度是可读的，而且差别很大（本次实测）**：`--nature-evidence` 用路由表
  自己的性质正则跑一遍夹具输入，**26 条里只有 10 条**词法上就命中期望性质（两条训练侧夹具都在
  其中），另外 16 条输入对三个性质零命中——它们靠的是流程里写明的语义兜底（`triage_semantic`）。
  （分母 26 = 全部夹具里 `expected.namespace` 带性质段的那部分，另 2 条没有性质段、不参与本栏；
  它与本节排序那一段的 28 条夹具不是同一个分母，别把两个数混着引用。报告自己会印出分母与
  不参与的夹具名，别手抄。）
  这两种夹具的保护强度不是一回事：前者改坏词表会当场报（实测把 `RuntimeError` 从 interrupt
  **两处症状组都**挪走 → `MSLLM-1655` 报出；只挪走一处不报——同一个词在多个症状组里重复出现时，
  夹具是被那几处**共同**锚定的），后者改坏词表也照样通过。
- **它测不到的东西**：夹具钉的是**某一条真实输入赖以命中的那几个正则**，不是那一侧的整份词表。
  实测把训练侧的性质词从一处挪到另一处（`build_train_valid_test_data`、`recv_forward`、
  `重复注册` 等训练专属 token，以及 `日志.*异常`）**语料级与夹具级都零检出**——这些词不是任何
  夹具输入的唯一证据，别的正则仍先接住它。所以"训练侧有夹具了"只读作"该侧链路接得通、
  且那几条 case 的性质判对了"，**不读作"训练侧词表被守住了"**。词表层仍靠人审
  （路由表里 `needs-review` 那条标法）。
- **侧判据本身不在回放里测**：回放喂的是固定输入 + 固定 `framework`，侧由"框架名对到库里目录"
  这一档确定，所以夹具断言的是"**正确侧的知识被检索到 + 侧内性质判对**"，
  不是"侧是怎么判出来的"。后者只能由 trace 的 `side` / `side_source` 回答——而这两个字段
  **当前没有任何代码在读**（只有 skill 正文要求写进 trace），所以那件观测暂时算不出来。

### 排序/筛选类改动的量尺（必须与管线同构）

管线是「按相关性**筛 ≤5** 候选 → 只加载这 5 条 → `quickly_check` 验证」。所以量尺也必须两步：
**recall@5**（期望 case 有没有进候选）与 **top3|≤5**（进去之后排第几）——两件事、两种修法。

```
python3 scripts/rank_candidates.py --eval
```

输出三行，且**同子集对照**：agent 的历史记录（来自 `eval/scorecard.yaml`）与两个机械键（score-only / 词法）。
**别用"整格内全量排序"的口径**论证收益：那个口径与管线不同构，曾据此得出"机械词法键把 top3 从 5 提到 13"，
而同构口径下同一份数据是「agent 19/19、词法 12/19、score 3/19」——机械键会替掉一个更好的判断者。
现状读数（2026-09-17，19 条同子集）：agent 19/19 进候选、机械词法 12/19、score-only 3/19；
**瓶颈在"筛"不在"排"**——候选一旦进池，两种键的 top3|≤5 分别是 5/5 与 11/12。

**为什么不去补机械筛选**（已证伪，别重复试）：逐条看过 11 条筛漏，**10 条的期望 case 行内对输入零字面量证据**
（`sig=0` 且 `tok=0`）——输入里的报错/版本/算子一个都不在该 case 里，兜底规则再怎么写也拿不到，
除非返回整格（那就等于取消筛选）。全库 **22/159（14%）** 的 case 行内无字面量证据，集中在
performance 与 precision——这两类按设计就不靠报错字面量判别。故方向在**内容侧**：审计「工程师会粘贴什么」
与「行内有什么」的交集，给能提炼出字面量的高价值 case 补行内证据。

**天花板是结构性的**（实测，别再审第三遍）：提高行内 token 上限（12/20/30）、改 token 优先级（非版本号优先）、
用全症状 token 不设上限——四组变体的 recall@5 **全部是 14/25**。超出这部分由 agent 的语义阅读承担（同子集 19/19），
这与设计原则三一致：字面量面拿不到的东西不该由它负责。可行且不批量做的只有一条：groom 逐案判断时，
若 case 证据里有可提炼的报错字面量（错误码/算子名/函数名/`file:line`），让它进 `quickly_check` 或症状首条；
**不做批量补齐**——审计显示输入侧字面量以环境模板噪声（版本号/OS/CPU/环境变量清单）为主，补进去是稀释。

### 门禁分级（2026-09，控制验证成本——改哪里测哪里，不机械全量）

| 改动面 | 例子 | 门禁 | 理由 |
|---|---|---|---|
| **检索/路由/候选选择**（影响哪些 case 会被选中） | triage 词条、阶段一/阶段二、quickly_check、两阶段加载逻辑 | **golden 子集**（挑受影响 namespace/症状的 2-5 条，非全量 23）+ 基线缓存；必要时补 ixn 检索类样本 | golden 对口的是"原来能命中的没改坏"——只有这类改动会改变候选集 |
| **交互/追问/指引面**（不改变候选选择） | 信息收集清单、双面族交叉提示、输出措辞 | **ixn 交互样本**（对口 2-3 条）或针对性探针；**不跑检索 golden** | golden 测检索、测不出交互（EV-2026-016 实证 0→100% 由 ixn 测出）；交互改动跑检索 golden = 低信号高成本 |
| **输出契约 / 交互形态**（改 agent 输出的结构与详略、追问链形态） | 输出模板、结论呈现节、追问纪律 | **盲辨对照**：同问题的新旧输出各一份（去掉来源），交不知情者判"哪份更清楚 / 更不像模板"；必要时外加一格扰动 | 这类改动的成败是**主观**的——只有对照能证明"更好"；实测（2026-09-10 diagnose 输出契约合并）：无对照时无法排除"只是换了措辞" |
| **纯文档/注释**（无行为变化） | SKILL 说明行、注释 | 不跑 replay；词表 scan + 人审 | — |

配套纪律（基线缓存已落地 B3 EV-2026-027）：
①**基线缓存**——同改动面干净状态的 fixture 结果 JSON 存 `.s2-replay/gates/<面>-baseline/`（本地）；
  下次只跑改后侧（改前 ×2 → ×1），改后写 `<面>-after/`；
②**机械对照**——`python3 scripts/gate_diff.py --base <面>-baseline --after <面>-after
  [--expected <面>.expected.yaml]`：退出 0=无回归（top3 一致或 expected case 仍在 top-3），
  非 0=回归/缺结果（逐 fixture 报告）；expected.yaml 可选映射 {fixture: expected_case}；
③**子集选择**——golden 按影响面挑 fixture，不默认全量；
④**分类判断进 EV 卡**——每张改 skill 的卡写清所属面与所选门禁（附 gate_diff 输出路径），
  审阅可复核。

## 对照集的封存（holdout：维护者独占的量尺）

上面这套门禁有一个结构性缺口：`eval/golden/` 在改动者的可写面内，而且「套件如何演化」一节
**要求 groom 跟着 case 改夹具**（case 的 fix 变了，夹具期望要同步）。于是"golden 无回归"是
一个**可控信号**——同一双手既改被测对象、也改对照标准。判据的独立性只有一条标准：
**改动者不能靠写文字（或改夹具）通过检查。**

`eval/holdout.yaml` 因此把一部分夹具**按内容哈希封存**（数据文件，同 `metrics/timeline.yaml`
的分层先例；机制解释在这里）：

```
python3 scripts/holdout.py --check     # CI：逐条核对哈希（改了即红）
python3 scripts/holdout.py --list      # 列对照集 + 覆盖面缺口
python3 scripts/holdout.py --reseal --all   # 维护者：重新封存
```

- **硬门**：封存夹具内容变了、或被删除 → CI 红。哈希就是判据，不必看 diff。
- **半硬**：改 `eval/holdout.yaml`（含 reseal）须带 `holdout-change` 标签，使"改量尺"在
  评审面上可见。**但在 CODEOWNERS / 分支保护落实前，有写权限者仍可自行打标签**——真正的
  独立性由 `CODEOWNERS.example` 的 `eval/holdout.yaml` 条目提供。在那之前，请把 holdout
  读成"标记可见"，不是"已有人把关"（原则十）。
- **软信号**：`--list` 报出"有 case 却没有夹具"的格子（本项不改 CI 结论——补夹具需要真实
  数据，不能凭空造，因此如实报缺口而非假装覆盖）。当前该报告指出 training 与 common 的
  六个格子没有任何回归保护。

**选取标准**（同「套件如何演化」）：每个有真实 case 的 (namespace × category) 格子至少一条；
频率加权；保留困难路径（多候选、排名非第一）。增删条目是维护者的动作。

**已知代价（如实标注）**：case 内容合法变更导致夹具期望需同步时，CI 会因哈希不符而红，
需要维护者 reseal 一次。这是**刻意的摩擦**——量尺被动过就该被人看见一次。

## 数据策略

| 数据 | 用途 |
|---|---|
| 真实数据（脱敏） | 套件骨干。真实日志有噪声、措辞多样、信号混杂；构造数据过于干净，会高估系统的真实表现。要点在于输入真实：日志片段与症状措辞来自真实案例，期望输出则由人工核定 |
| 构造的边缘 case | 补充覆盖真实数据没有触发的路径：优雅退化、框架歧义、precision 与 interrupt 的混淆、空库 |
| 构造示例 | 公开仓库中的格式演示（`example.fixture.yaml`） |

真实夹具不需要手工编造：`traces/`（完整交互轨迹）是主要来源，`scripts/replay_trace.py --emit-fixtures` 从 **status=resolved 且 feedback.outcome=resolved** 的 trace 自动派生 fixture 候选（输入=user 事件原文，期望=实际命中 case），人确认后入 `eval/golden/`。断言分两层：只有反馈闭环确认的 trace 能作正确性基准（强断言），未确认的只能做弱断言（行为差异回归）。postmortem 是次级来源（含未走 diagnose 的调查）。脱敏复用 to-postmortem 的同一步骤；无法充分脱敏的条目移入团队私有仓库。

### 记录的时效性：回放结果会**腐烂**，不等于当前状态

fixture 头部的 `candidates=Y/N`、`eval/s2` 的 `tier2_hit` 记的是**那一次回放当时**的结果。而回放本身会改变知识库：一条 miss 被诊断清楚后沉淀成 case，**同一个 issue 下次就变成 hit**。实测（2026-09）：`.s2-replay` 里记为 miss 的样本，其 case 在该次回放当天或之后入库，重跑时 6/6 全部命中；`VLLM-ASC-13973` 的 fixture 记 `path=semantic-obs`（未命中），其 case 入库后四个盲测格子全部命中。

因此：

- 要判"这条现在会不会命中"，**必须当场重跑**（或直接读 `knowledge/_index/` 分片核对），**不能引用历史记录**；
- 任何以「候选未命中」为前提的评测或实验（流程加载、深度排查、Tier 3 兜底、S2 miss 率）**不能用旧记录选样本**——改用**尚无对应 case 的新 issue**（判据：`knowledge/` 下无该 id 文件）；
- 反过来，**miss 率下降不等于检索变好**：知识库变大也会压低 miss 率。单看趋势不可下结论，要同时看库容量与该期新增 case 数。

## 套件如何演化

套件随知识库一起增长，由 groom 在例行流程中维护。维护动作分两类，节奏不同。

新增由覆盖驱动，所以会饱和，不是每条新 case 都配夹具。选择标准：

- 覆盖优先：`(namespace × category × platform)` 矩阵中每个有真实 case 的格子至少配一个夹具，新出现的格子必须补；
- 频率加权：高频命中的 case 优先，它们是常见路径，回归代价最大；
- 边缘路径：刻意保留少量困难夹具（框架歧义、多候选、precision 与 interrupt 混淆），即使罕见；
- miss 恢复：此前查不到、刚升格进知识库的 case 立即补夹具，验证现在能抓住以前漏掉的。

当覆盖报告全绿（每个有 case 的格子都有夹具、困难路径都已覆盖），新增趋于停止，因为此后新 case 多半是已覆盖模式的变体。只有领域发生真实变化（新框架、新问题类型、新平台）才会重启新增。

同步与退休不会停止：只要知识库在动，现有夹具就要跟着对应的 case 走：

- case 的 fix 变了，夹具的期望同步更新，否则测的是过期期望，产生假失败；
- case 合并，夹具的 `case_id` 跟着改；
- case 软退休，夹具标记 skip 或移入 `eval/_archive/`。

这部分由 groom 自动检测：引用的 case 变了就跟着改，保持轻量。

规模有上限。套件上限约 30-50 条，与知识库每命名空间 30 条的上限同理：回归套件的价值在密度而不在数量。饱和后不是冻结，而是在上限内缓慢换血，低价值出、高价值进。groom 每轮都跑覆盖检查（成本低，且能检测领域变化），饱和后通常静默，只在出现新的覆盖缺口时提示。

判断是否建够的标准是覆盖报告连续数轮全绿。此后 groom 只在领域出现新覆盖缺口时提议新增，团队的维护投入大幅下降，剩余工作是自动化的同步。

## 能力边界

- LLM 的非确定性：同一夹具跑两次可能得到不同路由。对策是多次运行取多数，或断言 top-3 命中而非必须第一；
- 套件检验的是固定输入下的路由、匹配与 fix 内容，不能检验交互质量（该问的问题有没有问出来），也不能检验新 case 的处理，这两部分依赖人工审阅；
- 小样本的限制：当前规模只能捕捉回归和大的改动，不足以度量小幅调整带来的改进。

## 与 roadmap 的衔接

- fixture replay 半自动化：脚本编排 replay 与期望比对，产出改前/改后报告；
- fixture 自动生成：groom 从 resolved+feedback 确认的 trace 派生真实夹具（`replay_trace.py --emit-fixtures` 产出候选，人确认入仓）；
- eval 覆盖报告：覆盖矩阵进入 groom 例行产出。
