# skill 改动评估（golden-case 回归套件）

> 改 KB 有指标反馈（confidence/命中率/误诊率）；改 skill 本身（流程措辞、步骤、输出格式）没有。
> 这套件是给 skill 改动补一个"改前/改后别回归"的检查——别把原来能查的查坏了。

## 机制

每条已解决的 Tier-2 命中 case = 一个测试夹具（见 `eval/golden/`）。改 skill 前/后各跑一遍 `/diagnose`（replay 模式：喂固定 input、不交互），对照 `expected`：

- 路由到对不对的 namespace？
- 匹配到对不对的 case？
- fix 包含期望值吗？

## 数据策略（关键）

| 用什么 | 为什么 |
|---|---|
| **骨干：真实数据（脱敏）** | 保真度——真实日志有噪声、措辞各异、信号混杂；构造数据太干净会 false confidence。**有意义的是输入真实**（真实日志片段/症状措辞），不是期望输出真实 |
| **补充：构造的边缘 case** | 覆盖真实数据没踩到的路径：优雅退化触发、框架歧义、precision vs interrupt 混淆、空库 |
| **公开仓：只构造** | 真实客户数据不能上公开仓（§部署公私分离）。公开仓的 eval/ 是格式示例，不是真正的回归防线 |

**真实 fixture 不用手工造**：它是已解决 postmortem 的投影（症状+日志片段+root cause+fix 都在 postmortem 里）。groom 半自动生成（v1.5）；脱敏复用 redact()。

## 怎么跑（v1 手动）

1. 改 skill **前**，跑一遍 `eval/golden/*.yaml`（喂 input 给 /diagnose），记录基线——哪些 pass
2. 改 skill
3. 改**后**再跑一遍，对照——**不能让原来 pass 的变 fail**（回归）
4. 把改前/改后报告附在变更摘要里交 owner 审

## 套件如何演化

套件不是建一次就完事，也不是每次都大量动——它跟着 KB 长，由 groom 在同一流程里维护。**关键是区分两类操作，动态不同**。

### 新增（additions）会饱和

新增是**覆盖驱动**，不是“每条新 case 都加”。选择标准：
- **覆盖优先**：套件要覆盖 `(namespace × category × platform)` 矩阵里有真实 case 的格子。新格子必须补。
- **频率加权**：高频命中的 case 优先（常见路径，回归代价大）。
- **边缘 case**：故意留几条难的（框架歧义、多候选、precision vs interrupt），即使罕见。
- **miss 恢复**：之前查不到、现在升格进 KB 的 case 立刻 fixture（测“现在能抓住以前漏的”）。

**饱和点**：覆盖报告全绿（每个有 case 的格子 ≥1 fixture + 硬路径都覆盖）→ 之后新增罕见，因为新 case 多是已覆盖模式的变体。只有**领域真实变化**（新框架/问题类型/平台）才重启新增。

### 同步/退休（sync/retire）永不停

即使不再新增，现有 fixture 必须跟着它的 case 走：
- case 的 fix 改了 → fixture 的 `expected` 更新（否则测过期期望 → 假失败）
- case 合并 → fixture `case_id` 更新
- case 软退休 → fixture 标 skip / 移 `eval/_archive/`

这部分轻量、自动化（groom 检测引用的 case 变了就跟着改），只要 KB 在动就得做。

### groom 的演化职责（v1.5 自动，v1 人工照标准做）

- **提议新增**：高 confidence 新 case 或覆盖矩阵空格子 → 提议从其 postmortem 衍生 fixture（人确认，像升格 PR）
- **同步**：case 变了 → 对应 fixture 跟着改
- **退休**：case 软退休 → fixture 退休
- **覆盖报告**：每次报告套件覆盖——“inference/sglang 0 条（缺口）”、“precision 类只 1 条（偏弱）”。**这是套件自身的健康指标**。

### 定界 + 慢换血

- **有上限**（如 30-50 条），超了淘汰低价值——和 KB 的 30/namespace 上限同精神。
- 饱和后不是冻结：cap 内慢换血（低价值出、高价值进）。
- groom 每次都跑覆盖检查（便宜，检测领域变化），但饱和后**多半静默**——像烟雾报警器，只在出现新覆盖缺口时响。

### 何时算“建够了”

覆盖报告连续 N 轮全绿 = 套件完整。之后 groom 的“提议新增”只在领域出现新覆盖时才触发。团队精力骤降：新增罕见，剩下的是自动化的同步。

### 诚实边界

- **饱和是暂时的**——Ascend 演进（新芯片/框架/FP8 等），领域一变覆盖就出现缺口，新增会再启动。覆盖检查就是为这个存在。
- **小 N 团队的覆盖缺口长期存在**——某些格子真实 case 少，fixture 也少，那条路径回归保护弱。靠覆盖报告暴露，接受。

## 注意

- **LLM 非确定性**：同一 fixture 跑两次可能路由不同。跑 N 次取多数，或断言"top-3 命中"而非"必须第一"。
- **套件测的是固定输入下的路由+匹配+fix**，测不了交互质量（有没有问对问题）、测不了新 case 处理——那部分人工审。
- **小 N**：只能抓回归和大改动，抓不了微调的提升。

## v1.5 路线

- groom 从已解决 postmortem 自动生成 `eval/golden/` 真实 fixture（脱敏）
- `/skill-eval` 自动编排 replay + LLM-judge 比对 expected，产出改前/改后报告
