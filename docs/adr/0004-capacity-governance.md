# 容量治理：category 子层与参数化 cap（替代拍脑袋的 30）

## Context

- 批量导入（评估 0001）暴露增长模式与容量模型的失配：groom 的容量模型假设渐进增长（每周几条，80% 预警线有缓冲），但 issue 拉取是**批式持续知识源**——首批 19 条直达 63%，下一批必然触线。拆分从"是否"变成"何时"，而答案是"几乎立即"
- 现有 cap（30/namespace）是**拍脑袋常数**。理论 §7 明示常数是参数估计而非推导链内；roadmap 待定池"参数治理"条目正是为这类常数准备的
- 拆轴已有预定：roadmap A2 首选 category（interrupt/precision/performance）——本 ADR 只是把落地时机从"撞线后"提前到"增长模式证明必然撞线"

## Decision

**一、目录结构按 (framework × category) 分层（方案 B：目录分层、索引统一）**

```
knowledge/inference/vllm-ascend/
├── interrupt/     # 本批 13 条
├── precision/     # 3 条
├── performance/   # 2 条
└── other/         # 4 条（other 是评估 0001 发现的原生类别，保留——见注释）
```

理由（理论推导）：
1. **检索语义两轴正交**（triage 输出 category + namespace）——目录反映检索结构（原则二：结构对齐语义）
2. **信道成本不变**：`_index.yaml` 单文件带 category 分组，阶段一加载量相同；category 过滤在阶段一自然发生
3. **cap 语义精确化**：30 cap 的本意是"单次可暴力过滤的候选集规模"——(framework, category) 格子才是 triage 定 category 后实际被扫的单元。现实现 cap 在框架层，粒度比理论要求粗
4. **triage-tree 不改**：search_namespaces 仍路由到框架层，category 过滤交给 quickly_check 阶段（两轴正交设计的既有行为）
5. A2 闸门针对"要不要引入新轴"；category 轴已被预定，本 ADR 是落地时机决策，非破例先例（决策留痕，原则十一）

注：other 是评估 0001 发现的"错误签名→版本支持差异"型知识类别，超出原三分类 schema——本 ADR 保留它作为格子，同时把"是否正式入 schema"登记为待定项（观察使用后决定）。

**二、cap 参数化：常数 → 三层模型**

| 层 | 值 | 语义 | 触发动作 |
|---|---|---|---|
| soft_cap | 每格子 30 | 到达即触发**拆分评估**（非强制拆） | groom 容量表标黄 + 健康指标检查 |
| 健康指标 | 见下 | 拆分评估的判据 | 任一恶化 → 评估报告 + 拆分建议 |
| hard_cap | 每格子 60（≈ 信道物理上限，B_ctx 内可加载 60×70≈4.2K tok） | 到达强制拆分（不管健康指标） | 索引加载成本约束的硬边界 |

**健康指标（三个可观测代理，替代"数到 30"）**：

| 指标 | 定义 | 恶化阈值（初始估计，参数治理复核） | 对应约束 |
|---|---|---|---|
| 候选溢出率 | 阶段一后候选 >5 的诊断/回放占比 | >20% | 区分力（候选 ≤5 是阶段二硬约束） |
| 重复率 | groom 去重检出的同根因对 / 格子 case 数 | 连续两轮上升 | 信噪比（重复=噪声） |
| 维护时长 | groom 周审该格子耗时 | >30 分钟/周 | 注意力预算 B_attn |

**三、实现变更**

- `build_index.py`：按 (ns, category) 分组输出；每格计数进入索引头注释；支持 soft/hard cap 配置（YAML 或常量，初值 30/60）
- groom 容量表：按格子报告（计数/soft_cap + 健康指标），替代按 namespace 报告
- roadmap A2 改写：触发条件从"超 30"改为"超 soft_cap 且健康指标恶化 / 超 hard_cap 强制"
- fixture 断言：`expected.namespace` 更新为含 category 的路径

## Rejected / Deferred

- **方案 A（目录深度 +2 全量迁移）**：代价高（triage-tree 也改）且索引不省——目录分层已满足语义，无需双重改动
- **立即把 other 并入 interrupt**：其他格子的 case 语义上是"版本/模型兼容知识"而非中断——并入会污染 category 判别（评估 0001 已证明其可检索性）。保留，观察
- **cap 全动态无上限**：信道物理约束是硬性的（hard_cap），不可为"可调"牺牲。动态调节发生在 soft_cap 与健康指标层，hard_cap 恒定

## 索引字段拆分（本 ADR 的延续，PR #8）

`_index.yaml` 条目只保留 `confidence.score`（阶段一排序所需）；hits/misdiagnoses 是学习环动态字段（Beta 后验），留在 case 本体，由 groom 置信度重算读取，不入检索视图。理由：动态字段进静态索引 → 每次反馈全量重建 + diff 噪音 + `--check` 把"索引过期"与"置信度未同步"混淆。索引是生成物，只读，不手改。

## 参数治理（本 ADR 的参数归属）

soft_cap=30、健康指标阈值、hard_cap=60 均为初始估计，服从 roadmap"参数治理"条目：metrics 实测（候选溢出率来自回放 harness/trace、维护时长来自 groom 报告）后按理论 §4.4 复核。首个复核点：评估 0001 的回放数据即可给出候选溢出率基线（当前 21 例溢出 0 次——格子健康，支持 30 起步）。

## 读侧形态与上限口径（本 ADR 的延续，2026-09-29）

**这条延续推翻的是本文自己那笔算术，不是决策本身。** 上表把 hard_cap 定成"每格子 60 条（≈ B_ctx 内可加载 60×70≈4.2K tok）"——那个 **70 token/条是估的**；同库实测（`scripts/index_read_cost.py`，现算）：旧 YAML 分片 **252 token/条**、一行一条的读侧视图 **177 token/条**。估小了 3.6 倍，后果是 `inference/vllm-ascend × interrupt` 93 条看起来"只是贴着线"，实际 **23449 token**——比诊断会话每次都要读的常驻指令面（SKILL + 仓库指令 + 路由表 ≈ 21K）还大。**被约束的量是 token（B_ctx），条数只是代理量**。

**三项决定**（依据与实验见 `proposals/ideas/EV-2026-160.yaml`，落地见 `EV-2026-161`）：

1. **上限按"阶段一实读 token"算，不按条数**：软线 8000 / 硬线 20000（每格，现算，不写进生成物）。硬线 20000 是**推导**来的：不许超过诊断会话的常驻指令面（SKILL 11.4K + 仓库指令 5.7K + 路由表 4.1K ≈ 21K）——阶段一不该比"每次都要读的指令"更贵；软线 8000 ≈ 该面的 38%（到这里就问「还能不能再省」；取整值，不追求与 21K 成整数比）。该格 23449 → **16442 tok**：硬线内、超软线，属"值得再省"的评估档（下一杠杆是平台轴切分，实测桶成本见 EV-2026-160）。
2. **读侧视图从 YAML 改成一行一条**（`knowledge/_index/<ns>__<category>.list`）：同信息，去缩进/引号/字段名/嵌套的结构开销（该格 −30%，全库类视图 43078 → 31564）。总表 `_index.yaml` 保持 YAML——它是机器面（面板、排序器、门按字段读它）。**ns 兜底视图（category 未定才读）更贵且不在同一条硬线里**（vllm-ascend 124 条 21821 tok），要治得另立项。
3. **不做结构拆分，也不砍行内容**：平台轴**可行但当前不必要**（17 条夹具里"输入提到的平台"与"case 声明平台"冲突 0 条；按平台切的读集 A5+未声明 38 行 ≈6.5K、310P 40 行 ≈7.0K、A3 54 行 ≈9.6K、A2 59 行 ≈10.3K，均 ≤ 硬线）——留作下一杠杆；按标签派生的子族覆盖只有 73/93 且需要读侧分类器；砍内容（标题截到 60 字 / 去掉症状首条）在 27 次独立对照实验里与完整行**不可区分**（top-5 命中 6/9、6/9、5/9），决定成败的是输入里有没有报错文本，不是行的长短。

**4. 条数退出政策面**（2026-09-29 统一）：两个条数阈值（30/60）从 `metrics/gates.yaml`、`build_index.py`、`index_counts.py` 里**删除**——`gates.yaml` 只留两条 token 线，`index_counts.py` 只报计数。条数仍在容量台账里显示（用来看"这一格在长"），但**不触发任何动作**。理由：同一个量（这一格有多贵）出现两处定义时，必有一处先腐烂——这次腐烂的是"70 token/条"。

**对本文的处理**：Context / Decision 两节保留原样（决策记录不追溯改写）；上表 `60×70≈4.2K`、`soft_cap`/`hard_cap` 两个条数阈值、以及"cap 语义 = 条数"三处以本节为准。判据身份见 `metrics/gates.yaml` 的 `cell_read_soft_tok` / `cell_read_hard_tok`；展示口径见 `docs/guide/metrics.md` 的判据表。

## 读入账与兜底视图接线（本 ADR 的延续，2026-09-29）

**这条延续推翻的是上面第 2 项里对兜底视图的处置**（原文："ns 兜底视图……更贵且不在同一条硬线里，要治得另立项"）。

把"要治得另立项"写成一句注释，实际效果是这个处置**没有发生过**：兜底视图是全系统最贵的一次读（`inference/vllm-ascend` 124 条 **24270 tok**，超硬线 20000），而它不在任何判据里——`index_read_cost.py --json` 退 0、体检报"所有格子均未触发"。政策洞与"可接受的取舍"在数据上同形，区别只在有没有人记得它。

**四项决定**（落地见 `EV-2026-163`）：

1. **兜底视图接上同一条线**，数值沿用同一套推导（硬线 = 常驻指令面量级、软线 = 其 38%），单列 dimension `capacity_fallback_read_tok`：改动只在把它接到这条读取路径上，好让"哪条路径越线"看得出来。动作：先看行宽/字段，再看"窄列视图（只留 id/标题/标签）→ 读判出来那一类的索引"两步法，最后才是按平台轴切分（不预拆目录）。
2. **`index_read_cost.py` 报"一次诊断的读入账"**，四个分项：类视图 / 兜底视图（判线）+ 先验层 / 阶段二候选全文（只量不判）。分项列出来是为了回答"该治哪一条"，报一个总数回答不了。
3. **先验层不设 token 线**：它是检索式读取（一次 grep + ≤5 行上限），成本不随库大小线性涨——"读太多"不是它的退化形态，"翻不到"才是。它的量化量是**检索残量**（平台 + 类别两刀切完剩多少行，现算），先有数（原则八），攒到期数够了再定线。给它配一条硬线会把"库该长"和"索引该瘦"两件事混起来，而前者的价值来源就是它的体量。
4. **阶段二候选全文不设线**：上限是"读几条候选"（≤5，按置信度降序、够了就停），压低字数是压低证据量。之前它一笔账都没有——最贵 5 条合计 17999 tok，与最贵的索引格子同量级。

**对本文的处理**：本节只改"兜底视图怎么治"，不改第 1、3、4 项（token 口径、不做结构拆分、条数退出政策面）。判据身份见 `metrics/gates.yaml`；展示口径见 `docs/guide/metrics.md` 的「一次诊断的读入账」节。
