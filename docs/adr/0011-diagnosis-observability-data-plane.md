# 诊断观测：条目使用增量落独立记录文件，结局分两条通道

## 状态

已接受（2026-10-17 落地）。

## 背景

本仓记下一次诊断的过程没有问题，但回答不了三个问题：这一次诊断值不值、这条知识还有没有用、流程哪里浪费时间。下面这些事实都能在本机重新跑出来。

| 事实 | 出处 |
|---|---|
| 三期 live 快照的反馈捕获都是 0，命中率、误诊率、校准只能标不可解读 | `metrics/timeline.yaml` 的三条 live 期 |
| 面板的约三十个指标标签只有三个消费点 | `scripts/metrics_health.py`、`scripts/evolution_health.py`、`skills/self-evolve/SKILL.md` 的漂移判读 |
| 十个指标有产出、在字段白名单里，8 期期文件一个都没写过 | `scripts/verify_metrics.py:40-60` 的白名单 29 项与 `metrics/timeline.d/` 求差得到：漏检类别、漏检会话、先验三态、先验消费点、停止原因分布、停止原因未记录、同批并发标记、候选全集事件、字段违规明细、字段违规总数 |
| 归因比恒为 0 | 读端 `scripts/trace_metrics.py:240-242` 只读 `verdict`；规范要求写 `verdict`（`skills/diagnose/references/diagnosis-procedure.md:331`），而实测 7 条 attribution 事件里 4 条写的是 `attribution_kind`、3 条两个键都没有；`scripts/component_tally.py:54-58` 记的是修法（两套都收），不是读端 |
|「命中」有两处口径 | 案例本体的 `confidence.hits`（现场确认解决）与期文件的 `tier2_hit`（由 `scripts/trace_metrics.py:338` 的现算值派生），两个数含义不同却都能叫「命中」 |
| 条目级观测只有先验侧有 | 期文件的 `metrics.reference_detail`；`scripts/settle_trace_feedback.py:18` 写着「数据都在 traces 里，但没有任何脚本产出它」 |
| 没有一处统计一次诊断内部的无效步骤 | 轨迹里预留了 `stop_reason`、`parallel_group`、`considered_candidates`，打分代码未落地 |
| 没有任何一处把 issue 或 PR 的状态回写成诊断结局 | 有 4 处 `gh` 调用会读 `state`（`scripts/auto_fetch.py:56`、`scripts/fetch_issues.py:50`、`scripts/s2_calibration.py:274`、`scripts/ev_proposal.py:334`），但它们分别服务于拉取、建池与改进项指针，都不写诊断结局 |
| 案例没有一条独立的外部确认 | 带 `validation_record` 的案例里 `consistent` 全为 0 |
| 案例的 `confidence` 有四种形态，迁移没有路径 | 四个键 87 条 / 只有 `hits` 与 `misdiagnoses` 49 条 / 三个键 31 条 / 带 `self_resolved` 1 条；一部分条目没有 `score` |

形态上有四条约束。期文件的 `metrics` 段受 `scripts/verify_metrics.py:40-60` 的白名单约束。面板的期文件解析器是手写的，它会把 `metrics` 上下文里缩进不超过四层的行折进 `metrics`。生成物里不写数字这条约束只针对生成物，仓根的 `ingest-state.json` 含数字且已上仓。读数按部署分家，见 `docs/guide/git-workflow.md:64-65`。

设计与规格在 `docs/mechanism/diagnosis-observability.md`，本文承载取舍。

## 决定

我们决定把条目使用增量落成独立的一族追加型文件 `metrics/entry-activity.d/<周>.yaml`：一周一个文件，每次知识整理追加若干行，一行一条自包含记录（`merge=union` 是行级合并，嵌套结构会拼出非法 YAML，所以记录必须一行一条），并配 `merge=union`；读侧由生成物 `metrics/entry-activity/<部署>.yaml` 汇总，一个部署一份、互不覆盖，不跨部署合并；观测计数（被选中、被加载、检索三态、解决与误诊）只落这份记录，`last_hit` 不单独存、由记录推出；案例文件里不再写计数，也不再写排序分数，分数由记录计数与冷启动先验算出来、只落在索引生成物里；条目既没有记录也没有搬运行时，分数退回它的冷启动先验值，并在索引头注与体检里写明这一次用的是先验值；迁移期的历史累计值写成 `kind: baseline` 的行，只计入累计、不计入本期增量；人为覆盖走案例的可选字段 `score_override`；结局真值分外部自动对照与现场人工确认两条通道分别计；无效探索只落地可离线重算的那一半。

## 被否决的替代方案

- 把条目使用增量直接写进案例文件、不建记录。好处是不新增文件族。代价是每一次结算都改一次知识文件，且「被选中」与「现场确认解决」两种含义混进同一个 `confidence` 块；这与本设计把观测与知识本体分开的目标相反。
- 把排序分数继续留在案例文件里。好处是读分数不必先读记录。代价是知识条目因观测而改，一周里被改几次取决于有多少条有结算，且分数与记录里的计数是同一个事实的两处表达；观测与知识本体的边界也就守不住。
- 把排序分数放进一个按 id 的独立文件。好处是案例不动、读侧也集中。代价是这份文件既不是源也不是生成物：它要么由脚本写而成为第二份派生数据（与索引里的副本重复），要么由人手写而无法回溯；而索引构建本来就要重建一次，顺手算出来不需要第三份文件。
- 把使用记录放进期文件的 `metrics` 段。好处是不新增文件族。代价是同一周的第二次运行要重写同一批 id 的行，而「重写已写下的行」正是冲突的来源；面板的期文件解析器是手写的，会把新键折进指标行；字段还要进 `verify_metrics.py` 的白名单。
- 把计数继续留在案例文件里，只把使用记录当副本。好处是读分数不必先读使用记录。代价是同一个量在两处，且每次结算都改一次知识文件；两处迟早对不上，对不上时没有判据说该信哪一处。
- 保留 groom 里由 agent 判断重算分数（现状）。好处是不用写代码。代价是「按时间衰减」没有公式也没有脚本，同一份输入两次算出不同的分数没有判据；而分数是候选排序的输入，属于必须可核对的口径。
- 按条目一个文件。好处是不同条目互不相干。代价是同一 id 的历史跨期写进同一文件，冲突时没有确定性重建命令，取一边等于丢数。本仓的同形先例是 `postmortems/2026-Q3/`，它的文件一次写定、不再追加。
- 做成仓根状态文件。好处是名字上不再属于指标。代价是它与期文件重复定义同一个量，两个落点必有一处先漂移。
- 每次诊断的指标单独开一个 PR。好处是证据与结论同行。代价是轨迹含客户现场信息，进 git 要先逐单脱敏；PR 量从每周一次变成每单一次，而每周一次是当前能维持的节律。
- 只保留周期节律。好处是冲突处理与门控节律不变。代价是条目级观测进不了仓库，「被检索却从没解决」到不了退休决定。
- 只保留事件驱动。好处是因果链最短。代价是同一期的数字被切成碎片，趋势线要重拼，分母复核没有落点。
- 把语义那一半与机械化一半合成一个「无效探索次数」。好处是面板上只有一个数。代价是两者强度与可比性不同：机械一半可由历史树离线重算，语义一半只能在线判断。合成后这个数无法解读，也不能当验收依据。
- 让 agent 自动判定现场结局。好处是回报成本归零。代价是外部对照只能判断内容对不对，判断不了现场是否解决，现场特异性只有现场能给。
- 在面板里直接读期文件自行求和。好处是不新增生成物。代价是取数出现两处实现，而面板的解析器是手写的，已实测会把新键折进指标行。
- 把检索的查询串、topK 与分数写进轨迹。好处是检索质量在线可算。代价是 live 轨迹没有「预期命中」这个真值，记下来的是候选集而不是对错；带真值的量尺已经在离线侧（回放夹具与排序对照）。
- 把 token 与耗时写进轨迹事件。好处是轨迹自足。代价是复制而非关联：真实账单在 harness 会话日志里，轨迹里那份是 agent 自报值，两边不一致时没有判据。正确做法是按 `session_id` 关联。
- 给案例加状态字段表达生命周期。好处是与先验层对称。代价是同一件事在案例层有两个表达，目录位置与字段值不一致时没有判据；现有机制是软退休加归档可复活。
- 把诊断标签扩成多个人工枚举。好处是语义完整。代价是单次回报的选择成本上升，而反馈捕获在三期快照里都是 0；能从已有数据派生的状态不该再问人一次。
- 把验证回放产物 `.s2-replay/` 收进主检出锚定表。好处是跨 worktree 可见。代价是写入侧分散在四个脚本的散文路径里，只锚读侧会得到「写进 worktree、读主检出、报 0 条结算」，比现在各检出自洽更坏。

## 后果

- 好，因为条目级观测与知识变更同行：一次整理就能把本机的使用记录带进仓库，不必再单独搬一轮。
- 好，因为观测不改知识条目：一次结算只写使用记录，案例文件一周最多被 groom 改一次，且只改分数变了的条目。
- 好，因为被选中与现场确认解决分开记，选中不再污染命中率。
- 好，因为开源类问题的结局可以自动查证并闭环，现场类问题保留人工通道，两条通道分别计，不合成一条准确率。
- 好，因为无效探索只落地可离线重算的一半，另一半标为在线判断，不是一个无法解读的复合数。
- 好，因为指标的存在条件写成了 3.6 的五个问题，没有决定读的指标会被删掉，而不是继续空转。
- 坏，因为要改案例 schema 与知识整理流程：`confidence` 块整体迁出案例，结算脚本与算分都要跟着改，算分还要从 agent 判断落成脚本，并新增一个可选的人工覆盖字段。
- 坏，因为计数与分数分居三处，读的人要认这个分工：使用记录是原始观测，分数是它的派生值、只存在索引生成物里，人为覆盖是例外。
- 坏，因为索引构建多了一条对使用记录的依赖；记录缺失或过期时分数退化为冷启动先验，要靠头注与体检把这一次的退化说出来。
- 坏，因为多了一族文件：源文件、生成物、校验脚本、`.gitattributes` 的 union 行，以及 `docs/guide/metrics.md` 与路径归属表的同步。
- 坏，因为使用记录按部署分家，跨机器的排行在第二台部署有数据之前看不到。
- 坏，因为整体读数仍按周落期，一天跑多次整理时只有周界那一次产出期文件；想按天看趋势要另说。
- 落地时的两处澄清（设计稿未写明，实现时定死）：**一次运行一个 `run`**——汇总与结算各印自己的时间戳，同一个 case 在一轮整理里因此可能有两行、字段互补（聚合按 id 求和），行的唯一键 `(run, kind, id)` 由校验脚本判红；**「记录过期」不改变索引里的分数**——过期由体检器按当天日期报出，索引只按「这个条目有没有记录」决定退回先验。理由：索引是提交进 git 的生成物、CI 逐字节比，按当天衰减会让它在没有任何知识变更时变红。
- 落地时的第三处澄清：**算分读仓里全部部署的记录生成物**（按 id 求和），面板排行仍按部署分家。索引是全仓共享的生成物、会在 CI 重建并与提交的那份逐字节比，按本机部署取值会让同一份索引在不同检出算出不同分数。
- 坏，因为要迁移：案例的 `confidence` 现有四种形态，搬运要跨三个 PR，中间有共存期；迁移期间分数先仍从案例读，切换到记录之后分数由记录计数（含搬运行带来的历史累计）与冷启动先验算出。
- 坏，因为记录按写入机器的本地 ISO 周归周，跨时区的两台部署在同一自然日可能落进不同周文件；汇总按部署分组，因此跨部署的排行仍然拼不出来。
- 坏，因为分步成本要接 harness 会话日志，两个数据源按 `session_id` 关联；关联失败时该会话的成本缺席，不补估值。
- 坏，因为外部自动对照只覆盖有上游锚点的案例，客户侧现网问题仍然等人工回报，学习环在那些问题上依旧没有分母。
- 坏，因为无效探索的打分在闸门满足前不写，面板上这一项长期显示缺打分代码。
