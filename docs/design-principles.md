# 设计原则

本文是 ascend-sleuth 的规范性基础。十一条原则从领域约束推导而来，误诊的代价、agent 的能力边界、人的注意力稀缺和知识腐化的必然性，不是风格偏好。原则的生成理论与公理推导见 [design-theory.md](design-theory.md)：四条公理（代价不对称、资源有界、世界非平稳和概率基座）经贝叶斯决策、信道与多样性约束和演化假设检验，推导出本文全部原则。它们约束本项目的全部设计、实现、修复和演进：roadmap 事项的立项理由、skill 的每次修改和 ADR 的每个决策，都应当能追溯到其中一条或几条，或者明确说明为什么需要挑战它。

原则不常改。修改需走 ADR 级别的论证，且原则上应先经过真实使用的检验。未经真实使用检验的规则，不足以成为规则。原则之间冲突时，安全类（一、六、七）优先于效率类（九），结构类（二、三、四）不为单项功能让步。

---

## 一、验证先于交付

**检索只负责提名，验证决定放行；交付形态是建议而非执行，交付方式由严重度决定。**

推导：诊断域的第一约束是代价不对称。一次误诊的成本（错误的修复动作、服务中断和数据损失）远高于多问一轮问题。任何把"匹配"当作"确诊"的设计，最终都会在这个不对称上翻车。

依据：理论 §2 推论三（非对称损失下验证的价值）与推论一（无界损失 → halt）。

落地：修复以建议形态交付，由工程师人工应用到客户环境。agent 不访问客户环境、不执行生产变更，交付的终点是建议而非动作。fix 只在 diagnosis checks 对照客户环境的真实信息验证通过后输出；severity 是交付闸门，data-loss-risk 只输出停机保现场指令，不给修复；连续两个 case 未解决即转人工，防止误诊级联。任何"匹配度高就直接给答案"的捷径都违反本条。

## 二、不变量写进结构

**凡能由文件结构、脚本或 CI 承载的规则，不交给执行者的自觉。**

推导：prompt 纪律是概率性的。同一份 SKILL.md，不同的 session、不同的上下文长度，遵守程度都会漂移。文件、脚本、CI 的失败则是可观测的：正则失效被 fallback 兜住、索引过期被 `--check` 挡住、脚本失败非零退出。架构利用的正是这个失败模式的不对称：关键规则搬进可观测的一侧，可靠性不再依赖概率组件的自觉。

依据：理论 §5（失败模式不对称：LLM 失败静默，确定性组件失败可观测、可归因）。

落地：阶段一加载固定为读生成索引（`_index.yaml`），不依赖"只读部分字段"的自觉；反馈追踪落在状态文件的 `feedback_pending` 标记上，任何 diagnose 或 resume 启动都会扫描它，不依赖记性；索引新鲜度由 `build_index.py --check` 硬校验并接入 CI。无法硬化的规则（脱敏彻底性、severity 标注正确性）必须显式标注强度为"约定"，不冒充已被强制。把约定当硬门宣传，等于制造虚假的安全感。

## 三、Agent 承担语义，底座保持词法

**语义层的模糊只有模型能消化，因此模型负责归一表述、不充当知识存储；知识底座保持词法形态，可 diff、可审和可回滚。**

推导：工程师说"训练跑着跑着就慢了"，这层模糊性需要语义能力归一成 `throughput drop` 这样的可检索信号。agent 恰好有这个能力，且坐在检索之前。反过来，知识库一旦换成向量等语义形态，就失去了 git 的审计链：变更不可 diff、误改不可发现、回滚不可执行。让两种能力各居其位，比让任何一方包办更稳。模糊由此分两层分工：含义的模糊归模型，形态的模糊（日志格式漂移）归 primary/fallback 双正则这类确定性机制。quickly_check 的双 regex 设计正是本条的实例。

依据：理论 §5（能力各居其位）与 §3（信噪比守恒）。

落地：模糊到精确的归一化是 diagnose 流程的显式步骤；知识以 YAML 提交进 git；检索信号使用错误签名、错误码和数值阈值等词法形态。不引入向量检索（论证与重评条件见 [ADR-0002](adr/0002-retrieval-no-rag-lightweight-index.md)）是本条的直接结论，不是独立的战术选择。

## 四、知识库有界

**增长是治理的产出，不是积累的默认；方法论与知识资产分目录而治。**

推导：无上限的知识库必然退化。重复条目稀释检索质量，过期条目污染候选集，最终重演"文档很多、没人能找到"的旧病。上限让"暴力检索永远够用"成为长期成立的架构前提：每命名空间 30 条，全量索引可以单次加载，就不必为未来的规模过早购置检索基础设施。

依据：理论 §3（信噪比随库大小单调不增）与 A2（资源有界）。

落地：groom 的去重、合并、软退休和复活维持有界性；容量达 80% 预告拆分而非事后补救；`skills/`、`scripts/` 和 `docs/` 是可公开、可 fork 的方法论，`knowledge/`、`postmortems/` 是团队资产，入库前脱敏。为"多多益善"放宽上限、或无治理的批量导入，都违反本条。

## 五、建议与决定分离

**自动化产出建议与证据；采纳、调整和驳回永远是人。**

推导：自动化的正确用法是压缩人的工作量，不是接管人的判断。预分诊读得比人快，但它没有现场上下文，也不承担决定的责任。把决定权交给自动化，短期省下的是审批时间，长期赔上的是知识库的可信度，而可信度是这个系统唯一的资产。

依据：理论 A1（损失承担者持有决策权）。

落地：预分诊三分类附相似度证据、agent 自起草候选 case 标低初始置信度、置信度重算产出建议，全部止步于"建议"。人的环节被设计成快速判定（约 30 秒一条）而非结构化劳动。与决定权配套的还有让"决定"名副其实的机制：高风险双签、随机审序和深审清单，防止人沦为橡皮图章。

## 六、闸门硬度与错误代价匹配

**硬门只设在错误不可逆或代价外溢的地方；漏判代价更高的地方用软降级。**

推导：门禁不是越硬越好。硬门用错位置会制造灾难性漏判，软门用错位置会放行危险变更。判据是错误代价的方向：错误方向是"漏掉正确答案"时（冷启动期版本不匹配的 case），降级不排除；错误方向是"放行危险动作"时（data-loss-risk 的修复、不合语法的变更），硬拦。

依据：理论 §2（误诊损失与漏判损失之比决定判据软硬）。

落地：compat 软匹配，版本不符只降置信度，因为漏判的唯一相关 case 代价极高（[ADR-0001](adr/0001-soft-version-matching.md)）；severity 硬闸，高危根因不给修复；CI 硬门，YAML 语法与索引新鲜度机器可判、错误无歧义，红即挡；语义闸门（脱敏、标注正确性）机器判不了，保持约定强度并靠人审抽查。对语义判断设硬门、或对安全问题设软门，都是本条禁止的错配。

## 七、变更可逆

**任何知识变更或修复建议都必须携带显式的回退路径；不可逆动作需要升级审批。**

推导：演化系统持续修改自身，错误变更不可避免。可逆性决定错误的半衰期：每条变更自带逆操作，错误在下一轮 groom 或下一次使用中被发现并撤销，系统收敛；没有逆操作，每次变更都是不可撤销的赌注，前置审查再严也兜不住全部。本条与闸门互补。原则六决定什么被放行，本条决定放行错了之后怎么办。

依据：理论 A1 + A3（可逆性给损失设上界；非平稳保证错误必然发生）。

落地：每条 fix 强制携带 rollback；软退休而非删除（`_archive/` 可复活）；索引是生成物、可幂等重建；知识变更走 git、可 revert 且过审；roadmap 引入自动变更的机制（自动升格、路由自修订）必须先回答"如何整体撤销"再立项。任何"先合入再说"的变更流、或无法重建的派生数据，都违反本条。

## 八、可观测先于改进

**不可观测的机制既无法改进，也无法证明它没有在腐化。**

推导：这个系统的核心承诺是"越用越准"。检验这个承诺需要数据；没有数据，承诺退化为信仰，演进退化为猜测。误诊归因是本条最直接的体现。一次误诊，是知识错了还是执行错了？两者修复路径相反，混在一起会改坏本来正确的知识。

依据：理论 §4.2（元层无证据则无更新）。

落地：trace 是诊断流程的硬要求，词表固定、每步落盘、历史不删；每个机制配一个指标（命中率、路由准确率、反馈捕获率和 Tier 3 挽救率）；误诊必先读 trace 归因再动手修复；trace → metrics → 闸门构成数据回路，`trace_metrics.py` 使指标可半自动计算。无 trace 记录的流程变更、无法度量的"改进"，都不应被接受。

## 九、稀缺资源显式预算

**人的注意力与模型的上下文窗口都是硬预算，设计必须为两者同时做预算。**

推导：系统的两类瓶颈都不在算力。人的注意力决定知识入库的质量上限。逐条即时审阅违背工程师工作节律，很快没人做；上下文窗口决定诊断的推理质量。日志灌满窗口，推理质量直接下滑。两种资源都必须像预算一样被显式分配，而不是被默认消耗。

依据：理论 A2 + §3（信道与注意力双约束；变量与影子价格见理论 §6 与附录 A）。

落地，人的注意力：inbox 队列加每周批处理，单条约 30 秒，停留过久标红；fixture 套件设上限、饱和后换血，用密度换数量。上下文：三层知识按需加载、阶段一读索引和日志裁剪到失败 rank 加栈尾，守住推理的舒适区。全量日志灌入、逐条即时人审、"每条 case 配一个夹具"式的无密度增长，都是对预算的透支。

## 十、诚实退化，永不假装

**能力边界必须向用户显式陈述；每个兜底路径都要说明当前的真实覆盖。**

推导：信任是诊断系统唯一不可再生的资源。空库时装作能查、脚本未接入时装作能调，一次被拆穿，之后真命中也不被相信。诚实的成本是一次尴尬的坦白，不诚实的成本是整个系统的信用。

依据：理论 §4.1（校准性质：虚报毒化全部下游决策计算）。

落地：命名空间为空时明说并给出三条出路；Script 未接入时明说，不假装调用；机制强度如实标注（硬 / 半硬 / 约定）；单条 fixture 的判别力如实说明（N=1 时匹配近乎必然）。静默退化到次优路径、以及任何形式的能力虚报，都违反本条。

## 十一、演进由数据触发，决策留痕

**假设换成实测，闸门取代日历；架构决策连同其重评条件一起留痕。**

推导：知识系统败于两种冲动：按日历排期的"计划演进"（不管数据是否支持）与追随技术趋势的"时尚演进"（不管问题是否存在）。两者的解药相同：为每个演进动作定义可度量的入口条件，让数据说话；同时把每个不可逆决策的理由写下来，否则重评时无人知道当初为什么这样选。

依据：理论 A3 + §4.4（演化即假设检验，闸门即拒绝域）。

落地：roadmap 闸门驱动而非日期驱动，闸门数值每季度用实测指标复核；过滤率、退休率等参数从假设开始、由 `trace_metrics.py` 实测替代，第 6 个月重算容量推演；ADR 记录决策及被否决的替代方案；embedding 等推迟项写明重评触发条件，触发前不进任何阶段池。闸门驱动有已知盲区。不产生指标信号的必要工作（安全审计、依赖升级和文档偿债）由 roadmap 的"待定"池显式承载，不假装闸门万能。

## 使用与修订

- **立项**：roadmap 新事项应声明服务于哪条原则；不服务任何原则的事项默认不立。
- **评审**：skill 与流程的修改，评审时对照本文件。违反结构类原则（二、三、四）的实现，无论功能多好都应退回。
- **修复**：误诊修复先归因（原则八），修复方案不得违反验证、闸门与可逆原则（一、六、七）。
- **修订**：修改本文需 ADR 论证，且被修改的原则应已有真实使用记录；新原则必须同样从领域约束推导，而非从个别案例归纳。
