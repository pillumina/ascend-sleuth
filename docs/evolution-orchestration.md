## 1. 会话模型：一轮自演进是一个有状态会话

### 1.1 为什么需要会话

pipeline/execution 定义了"一轮里每一步怎么走"，但没有定义"一轮"本身的边界。没有会话边界，就会出现：无入口协议（人不知怎么开始）、无轮间衔接（每轮从零开始）、无恢复点（被打断就丢）。**会话 = 自演进的一次可审计运行**，类比 diagnose session（有 state 文件、可 resume、有报告）。

### 1.2 会话生命周期与启动协议（人一开始怎么下指令）

**自演进是隐形执行策略，不是用户要复述的要求**。用户下指令只说**目标 + 必要边界**；机制细节（观测什么信号、走 S2 评测、feedback loop、proposal→action→eval、授权分级、停止条件）由系统的**默认执行策略**自动装载——就像用户让"跑一次诊断"不需要复述 triage 流程一样。要求用户每次说"要 xxx 观测数据 + self-evolving"是把实现细节强加给人，违背原则九（注意力预算：人的输入成本要低）。

```
① 目标（人，一句话）
     "提升 vllm-ascend interrupt 命中率" / "降低最近的回滚" / "看 verl 有什么可沉淀的"
     —— 只说：范围 + 意图 + （可选）预算上限。机制一律不说。
② 装载默认策略（agent，隐形）
     从目标推断：scope / goal 类别 / 数据前提（S2 池够不够、feedback 有没有）
     自动带出：观测信号集 + 候选生成 + 授权分级 + 停止条件 + 预算分层（本文全部默认值）
③ 对齐（agent → 人，关键步）
     回显理解："我理解为：范围 X、目标 Y，将按默认策略跑一轮（约 Z token）。
     自动类改动即时合入；需你审的改动攒到轮末一次提一个 PR（批粒度，不会
     每卡打断你）；高风险（路由/流程结构）改动会标注，你重点审"。默认批
     提交模式（pipeline §6.3a）；用户可要求任务级攒批（做到目标完成再提 PR）。
     以下情况**先澄清再执行，不边跑边猜**：
       - 范围/目标有歧义（如"优化系统"→ 问哪一层/哪个 namespace）；
       - 数据前提不满足（如目标提命中但 S2 池未建 → 说明要先建池或改用现有数据）；
       - 目标互相冲突或与现状矛盾（如"零人工"但目标含结构层改动）；
       - 用户表述含糊（"感觉没想清楚"→ 给 2–3 个候选目标让用户选，而不是代用户决定）。
④ 计划（agent）    产执行计划：候选 proposal 清单 + 预计 token/轮次 + 依赖顺序
⑤ 确认（人）       批准 / 调整（建议与决定分离在会话层的形态）
⑥ 执行 → 报告      轮内按计划跑 → 产出报告 → 存档 → 可 resume
```

**对齐 gate（③）为什么必要**：self-evolving 是隐形策略意味着系统主动性强，主动性强的东西若在错误目标上跑，浪费比人工还大（一轮就是几十 K token）。对齐 = 用一句话回显 + 至多 2–3 个问题，换取"整轮跑在用户真实意图上"。**对齐不是让用户补机制描述**（机制是默认的），是确认目标本身——这是原则五在会话入口的形态：agent 提出理解，人校准目标，然后才授权执行。

**对齐必须说用户语言（UX 规格见 evolution-user-guide.md）**：回显与提问不得使用内部术语（S2 池、结构层、授权分级、观察窗），要翻译成使用者的领域语言——"需要先拉一批历史 issue 当测试集"而非"S2 池未建"、"涉及路由/流程本身的改动会先请你确认"而非"结构层走 dual"。术语解释放可展开处（tooltip/details），不占主对话。**对齐的输入是领域目标，输出也应是领域语言**——否则对齐本身引入新的理解负担，与目的相反。对齐同时要说清**冷启动预期路径**：若数据基础不足（如无测试集/无反馈记录），明说"第一轮先建基础，预计第 N 轮起才有真正的 X 判断；期间会产出 Y（如覆盖缺口清单）"，避免用户期待改进却只收到基建报告（见 user-guide §3）。

**默认策略与用户覆盖的边界**：所有机制参数（观测信号集、S2 池口径、授权分级阈值、预算分层、停止条件）有文档默认值，用户不必说；用户只需覆盖自己关心的（范围、意图、预算上限、特殊约束如"这轮不许动 triage"）。**覆盖是例外不是常态**——绝大多数指令走到 ③ 对齐即可，⑤ 确认一键放行。

会话状态落 `proposals/sessions/<SESSION-ID>.yaml`（session id、参数、计划、每卡进度、已耗 token、停止原因、报告引用），**运行时状态，本地留存、gitignore**（对齐仓库 traces/ 与 inbox 草稿的哲学——逐轮变化的进度/账本不进 git，避免噪音与跨机断链）；稳态结果以报告与采纳卡投影入 git。会话可 resume：中断后重新加载 state，未完成的卡继续，已完成的卡不重跑（幂等，同 issue-ingest 的 processed 排除哲学）。

## 2. 目标函数与停止准则

### 2.1 目标函数（G2：每轮在优化什么）

**目标函数与用户 goal 的层级（关键，防 override 用户意图）**：用户 goal（§1.2 第①步，提命中/降回滚/省 token/补覆盖）决定**本轮做什么**（候选排序权重与停止条件）；目标函数决定**本轮做得怎么样**（效果判读）。两者不冲突时目标函数是选择依据，冲突时**用户 goal 优先**——目标函数永不 override 用户明确意图（原则五：用户是损失承担者）。目标函数的角色：

- **候选排序**：同 goal 下多个候选都符合时，用目标函数排序（增益高/成本低/风险小的先做）；
- **报告判读**：衡量本轮"增益是否盖过成本"（见下）。

```
目标 = max( Σ validated 卡的效果增益 − λ_token × 本轮 token 消耗 − λ_risk × 回滚/误诊代价 )
```

- **效果增益**：由 execution §4/§5 的 predicted_effect 达成率度量（沉淀 resolve、组件 mis 下降、命中率提升）；
- **λ_token**：token 的影子价格——预算紧时调高，token 效率 proposal 的价值上升（这就是第 3.4 节"token 优化项"的理论依据）；
- **λ_risk**：回滚/误诊代价权重——高风险区域自动调高，压向更保守的授权级别。**注意 λ_risk 只影响同一 goal 内的候选排序与授权建议，不导致系统"永远不提结构类改动"**——结构类候选由数据信号触发（组件台账/E2 错例），授权级别（dual）是门禁不是否决；若某结构类长期被数据指向但被 λ_risk 压制，季度自评应复核 λ_risk 是否过高（参数本身服从实测修正）。

目标函数不进代码（它是季度自评校准的人读参数），但它给出**每轮报告的判读框架**：这一轮产出 validated 卡 X 张、耗 token Y、回滚 Z 次，增益是否盖过成本。

### 2.2 停止条件（G2：即使 token 无限也要设停止目标）

**任一满足即停**（停止后出报告，不硬断——state 保留可恢复）：

| 条件 | 触发 | 含义 |
|---|---|---|
| 预算耗尽 | token_budget 用尽 | 本轮边界（最常见） |
| 产出达标 | validated 卡达 N 张（默认 3） | 已产出足够，不再贪多 |
| 信号误报 | 连续 M 个候选被否决（默认 3） | 信号质量差，停比继续堆好 |
| 收敛 | 本轮无新候选或全部卡进 rejected/validated | 数据已榨干 |
| 人中断 | 人在任一步打断 | 最高优先级 |

### 2.3 稳态降频（G7：收敛区域不再产 proposal）

某 scope 连续两轮满足"无新信号 + 无 rejected + 无降级态积压（unconfirmed_valid/unconfirmed 卡为 0）+ validated 效果达标" → 该 scope 标记 `steady`，进入降频池（默认停 4 轮再复检）。防止在已收敛区域空转烧 token；**降级态积压不算收敛**（有未决的存疑卡说明该区域仍有待处理项，降频会掩盖）。`steady` 状态记录在 session state / 索引，新信号（新 issue 类型、新 trace 模式）或新降级态出现时自动解除——**稳态是数据触发的暂停，不是永久关闭**（原则十一）。

### 2.4 候选积压治理（防候选池腐烂）

候选 idea 每天由信号产生，但消化受轮次预算与人审节奏限制——无治理则候选池腐烂（过期候选、重复候选、低质卡堆积）。规则（复用仓库 inbox 纪律：队列不是档案）：
- **候选水位上限**：每 scope 未处理候选超上限（默认 20，参数落地校准）→ 停产新候选，优先消化积压（信号继续记录但不产卡）；
- **候选过期**：候选停留超期（默认 8 周，参数校准）且从未被采纳 → status 标 `stale`（候选过期态，pipeline §7 词表），季度自评批量转 rejected + 理由"长期未采纳"；stale/rejected 不删除记录（同 rejected 留痕纪律）；
- **重复候选**：起草时若同 trajectory/同 target 已有在池候选 → 合并而非新建（起草 agent 检查在池卡，§5.2 冲突检测同源）；
- **信号误报反馈**：候选积压率高 = 信号产卡超过消化能力 → 下调该信号触发权重（§5.1 参数校准的输入），不是无限扩池。

## 3. Token 预算与成本侧

### 3.1 会话级预算分层（G6 + 原则九）

| 阶段 | 默认占比 | 说明 |
|---|---|---|
| 观测 | 10% | 跑信号脚本——本应近 0（脚本聚合），大头是读聚合结果 |
| 起草 | 30% | 读卡/台账/先例 + 起草 proposal（分层供给：先聚合后全文） |
| 实验 | 50% | 最大头：执行 validation（replay/复测） |
| 报告 | 10% | 会话报告 + 季度自评输入 |

占比是**执行参数**，由实际用量实测校准（进 timeline，季度复核）——不是拍脑袋定额。

### 3.2 卡的成本侧字段（G6：predicted_effect 只有质量，没有成本）

成本字段已并入 **pipeline.md §7 v3 schema**（唯一事实源），此处只重申语义：

```yaml
predicted_effect: {metric: "...", from: X, to: Y}   # 质量预期（execution §2）
estimated_cost: {tokens: 8000}                      # 预计 token（起草时填）
actual_cost: {tokens: 9500}                         # 合入/回测后写回，缺失即审计缺口
```

`actual_cost` 随 decisions 一起写回，进 timeline——**没有实际成本记录的 proposal 是不可审计的**（与"无实验证据不合入"同一纪律强度）。

### 3.3 Token 效率作为指标

- **每 validated 卡的平均 token**（趋势：上升 = 演进变贵，触发效率审查）；
- **阶段占比漂移**（某阶段占比异常上升 = 该环节退化）；
- **候选→validated 漏斗**（起草大量卡但 validated 少 = 起草/信号质量差，烧 token 在无效候选上）。

这些指标回答一个决策问题："演进系统本身是否在变贵？该在哪一环省？"——正是 roadmap M5（groom token 治理）从一次性修复变成**持续目标维度**的形态。

### 3.4 Token 效率作为优化项（你的第三个问题的答案：是，且归 L3）

**归层**：L3（编排层）或 L2 process 维度——它优化的是"系统产出的成本"，不是知识内容。

**信号（自动触发候选）**：

- 每 validated 卡 token 连续两轮上升；
- 某阶段占比 > 预算占比 × 1.5（如起草长期超 45%）；
- 同组件重复提案（台账显示同一组件被改过且回滚过，又出新卡——先查是不是该省 token 直接复用教训）。

**典型 proposal 类型**：

| 提案 | 例子 | 验收（关键） |
|---|---|---|
| 信号脚本瘦身 | 让 trace_metrics 直接输出候选卡骨架，起草 agent 少读原始聚合 | **A/B 同质量省 token**：同样输入集，输出卡与脚本化前一致性 ≥ 阈值，且省 token ≥ X% |
| 分层供给调优 | 决策点先给聚合、判定前才展开全文（execution §7 已有），调"展开阈值" | 判定准确率不降（抽审发现率不升）+ token 下降 |
| prompt 精简 | 起草/实验 prompt 去掉冗余指令 | golden 回放无回归 + 输出一致性 |
| 先例复用 | 同组件已有 rejected/教训时，直接附教训让 agent 不再重新分析 | 重复提案率下降 |

**验收硬规则**：token 优化提案**不得牺牲供给完整性**（execution §7 论证过信息不足损害执行质量）——验收必须是"A/B 同质量省 token"，即 golden 无回归 + 抽审发现率不升 + 输出一致性达标。用 token 换质量是转移成本到无预算科目，违反原则九精神（design-theory §6 评审纪律）。

## 4. 自我指涉治理（G3：系统改自己的 skill，如何防自我确认偏差）

演进对象（skill/KB）与演进引擎（agent）同源，最危险的腐化是**系统改了自己的 skill，然后用自己定义的指标证明改对了**。对抗机制（全部已有零件，这里显式化）：

| 机制 | 对抗什么 | 落点 |
|---|---|---|
| **客观评分源优先** | 自评指标漂移 | follow-up 判定优先 S2（issue 外部 resolution）/golden，S1 工程师反馈 > 组件台账自评（execution §5 观察窗已按此排序） |
| **独立评审** | 起草 agent 自我背书 | review/dual 级合入由 reviewer/双签人审，auto 级月度抽审 + 可撤销授权（pipeline §6.3） |
| **回滚率入指标** | 错误合入被掩盖 | 回滚率是授权级别校准输入（execution §6），上升即收紧 auto |
| **台账教训复用** | 重复犯同一错 | 组件台账记 mis + 教训，新提案必须引用先例（execution §7） |
| **季度自评审视指标本身** | 指标定义被演进"优化"掉 | 自评审的不是卡，是流程与指标是否还在测对的东西（pipeline §6.6） |

**显式红线**：自演进提案**不得修改评分/指标定义本身**（不得"让指标更容易达标"）——指标口径变更只能由人走 methodology PR 发起（L3 结构级，双签），agent 只能建议不能执行。这条是自我指涉治理的闸门，违反 = 系统给自己改考卷。

## 5. 全局上下文页与执行编排规则（G5/G4）

### 5.1 全局上下文页（G5：agent 每轮执行前加载什么）

agent 执行自演进前必须加载的**系统运行状态页**（替代每轮从零摸索，也控制重复读取成本）。**两部分生命周期不同，分开存放**：

```
proposals/sessions/<SESSION-ID>.context.yaml    # 会话级快照（运行时状态，gitignore）
  每会话开头由观测 agent 生成（~2K token 内）：
  - 当前 KB 规模（_index 头注）与覆盖缺口
  - 处于观察窗/实验期的组件与卡（谁在动、别冲突）
  - 最近 N 轮会话结论（采纳/回滚/稳态标记）
  - 当前授权白名单（哪些类目 auto 可用）
  - 指标快照（四层，最近 2 期）

proposals/strategy-memory.yaml                  # 策略记忆（跨会话累积的资产，人确认后入 git）
  结构级教训的持久层（见下），随季度自评追加，不随会话重生成
```

**策略记忆（跨轮结构级教训）**：台账记的是"组件失败"单点教训；结构级教训（"这个 namespace 用 category 轴拆比 platform 轴好""该 issue 池的 workaround 类 resolution 占比高应降权"）需要跨轮累积——否则季度自评的结论随会话结束丢失。规则：季度自评的结构性结论追加进 **`proposals/strategy-memory.yaml`**（每条带日期 + 依据指标引用）；后续会话的 context 快照引用它作决策上下文（对应 SkillOpt meta-skill 思想，载体是词法文本可 diff 可审）。记忆条目由人确认后写入（季度自评产出），agent 只建议不直写。**策略记忆是资产（进 git），会话 context 是快照（gitignore）——两者不混放，避免策略记忆随会话重生成丢失或被运行时状态覆盖。**

生成成本计在"观测"阶段；执行 agent 只读这一页 + 自己卡的证据，不重复全量扫描（token 预算同 groom M5 纪律）。

### 5.2 执行编排规则（G4：同轮多卡冲突）

| 规则 | 内容 | 理由 |
|---|---|---|
| 同组件串行 | 同一 target_component 的卡不并行实验（排队） | 并发改同一组件 = 无法归因 |
| 冲突检测 | 计划阶段扫描 affected_paths 交集 + **同文件/同 namespace 写交集**；冲突卡降级为串行或合并 | 防修 A 弄坏 B 且无法回测；**粒度不止组件**——不同组件可能改同一 case 文件（git 同文件并发写会冲突），冲突检测覆盖到"改动的文件集 + namespace 目录"层 |
| 依赖排序 | 依赖卡（如先补 case 再改其引用的 triage）先执行 | 实验基准有效 |
| 变更集原子 | 一轮内对同一组件的多次小改合并为一次合入 + 一次回测 | 回滚粒度清晰 |

## 6. 原则追溯

| 设计元素 | 服务的原则 | 说明 |
|---|---|---|
| 会话协议（目标→对齐→确认→执行） | 五（建议与决定分离） | 人给目标与边界，agent 装载默认策略并回显对齐，人批准后执行 |
| 目标函数 + 停止条件 | 十一（数据触发）、九 | 无目标不可判达成；无停止不可审计 |
| 稳态降频 | 十一、九 | 收敛区域不空转烧 token |
| token 预算分层 + actual_cost 写回 | 九（资源预算） | token 是预算资源，使用必须可审计 |
| token 效率提案 A/B 同质量验收 | 九 | 预算优化不得转移成本到质量 |
| 指标口径只能人改（红线） | 十（诚实退化）、二 | 系统不得给自己改考卷 |
| 客观评分源优先 | 八（可观测先于改进） | 外部 ground truth > 自评 |
| 同组件串行 / 变更集原子 | 七（变更可逆） | 归因与回滚粒度清晰 |
| 全局上下文页 | 九、二 | 每轮加载最小充分状态，防重复扫描 |
