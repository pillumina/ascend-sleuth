# ascend-sleuth 诊断面板（DSH 插件）

诊断可视化操作台。**常驻包里**对话视图只留「诊断」tab，指标挂在整页「Ascend Sleuth」（`dsh-plugins/sleuth-console/`，
与自演进同一个入口）——它读的是全库读数，与当前会话无关。**动态热加载路径**没有整页容器，仍退回
`conversation.view` 的两个 tab（诊断 / 指标）。

- **诊断**：会话列表（状态/时间/搜索/过滤/排序）→ 展开轨迹（summary/evidence/reason/reference）→ 证据文件打开；每张卡上的「打开会话」直接切到那一单的会话
- **侧栏「诊断记录」**（页脚入口 + 弹出的面板）：可按时间或按价值排序的诊断会话清单（默认按最后更新时间倒序），点一行切过去
- **指标**（Ascend Sleuth子页）：**累计读数**（覆盖 / 不可解读 / 需处理 / 条目使用 / 长期零选中 / 过程动作成本 / 变差的读数 / 本期该做）→ **闭环判决**（首屏只列要处理的判据：结论 → 证据 → 下一步 + 可复制指令）→ 状态条（快照新鲜度 + 判据覆盖面 + 索引/磁盘 drift）→ 闭环检验（判据全貌，折叠）→ 容量台账（**逐格** + 历史趋势条）→ 存量体检 → 趋势差分 → timeline 快照 → 实时计算

### 会话攒多之后怎么找（打开会话 / 价值优先 / 诊断记录）

三件事一起解决"会话太多、有价值的要一条条点进去才发现"：

| 入口 | 在哪 | 做什么 |
|---|---|---|
| 打开会话 | 每张会话卡的指令区第一个按钮 | 切到这一单的会话（`sessions.open`），不用回左栏按会话号找 |
| 排序：按价值 | 列表工具条（时间范围右边） | 已沉淀 ＞ 库中已有案例 ＞ 新形态 ＞ fix 已生效 ＞ 已定位 ＞ 其余；同档按最后更新时间倒序 |
| 诊断记录 | 侧栏页脚「诊断记录」按钮 → 弹出的面板 | 同一个清单的紧凑版：状态 / 会话号 / 一句背景 / 命中案例（库里没有时标「新形态」）/ **待回报 · 欠 N 天** / 已沉淀 / 当前 / 更新时间，点一行切走；面板里可按时间（默认）或按价值排序 |

三条约束把这三件事钉在"不让读者误读"上：

- **判据只有一份**（`valueRankOf`，在 `panel-client.js` 的 apply 作用域）：列表排序与诊断记录共用，
  两处各写一份就会给出两套"价值"。五档全部取自 trace 已有字段（`sedimented.state` /
  `active_case` + `active_case_in_kb` / `feedback` / `status`），不新增口径。
- **打开失败要说话**：`traces/` 里可能有从别的机器接手的单（`import_trace.py` 落位），那些会话在
  本机不存在，`sessions.open` 会抛。面板把原因写在那行旁边，不静默——静默会被读成"面板坏了"。
- **只读边界不变**：诊断记录只读 `traces/`、只做导航；生成指令仍然在「诊断」tab 里。

两个新席位都是**附加**的：`sidebar.footer.action` 是一个新 id（不替换自带那一格），
`shell.overlay` 是帧级点击穿透层（无自带 occupant）。不碰 `sidebar.workspaces`——注册进去等于
接管整个自带会话浏览器，DSH 每次升级都可能坏。

**诊断记录面板的六条交互**（这份清单就是"还能优化什么"的验收项）：

- **键盘一等**：打开即聚焦搜索框；↑↓ 选行、Enter 打开、Esc 关闭、Tab 在卡内循环。
  用来做的是"批量翻"——一条条鼠标点开再关掉要慢一个数量级。
- **筛选**：全部 / 待回报 / 可复用 / 未收尾 / 近 30 天。计数按**搜索后**的集合算，
  所以「待回报 3」与旁边的「全部 12」是同一口径。「近 30 天」按开始时间（`created_at`）算，
  chip 上有 tooltip 说明——它与列表默认排序用的不是同一列。
- **排序**：按时间（默认）/ 按价值。按时间排的是行尾那一列（最后更新时间），因此这一列从上到下是
  降序；按价值沿用与「诊断」tab 同一份 `valueRankOf`。默认按时间，理由是这张卡的用途是"先看见最近
  动过的那几单"：只有价值序时，最近开工但还没结论的单会落到列表最底部（两单最新开工的诊断排在
  全部已沉淀单之后，读起来像排序坏了）。
  两处「按时间」各按自己排序的那一列：诊断 tab 用开始时间（`created_at`），诊断记录用最后更新时间——
  两边的 tooltip 与页脚分别写明用的是哪一列。
- **键盘可到排序开关**：Tab 焦点环含 `select`（`button, input, select, [tabindex]`）；焦点在开关里时
  ↑↓ 与 Enter 交给下拉自己处理，不挪行高亮；焦点在这一格时 Tab / Shift+Tab 仍由焦点环接管。
- **当前会话**：面板行里标「当前」；会话卡的「打开会话」换成「当前会话」（不再是一个点了没反应的按钮）。
- **计数对照**：面板头写「N 条诊断记录 · 本工作区 M 个会话」，一眼看出还有多少会话没有诊断记录；
  底部只在被截断（>40 条）时才说「只列前 40 条」。

「浮层」这个词只在代码注释里用（指的是 DSH 的 `shell.overlay` 槽位）；读者面前一律叫面板。

### 侧栏行首的两个记号（会话列表里能直接看出来）

一行只有一格（约 8px），所以只画**一件欠着或可复用的事**，不铺状态目录——状态全貌在诊断记录与
会话卡里。形状与颜色双通道区分，色弱读者只凭形状也认得出：

| 记号 | 画法 | 什么时候出现 | 悬停卡写什么 |
|---|---|---|---|
| 待回报 | 琥珀色**缺环**（圆环留一个缺口） | `feedback.outcome: pending`：给了 fix，等现场回报 | `待回报 · 欠 N 天` / `自 MM-DD · 命中 <case>`；**已收尾的单再加一行**`诊断状态 已定位（收尾与回报是两条轴）` |
| 知识库可复用 | 紫色实心**菱形** | 已沉淀，或命中的案例库里已有（即「价值优先」的前两档） | `知识库可复用` / `命中 <case>（库中已有）· 已沉淀` |
| 不画 | — | 其余一律安静：在查、已转上游、不跟了、空记录，以及"已定位且无人欠账"（那是常态） | — |

两条取舍：

- **优先级 = 欠着的事 > 可复用的东西**：同一单两种都成立时画缺环（`panel-host.js` 的
  `ascend-session-marks` 里一条三元表达式，读的时候别把它当随机顺序）。
- **"在查"不画**：DSH 自己在运行中/未读的行画状态点，我们的记号只在**空闲且已读**的行出现
  （见 `TraceRowLeading` 上方的注释）。画了也正好在它有意义的时候被盖住，等于白做。


### 单次诊断的五块与累计读数（诊断观测数据面）

设计与口径在 `docs/mechanism/diagnosis-observability.md` 的 3.7 与第 4 节；这一节只记面板从哪取数、
缺数据时显示什么。

**诊断 tab：一次诊断展开五块。** 数据来自轨迹（`traces/<会话>.yaml`，只读）与单次诊断的本机明细
（`metrics/entry-activity.local/<会话>.yaml`，不进 git，只在产生它的那台机器上）：

| 块 | 给什么 | 取数来源 |
|---|---|---|
| 本次结论 | 会话号、最终状态、结论强度档、根因一句话、命中的案例与分数、沉淀到哪个案例、回报状态 | 状态与定位结论取轨迹；`strength` / `route.hit_case` / `feedback` 取本机明细；案例标题与分数取读侧视图 `knowledge/_index/*.list` |
| 各步 | 步骤名、同批并行分组、返工标记；每步的耗时占比这一格写「本次没记」 | 动作与 `parallel_group` 取轨迹事件 |
| 检索 | 展开候选、载入正文、排除的条数与 id、命中的那条、先验三态与消费点 | 轨迹事件的 `candidates` / `considered_candidates` / `excluded_cases` / `reference_lookup` |
| 成本 | 诊断窗口内的四类 token、工具总耗时与最慢一次、窗口外的调用数、长调用标记、本会话累计（对照）、一次诊断的读入账（四个分项） | 本机明细的 `cost.window`（窗口内）与 `cost.tokens`（本会话累计）、`cost.index_read_tok` |
| 本次没记 | 这次没有数据的字段与原因（停止原因、分步工具耗时、会话账单关联等） | host 逐项判"有没有数据"后交给卡片 |

判据写在界面上，读者不必回查代码：返工 = 同一动作在本单出现多次；同批并行 = 事件的
`parallel_group` 取同一个值。

**本机明细缺件时先补，不要当成面板坏了。** 五块里的 `strength` / `route.hit_case` / `feedback` /
`cost.*` 都读 `metrics/entry-activity.local/<会话>.yaml`；这个目录为空时整块显示「本次没记」。
补法：先 dry-run 看会写什么，再落盘——

```bash
python3 scripts/trace_entry_activity.py                    # dry-run
python3 scripts/trace_entry_activity.py --apply            # 写本机明细 + 增量行 + 游标（周批用）
python3 scripts/trace_entry_activity.py --apply --session <session_id>
python3 scripts/trace_entry_activity.py --local-only       # 只写本机明细（面板自动走这一档）
```

**成本明细是旧格式时不用手工跑命令。** 明细里没有 `cost.window` 的（旧格式只有本会话累计）单一经
展开，面板会自己跑一次 `--local-only` 重建这一单，然后按诊断窗口重画。重建完会读回明细核对窗口
真的补出来了：会话日志不在这台机器上、或轨迹缺 `created_at` 时补不出来，卡片会如实说失败并给
手工命令，另留「重试」。只重建打开的这一单（单会话约 4 秒），不做列表级全量重建：全量要几十秒。

`--local-only` 与 `--apply` 的分界不是方便与否，而是写什么：前者只写 `metrics/entry-activity.local/`
（运行时数据，不进 git）；后者还会往 `metrics/entry-activity.d/<周>.yaml` 追加增量行、更新共享游标。
面板自动跑只能走前者——用后者会把用户当次聊天里的工具调用记进诊断指标，并与其他 session 抢游标。

**日志找不到时不会覆盖已有明细。** 会话日志按几个候选目录逐个找：`DSH_HOME`、`~/.dsh`、桌面版
放数据的目录；面板调子进程时还会显式传 `DSH_HOME`。一个都找不到时，脚本保留原来的明细、不写空
记录，`--local-only` 以非零退出——面板据此报失败而不是「已重建」，卡片里给原因与手工命令。

**每步耗时与 token 还要求轨迹里有 `ts`**：没有 `ts` 切不出步窗口，明细里 `cost.step_cost` 就只能是空。
所以看到「每步耗时」一栏恒空时，先查 trace 有没有 `ts`（`skills/diagnose/SKILL.md` 的「每步必写 trace」节），
再查明细文件在不在——两者是两回事。

**成本块报的是诊断窗口内的成本，不是本会话累计。** 会话日志记的是整个 harness 会话的账：同一段
对话里先后做两单诊断时，本会话累计会被两单各算一遍，两行的耗时与 token 就会一模一样——那不是
「两次诊断一样贵」，是同一条账单被记了两次。窗口取 `created_at` → `ended_at`（没写就退到
`updated_at`，卡片上会写明），窗口外的调用只计数、不计入本单。

窗口边界来自轨迹里手写的两个时间，所以读数是**下限**：这一单若在 `created_at` 之前已经开始动作，
那部分不计入。明细是旧格式（只有 `cost.tokens`、没有 `cost.window`）时，列表这两列写「—」而不是
拿本会话累计顶替；展开那一单会自动重建（见上）。


每步的耗时占比这一格固定写「本次没记」，因为现在没有产出方：会话日志里的工具耗时按 harness 的
`step`（每轮助手消息一个）计数，轨迹的 `step` 是诊断流程自己的编号，两套编号不同源。按 `step`
直接关联会把耗时挂到别的动作上，比留空更坏。指标清单里「分步成本」也还是蓝图项。

**指标 tab：累计读数。** 数据来自生成物 `metrics/entry-activity/<部署>.yaml` 与体检判决
（`scripts/metrics_health.py --json`）：

| 块 | 给什么 |
|---|---|
| 覆盖 | 部署、期号与期数、记录运行次数、检出、本机明细份数、全库案例数（零选中的分母） |
| 不可解读 | 缺分母的读数与缺的是哪个分母；判决不可用时写明这一步判不了 |
| 需处理 | 越界或退化的项数、判据评估进度（`N / M 条判据已评估`）、可解读性判定进度 |
| 条目使用 | 本期增量榜与跨期累计榜两张，各含案例与先验两段；每行 id（等宽）+ 标题 + 计数。累计榜另有「最后」列：案例行读生成物的 `last_hit`，先验行读 `references.<id>.recent` 里最近一次运行所处的周 |
| 长期零选中 | 本期与跨期都没被选中的案例数（分母 = 读侧视图的条目数），并写明「不据此退休」。与生成物的 `cold` 不是同一个集合：`cold` 按有没有非搬运行记录算 |
| 过程动作成本 | 按工具的调用次数、p50 / p90、失败与超时（生成物的 `tools` 段） |
| 变差的读数 | 每条给读数（含阈值或对照）与一条动作 |
| 本期该做 | 三到五条，取判据给的动作用与体检输出的候选命令；凑不满就少写，不补凑数条目 |

两条硬规则（缺一条就会把"没数据"读成"读数是 0"）：

1. 没有数据的格子写「本次没记」，缺分母的读数写「不可解读」，都不写 0。
2. 读不到生成物时只报缺哪个文件与重建命令（`python3 scripts/build_entry_activity.py`），
   **不回退到原始记录自行求和**。源的形态（`metrics/entry-activity.d/<周>.yaml`，一周一个文件、一行一条）
   归生成器，面板只读生成物。

**两条路径分开。** 运行时件（`traces/`、`metrics/entry-activity.local/`）读**主检出**那一份：
取值与 `scripts/exec_log_path.py` 的 `main_checkout()` 同源（git common dir 的父目录），
解析不出主检出时退回会话自己的工作目录。进 git 的读取（`knowledge/`、`metrics/timeline.yaml`、
`metrics/entry-activity/<部署>.yaml`、`scripts/`）读会话自己的检出。在主检出里开面板时两者是同一个目录。

案例分数读的是索引生成物（`knowledge/_index/*.list`）：它由 `scripts/score_entries.py` 按记录计数与
冷启动先验算出、写进生成物，案例文件里不再有这个字段。

### 体检器失效与容量趋势（2026-09 三轮）

**① `--check` 三态接进首屏**。体检器现在区分三种结局——`0` 判据全部评过且无越界 / `1` 有判据被违反 /
`2` **有判据没被评估**（结论不可用）。第三态是本轮实测出来的必需项：修前只看"有没有 ✗"，
于是两回假绿都无人喊——一处漏解包让容量判据从未触发、`gates.yaml` 解析失败被
`except: return {}` 吞掉后体检器报 `clean（判据全部评过）`。面板据同一份输出：

- 状态条加"判据 N/M · 可解读性 K/L"（**"没报越界"与"没被检查"从此可区分**）
- 第三态时出现红色 `BrokenDetector` 横幅：点名哪条判据没被评估，并明写
  **"下面列的『没有报出越界』不等于『没有越界』"**，附复现命令与三态退出码语义

**② 容量历史趋势条**。容量是唯一有多个数据点的通道（live 快照只有 3 期且指标口径逐期不同）。
每格画迷你条形（CSS 条形原语，与 ev-panel 的 `.ev-bars` 同一套，不用 SVG）并标净增量
——实测 `inference/vllm-ascend · interrupt` 显示 **`32→85 (+53)`**，从"压线"到"硬上限"的
走势一眼可见。**门槛**：当前值以判决（体检器对磁盘现实的判定）为准，历史只画走势。

做这条时踩到一个形状问题（如实记下）：timeline 里的容量有**三种写法**——
`{count, cap}` 字典（W37-live 起）、`"36/30"` 字符串（W35/W36-capacity）、整块缺席（诊断侧 live 快照）。
只认第一种的话趋势永远只有 1 个点、什么也画不出来。`normalizeCapacity` 归一三种形状后才有 3 个点；
`scripts/panel_render_check.js` 的断言也按同一归一口径独立重算，避免"只认一种形状"悄悄退化。

### 指标 tab 的"闭环判决优先"（2026-09 二轮重做）

一轮重做（下面那节）把"变了什么"提到了首屏，但仍然**没有回答"这算好还是坏"**：
实测面板显示 20+ 行 label/value，其中 `85/30`（soft_cap 的 2.8 倍、已超 hard_cap）
和一格正常的 `8/30` 长得一样；`misdiagnosis_rate 0/3` 被读成"零误诊"。
根因是**判据链在最后一步断了**：

| 层 | 状态 |
|---|---|
| 判据（阈值） | `metrics/gates.yaml` 有 —— 面板**不读**（自己写死 `/30`，还把格子加总到 namespace） |
| 检测器（结论+动作） | `scripts/metrics_health.py` 有 —— 面板**不调** |
| 展示 | 面板把「数据说明」默认折叠，正文是"早期 trace 缺事件"的历史欠账说明 |

二轮改成：**面板不重算判据，只渲染体检脚本的结论**。首屏是 `VerdictCard`——
一行一条判据，恒为 `结论 · 证据 · 下一步`，点开给可复制指令；零越界时不占位，
只留一行"本期无阻塞项 · 已检 N 项判据"。

四个随之修掉的具体缺陷：

| 缺陷 | 实测 | 修法 |
|---|---|---|
| 容量口径与判据不一致 | 面板把 (framework × category) 加总到 namespace 比 `/30`（vllm-ascend 显示 `114/30`），判据是**逐格**计（interrupt 单格 85/30） | `CapacityLedger` 逐格渲染，阈值从 `gates.yaml` 读 |
| 假绿无视觉区分 | `0/3` 与 `85/30` 同等权重；gates 明确判 `misdiagnosis_rate` **不可解读** | 指标行挂「不可解读」徽标 + title 说明；反馈告警改写为"所以标着不可解读（不是 0）" |
| 看到的不等于现实 | 面板读的是**生成物**索引/快照（条数与逐格容量**现算**：`index_counts.py`／体检链；索引头注已不再写数字，写进去就会在并发合并时撞行或漂移），陈旧时不标注 | 状态条报快照龄期（`2026-W37-live · 1 天前（阈值 7 天）`）+ 索引↔磁盘 drift（`索引 N ≠ 磁盘 M`；两者一致时不显示告警） |
| 判据不可查 | 读者不知道面板覆盖了哪几条腿 | `CheckLedger` 折叠区列出全部判据项（含 ✓），一行标出来源是 `gates.yaml` |

**阈值的唯一归属**：面板、CI、周批都读 `metrics/gates.yaml`。改判据只改那一处；
`scripts/panel_render_check.js` 有断言钉住"面板报的越界格 == 按 gates 独立算出的越界格"。

**顺带修掉的判据链断点**（本轮实测发现，改面板之前先修它）：
`scripts/metrics_health.py` 里 `MS.collect_structural(root)` 返回 `(out, notes)` 元组，
但调用处没解包 → `structural.get(...)` 抛 AttributeError 被 `except` 吞掉
（`s_notes` 因此恒为空）→ `capacity_by_ns` 恒为空 dict → **容量越界判据从来没触发过一次**，
`--json` 的 `current` 块也跟着恒为 `None`。容量这个最要命的信号（85/30，硬上限 60）
因此只能靠人读快照 note 里的散文才发现。

### 指标 tab 的"变化优先"（2026-09 一轮）

旧版把 7 期 × 10+ 指标全平铺成 label/value 网格，读者得自己逐行找"哪一行和上期不一样"。
一轮改成首屏 `CompareStrip`：只列**动了**的指标（新增 / 变化 / 本期不再采集），
标注 `7 → 11` 与增量，末尾报"N 项持平"；期卡收起时带前 3 项指标摘要。
差分回答"动了什么"，判决回答"这是不是问题"——两者叠加，首屏才既聚焦又可解释。

## 加载方式

本插件有四条装载路，按本机 DSH 有哪些工具选。面板源码一份，四条路读同一份。

| 路 | 怎么装 | 生效范围 |
|---|---|---|
| 热加载 | 用 `dsh-plugins/loader/` 装出 `panel_from_file`，再发两个路径 | 本会话，随进程消失 |
| 常驻插件包 | `plugin_manager install_bundle(target: <仓库绝对路径>/dsh-plugins/dsh-sleuth-panels)` | 本 profile 每个会话，重启不丢 |
| 脚本安装 | `node scripts/panel_install.js`（经 `/api` 通路调本机界面那个插件管理器） | 本 profile 每个会话，重启不丢 |
| 插件页安装 | 在侧栏「插件」页粘贴 `<仓库绝对路径>/dsh-plugins/dsh-sleuth-panels` | 本 profile 每个会话，重启不丢 |

后两条路装的是同一个包，落进 profile 的是同一处状态，差别只在谁去调插件管理器：模型的工具、
脚本，还是用户点界面。

### 快速开始

在 DSH 对话中粘贴（或直接 `/skill:preload-panel`）：

```
请加载 ascend-sleuth 诊断面板：
① 若会话里没有 panel_from_file 工具，先读 dsh-plugins/loader/panel-from-file.js，
   用 cordis_define（kind: new，idPrefix ldr，code.host ← 全文）+ cordis_run 加载它（host-only，免审批）；
② 然后 panel_from_file(host: dsh-plugins/ascend-panel/panel-host.js,
                        client: dsh-plugins/ascend-panel/panel-client.js,
                        idPrefix: sleu, name: "ascend-sleuth 诊断面板", purpose: "…")。
完成后对话视图应出现「诊断」「指标」两个 tab。
```

`panel_from_file` 读盘 → 定义 → 激活，**只发两个路径**。**不要自己把文件内容重新输出一遍**：两个文件合计 ~70KB，转写要几千 token、几分钟；给路径只要几十 token。`/skill:preload-panel` 是同一流程的 skill 封装（仅 DSH）。

前置条件：工作区为 ascend-sleuth 仓库（面板读 `traces/`、`knowledge/`、`references/`、`metrics/`）。热加载那条另需 `cordis_define` / `cordis_run` 工具；常驻插件包那条另需 `plugin_manager` 工具。三样都缺时先跑 `node scripts/panel_install.js`（脚本安装，走界面同一条 `/api` 通路）；它拿不到地址与 token、或 `/api` 没有认领端点时，再走插件页安装——那条不需要工具，只要用户能操作侧栏「插件」页。替换已装包时都要能重启 DSH Desktop。

### 手动加载

1. 加载 loader（一个会话一次，host-only 免审批）：`cordis_define`（kind: new，idPrefix `ldr`，`code.host` ← `dsh-plugins/loader/panel-from-file.js` 全文）→ `cordis_run`
2. `panel_from_file`（idPrefix `sleu`，`host` / `client` 指本目录两个文件）→ 返回 awaiting-approval 时在 UI 允许 → 出现「诊断」「指标」两个 tab

### 常驻插件包（有 `plugin_manager` 工具）

```
plugin_manager install_bundle(target: <仓库绝对路径>/dsh-plugins/dsh-sleuth-panels)
```

`lib/index.js` 与 `lib/client.js` 由 `node scripts/build_panel_bundle.js` 从本目录两个源文件生成，不要手改；改源码后重跑它，`--check` 核产物与源文件一致，`node scripts/check_panel_bundle.js` 做可加载性冒烟。安装结果里 `restart-required` 表示运行时仍持有先前那份模块，让用户重启 DSH Desktop 后 tab 才出现。

### 脚本安装（三件工具都没有，DSH Desktop 默认如此）

界面调的是 `pluginManager` 这个 Remote 服务，Connection 在 `/api` 上把它的端点交给已认证的
调用方，所以模型可以自己装，不必让用户粘贴：

```
node scripts/panel_install.js            # 装并使能（地址与 token 从日志里取）
node scripts/panel_install.js --check    # 只查状态（只对能定到包名的目标给判断）
node scripts/panel_install.js --remove   # 卸载
```

它先 `GET <base>/?token=<token>` 换会话 cookie，再 `POST <base>/api/pluginManager/<方法>`
（信封 `{type:'client-request', rpcId, method:'pluginManager/<方法>', payload:{args:{…}}}`），
先 `inspect`（spec 传字符串）：认了且没装就 `installBundle(spec, {enabled:true})`；回
`already-installed`（这条 refused 不带包名）就从本地 `package.json` 读包名再 `setBundleEnabled(name, true)`。
`installBundle` 阻塞到操作结束才返回，结果里的 `application` 与 `warnings` 与
`plugin_manager` 那条同一套。退出码 0 = 操作完成（装好并使能、`--check` 有结果、`--remove`
成功都是 0；`application` 可能是 `restart-required`，那要重启 DSH Desktop 才加载新版本），
2 = 拿不到地址与 token、地址取到了但连不上，或 `/api` 没有认领端点／未授权，1 = 其他失败；
取不到地址时传 `--url` / `--token` / `--log`。

### 插件页安装（脚本安装拿不到地址与 token，或 `/api` 没有认领端点时）

发行版把插件管理器的模型侧入口写成 `disabled: true` 时，装包由界面的插件页做，装出的是同一个常驻包：

1. 侧栏「插件」页 → 添加入口 → 粘贴本仓库 `dsh-plugins/dsh-sleuth-panels` 的绝对路径（粘的是这个包目录，不是上面的面板源目录 `dsh-plugins/ascend-panel/`：后者没有 `package.json`，入口会拒）。该入口也接受包名、Git 地址与压缩包。
2. 装完看 profile 里的四处记录：`package.json` 的 `dependencies` 与 `dsh.profile.bundles` 各一条 `dsh-sleuth-panels`；`dsh.desktop.generationProjection` 里一条 generationId，形如 `dsh-sleuth-panels+<版本>+<哈希>`；`pnpm.overrides` 里一条指向 `dirname($DSH_PROFILE_DIR)/.generations/live/<generationId>/node_modules/dsh-sleuth-panels` 的 link。界面不给模型可读的 application / warnings，以这四处记录为准。包进了 generation，仓库被移动或 worktree 被清掉都不影响已装的那份。
3. 在仓库里跑 `node scripts/panel_rpc_probe.js`（退出码 2 = 拿不到地址，或路由没在服务或未授权），再刷新页面：对话视图的 tab 条里应出现「诊断」，左侧栏应出现「Ascend Sleuth」图标（指标 / 自演进在这一页里）。
4. 卸载也在这个页面做。

桌面版没有 `dsh` 命令，界面提示的 `dsh plugin --profile web install` 与 `dsh --profile web --dump-config` 都用不上。profile 的 `dependencies` 里若有指向没有 `package.json` 的目录的 link 依赖，桌面版启动的 generations 迁移会 defer，之后需要解析这个包的操作报 `cannot resolve profile bundle "<名字>"`；处置是把 `package.json`、`pnpm-lock.yaml`、`node_modules` 里的死链一起删干净。

**形态约束**：文件是 `cordis_define` 需要的函数体（`return { apply(ctx) {...} }`），原样读入/粘贴。不要改成 `export default` / `import`——动态插件代码不经过打包器，ESM 语法无法加载（此前因此失败过一次）。生成器嵌入的也是这份原文。

**改代码后**：读入的是**定义时的快照**——编辑 `panel-*.js` 后要 `panel_from_file`（`pluginId` + `mode: 'update'`）追加新 Package 再切换。

**DSH 版本差异**：`cordis_define` 支持 `codeFile` 时，可跳过 loader 直接
`cordis_define(codeFile.host, codeFile.client)` + `cordis_run`；两者都没有时回退到读全文内联。


### 面板统一色语（2026-09）

本面板与 ev-panel 共用一套颜色角色（`scripts/check_panel_tokens.py` 校验）：
`--c-*` 文字色、`--acc-*` 装饰色、`--fill-*` 实心底、`--btn-*` 渐变端色。
改动：原先直接拿亮色当文字用（`#22c55e` 绿 2.28:1、`#f59e0b` 琥珀 2.15:1，均不达 AA），
现在文字走 `--c-*` 深档；渐变按钮压深一档（原 `#3b82f6` 白字 3.68:1 → `#2563eb` 5.17:1）。

> **跨面板契约不在本文件维护**：颜色角色、字号行高、文案规范、只读边界与依赖缺失时的退化口径，
> 统一见 [../README.md](../README.md)（`dsh-plugins/README.md`）。本文件只写本面板的信息架构与历史。

**五轮追加的角色纪律（一色一义）**：`--d-*` 是"同色相深档"，专供**文字与描边**；
`--acc-*` 只作**大块面 / 进度条 / 图形**；`--tint-*` 是统一轻底纹（亮色 9% / 暗色 15%）。
判据颜色由语义唯一决定：红=越界，琥珀=提示，绿=健康态，紫=不可解读，蓝=品牌与交互。
**为什么加这一层**：实测所有文字色都已过 AA（4.76–7.09:1），而用户仍反馈"配色尖锐"——
根因是同一语义色出现在四处（底纹+左边框+图标+胶囊），以及绿色同时表示"库健康/品牌/容量正常"
三项无关语义。**收敛用色位置比调色值有效**。另补 `--surf` 叠加层与 `--hair` 发丝线
（定义了却没用到等于白写；亮色下 `border-l1` 只 4% 黑，卡片没有边界、层级靠色差硬撑）。

## 依赖

- Host：`fs` / `sessions` / `shell`。`shell` 缺失时证据文件打开、**指标判决**与实时计算降级，其余正常。
- **`ctx.shell` 不是 bash**：服务名写着 "bash execution"，但 **DSH 在 Windows 上把它接到 Windows PowerShell 5.1**
  （实测：bash 语法 `a || b`、`2>/dev/null`、`&` 全部是语法错误）。面板里任何走 `shell` 的命令都必须
  按方言安全写——打开文件那条用了"最可能的方言在前、失败试下一个、按 exit code 判定"的阶梯
  （`Start-Process` → `open` → `xdg-open` → `explorer.exe`），不是一条 bash 链。踩坑记录：
  旧实现 `(open X || xdg-open X) >/dev/null 2>&1 &` 在 PowerShell 下整条命令解析失败，又被后台重定向吞掉，
  用户点「打开报告」**完全没有反应**。要确认某条命令在面板环境里的真实行为，可临时注册一个 host-only
  探针工具（跑 `shell.resolve` + `shell.run` 并回传 exit code/stdout），而不是拿本地 pwsh 的直觉推断。
- **指标判决依赖 Python 3 + PyYAML**（跑 `scripts/metrics_health.py --json`）：解释器按
  `python3` → `python` → `py -3` 逐个探测；缺解释器/缺 PyYAML/超时/无输出都返回**可执行的提示**
  （例如 `pip install pyyaml`），面板显示「体检不可用」而**不是**假装闭环正常。
- **工具重名降级**：host 会注册 `ascend_trace_status`（供诊断收尾核对、续接与面板待办时查会话状态与反馈债；
  **不是新诊断开屏的必查项**——新问题的第一屏只服务新问题）。
  `harness.registerTool` 在名字已被占用时**同步抛错**——曾因此让整个 `apply()` 中断、面板完全加载不上。
  现在改为 try/catch 告警：同名工具仍可用（占用者通常是上次会话遗留的同类插件），面板其余功能照常。
- 工作区：ascend-sleuth 仓库（Host 从 session.header.cwd 解析）。

## 功能

| 能力 | 说明 |
|---|---|
| 会话列表徽标 | 状态 / 定位到的 case / 四类待办之外，还标三件与"能不能马上动手"有关的事：**严重级**（只有 `data-loss-risk` 与 `service-affecting` 出徽标，前者写「数据风险 · 先停」）、**有没有给出 fix**（`fix_emitted`）、**fix 验证结果**（`feedback.outcome`）。缺记录的字段不占位，不制造噪声。 |
| 会话列表 | 一行两行读完：状态 / 会话号 / 框架·平台 / 事件数 / 耗时 / token（两列都是**诊断窗口内**；旧格式明细写「—」）；**按诊断开始时间（`created_at`）倒序**；筛选条与列头**一起吸顶**；搜索（session/状态/框架/定位 case/背景/未收尾/待沉淀/待复核/已交草稿，`Esc` 清空，右侧给匹配数）；按**诊断开始时间**筛选（全部/近 7/30/90 天）；收起态显示「开始 MM-DD HH:mm」+「更新 X」，完整时间在 hover；过滤（全部/库中已有/新形态/无对应案例/未闭环/待沉淀/待升格），待跟进横幅上三个数也可点 |
| 定位 | 卡片的「定位」只给**真 case id**；`active_case` 里写的是"没命中"的占位串（`pending-investigation` 系）时按「没有对应案例」显示，旁边以灰字摆出 trace 里的原值（hover 给说明），**卡面不写解释**——"这是什么、不是什么"是给改 trace 的人看的说明，不进扫读面 |
| 轨迹展开 | summary 问题背景；每步 output/reason；evidence（inline 原文折叠/文件点击打开/缺口标记）；reference 参考层徽章 + **三态徽标**；**关联面**（见下）。**默认只铺前 8 步**（更多时给一处「展开剩余 N 步」开关），列表自带 `maxHeight` 滚动；证据原文按 3000 字切片，超长时行内写明「原文 N 字，此处显示前 M 字」 |
| 打开反馈 | 点证据文件 / 资料链接 / 打开报告，成功与失败**都落在点击处**：chip 文案变「已交给浏览器」/「打不开」，明细紧跟其后（`via` 或四种方式全失败的原因），并带一个**「复制链接」**兜底。旧版只把结果渲染在卡头那一行，而证据与资料都在展开后的轨迹里——点完那一行什么都不变，读者只会说"点了没反应"。**措辞只说得出证据的那一半**：host 只证明"URL 交给了浏览器"（退出码 0），验证不了浏览器是否到前台——实测从 DSH 的 shell 打开时它不到前台（本地 http 探针能收到请求，屏幕上却什么都没有），所以不写"已打开" |
| 关联面 | 每一步"用到/查到了什么"，与「证据」（现场材料）分开、排在它之前：`case`（这一步核验/读到的 case）· `候选`（本轮载入的候选集——"看过但没选"的那一面）· `先验`（取用的词条 id + 消费点人读名）· `甄别`（agent 自己写的取舍理由，全块最值钱的一行——它把"命中"与"有用"分开）· `资料`（知识库**以外**的链接，可点开）· `调用`（工具调用清单，按需展开）。存在性以 `候选 N` / `资料 N` 徽标提到步骤行——**徽标用行的名字，不用"关联/外部"这类伞形词**：前者没说清关联什么，后者更错（先验词条就在库里）；参考层步骤已由「参考层 + 三态」覆盖，不重复给徽标 |
| 定位结论 | 卡片以结论收尾：轨迹之后单列一块「定位结论」。落点由 trace 的 `conclusion: true` 标出，没有该标记时退到"人读视图里可见的最后一条是 `hit`"这条约定；**不取"文件里最后一个事件"**——真实 trace 的末条常是 report/feedback 这类记录维护动作，人读视图会收起它们。人读视图里该条不再重复出现在轨迹末尾（完整轨迹保留原位置）；一单还没有结论时给一行说明，读者能分辨"还没收尾"与"这单没有结论" |
| 续接 | 未解决会话生成 resume 指令（复制→对话触发） |
| 沉淀 | 四状态呈现 + 沉淀指令 copy + 双标记操作（Tier2/Tier3 回写）。**case 与先验候选分家**：上段是本单 case 的沉淀状态（走 to-postmortem），下段是先验知识候选（走 to-reference，与 case 的沉淀状态互不影响）——case 沉淀不产出 reference 词条，混在一处会被读成"reference 也跟着沉淀了"（实测误读）。**「待沉淀」与「待升格」两种状态**：「已收尾 · 待沉淀」「有结论 · 待沉淀」（报告或沉淀候选已产出、但诊断还没标收尾）与「未闭环 · 待升格」在列表上有徽标、可筛选可搜索；前者按筛选结果一次生成批量沉淀命令，后者勾选后批量标已解决（只允许「已解决 · fix 生效」一种结局） |

## 回归闸门

`scripts/panel_render_check.js` 的「指标 · 闭环判决」节断言（用真实 `gates.yaml` +
真实 `metrics_health.py --json` 输出，不硬编码计数）：

- 体检 JSON 的字段齐备（`gates` / `readability` / `capacity_cells` / `freshness` / `candidate_commands`）
- **口径一份**：面板报的越界格数 == 按 `gates.yaml` 阈值独立算出的越界格数
- 首屏出现判决条、失败判据文案、容量越界格 `85/30`；「不可解读」被标记且原因可查
- drift 双向测（不等时报、相等时不报 + 合成不一致时能报）
- 点开判决行给出「下一步动作」「可复制指令」，且指令含真实脚本/技能名
- **负样本**：体检不可用时如实报错、且不显示"闭环未见阻塞项"
- **加载窗口**：判决 RPC 未返回时首屏不出现「本期无阻塞项 / 全部通过」，并如实说"读取中"
- **结果复用窗口**：判决在 30 秒窗口内复用（切走 tab 再切回不重跑 `metrics_health.py`）；
  `refresh: true` 绕过窗口强制重跑；失败结果同样按窗口复用、同样能被强制重跑；
  首屏那次**不**强制（否则缓存白加）。状态条上的「重新体检」按钮就是这条出口，
  它的说明与 host 的窗口常量同值（只改一边即红）
- **数据源三态**：timeline 读不到时判决与实时计算仍在、且不谎称"尚无 live 快照"；
  **解析不出期次**时与"没有数据"分开说并给复现命令
- **解析器与权威口径一致（metrics）**：真实 `metrics/timeline.yaml` 经 host 的 `parseTimeline` 与
  `yaml.safe_load` 的期号/kind/每期指标键数逐条相同（这条是本轮补的，此前断言喂的是 Python
  解析结果、**绕过了被怀疑的那一层**）
- **解析器与权威口径一致（trace）**：13 种**合法 YAML 形状**逐条比 PyYAML——块写法（dash 2/4 空格）、
  内联一行一事件、**折行的行内映射与行内序列**、**序列项与键同缩进**（PyYAML 自己生成的形状）、
  BOM、CRLF+BOM、块标量 `>-`/`|`、多行普通标量（含以 `- ` 开头的那行）、序列项本身跨行、
  dash 单独一行；比的字段是事件数/角色/步号/动作/output/content/evidence。主检出那一份
  `traces/*.yaml` 逐份同样对照（路径走 `scripts/shared_dir.py traces`；CI 里没有 traces/ 就
  如实打印跳过）。反方向的判据同样在：结构坏的 trace **不许静默少事件**——缩进错乱、行内集合
  没闭合两种都要出 `parseAnomaly`（行数 + 行号），host 的 `traces-detail` 与 `traces-list` 都带
  该字段，client 在轨迹行与会话列表两处都说出来，渲染层另有一条断言钉住收起态的呈现
- **默认展开最新两期**：最新一期 notes 可见、最旧一期收在「历史快照」里
- **报告进面板**：点「看报告」真的取报告（`ascend-read-report` 被调用）、默认停在 TL;DR 节、
  只渲染所选那一节（不把整份报告铺开）、给「复制全文」与「打开文件」、无写入报告的 RPC
- **期卡数据文案无字面星号**：notes/title/source 是数据，显示前经 `plainNote` 去标记
- **反馈轴分型**：占位串单显示「等现场补材料：<等什么>」、归「在查」、不显示「结果待回报」；
  只有真实 case 单才显示「结果待回报：<case>」；读取端（面板）与写入端（`diagnose` 的
  `case` 取值规则）、追问端（`resume-diagnosis` 的两分支）三条一起钉
- 契约：client 每个 RPC 都有 host 声明、host 没有 client 不用的 RPC；
  host 侧不再有 `byNamespace`、不再内联 `30` 做判断、确实走 `metrics_health.py`
- **三态**：用 `scripts/fixtures/make_broken_metrics_root.py` 造两个"判据不可评估"的临时 root
  （多一条未实现的 dimension / gates.yaml 语法坏掉），断言 `--check` 报 **2** 且 verdict 不是 `clean`；
  真实数据下断言 `violations` + `exit 1` + 判据 3/3
- **体检器失效态**：合成 broken verdict → 断言横幅出现、点名缺口、覆盖面显示 3/4、
  且**不**出现"闭环未见阻塞项"
- **趋势条**：按三种容量形状归一后独立重算，断言条形渲染 + 走势与净增量文本一致
- **trace 解析契约**：两种写法都要吃——内联 `- {role: …, output: "…"}` 与块写法（`- role: agent` 换行展开、
  长文本用块标量 `>-`）。断言"事件里有没有 output/content/reason/evidence"，**不看步数**：
  `role` 在 dash 行上，旧实现（只认内联）虽然把事件内容全丢光，步数计数**恰好仍然是对的**——
  于是这个 bug 一路漏到用户面前（表现为"agent 回答都是空的"）。含证据两种形态（内联字符串 / 块映射）。
- **报告与沉淀入口**：host 从 trace 读 `report_file` / `sediment_candidates`；client 给「打开报告」与
  「沉淀建议 N 条」；断言面板**只做入口不写报告**（无 write-report RPC）。
- **沉淀候选分家**：断言 case 段与先验段各有标签与入口、先验候选的指令走 `to-reference` 且
  把候选摘要当引子（`to-reference` 没有"读 trace"这种输入模式，不能拿 trace 路径当输入）、
  引用计数挂在轨迹标题行且措辞点明"用了几次"、**没有编辑候选项的入口**
  （面板只产指令，口径在对话里由 `to-reference` 的 grill 对齐——做成可编辑字段会与 grill 后的实际产出分叉）。
- **长输入不把卡片撑爆**：host 的证据原文有 3000 字切片，**且同时给出原文长度**（两种证据写法都要给）；
  client 的证据徽标读原文长度（不是切片后的长度）、截断时行内如实说明、轨迹默认只铺前 8 步、
  展开/收起只有一处开关、列表带 `maxHeight`、折叠点上仍画竖轨（不把折叠点画成轨迹终点）。
- **关联面**：host 的 `traceDetail` 把关联字段都提出来（`ref_id` 单数与 `ref_ids` 数组**两种写法都吃**、
  `purpose`/`outcome`/`note`/`case`/`candidates`/`tool_calls`），外部链接**两种位置都吃**
  （user 事件的 `evidence.sources` + agent 事件的顶层 `sources`）并去重；client 只在参考层步骤上
  渲染三态徽标（`feedback` 事件也带 `outcome`，那是回报结果，挂成"命中"会读反）、四类节点各一行、
  甄别理由单独成行、链接标签走"域名 + 末段"（全 URL 在 title）。
- **打开通路**：外部 URL 与仓库内文件走同一条；URL **不拼 cwd**（拼了就永远点不开），
  而"拒绝绝对路径 / 拒绝 `..`"的守卫仍然生效——三条一起测（URL 通、相对路径照旧、绝对路径仍拒）。
- **打开反馈就地**：成功与失败都按**目标**记（`openLabel` / `openNote`），chip 文案与明细都渲染在
  点击处；成功也是反馈——打了浏览器而面板不吭声，读者同样会判成"没反应"。
  两条负向判据同时钉住：**不许出现「已打开」**（面板验证不了的措辞），且反馈里必须带「复制链接」
  （不依赖浏览器焦点的兜底）。
- **指令区形态**：按钮横排（`flexWrap`）、展开的命令块只有一处（指令区与沉淀区各一处）、卡片内不复读提示文案。
- **三条状态轴与批量入口**：诊断收尾（`status`）、诊断闭环（能否升格）、知识沉淀（`sedimented.state`）
  各有名字，不互相借（词表见仓库根 `trace-status.yaml`）。筛选里的「未闭环」是诊断收尾轴
  （`in_progress` / 未知）且没有可沉淀结论、没有待复核材料、不是空壳；「待沉淀」是有 `kind: case`
  沉淀候选的未沉淀单（库中已有一律不进——再沉淀只会被 groom 判 `covered_by`）；「待复核」是有报告
  或只有 `reference` / `triage` 候选、没有 case 候选（根因可能还没定）；「待升格」是草稿已提交、
  来源诊断未收尾（升格闸门会拦，与诊断收尾是两件事）。连一轮对话都没有的记录（0 条事件、无背景/
  报告/候选）不占筛选：它在列表上挂「空记录」徽标，提示补一次诊断或标「不跟了」。
  三个 chip 带数量（未闭环与两条沉淀债）；待沉淀一次生成一条 `to-postmortem` 批量命令；两条批量分支在渲染层
  真的点得动（不是只匹配源码字符串）；批量闭环只允许「已解决 · fix 生效」一种结局（多结局混批会虚高解决率）。
  闭环判据与 `scripts/verify_case_draft.py` 是同一口径（两处各自实现，改动要同步）：命中单看
  `feedback.outcome`，无命中单看 `status: resolved` **且没有显式 outcome**。来源未闭环的单升格时会被拦下；
  有强外部证据档的可走 owner 双签。
