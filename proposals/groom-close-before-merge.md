# 兼容 Copilot 的 groom 收尾：避免重复评估，合入后补齐出队与清理

> 状态：提议。本稿调整设计，尚未同步修改分支实现。

本文供 groom 与 Copilot 维护者评审。以 main `e4cdbd3` 的沉淀面板行为为约束，包含已合入的 [PR #450](https://github.com/pillumina/ascend-sleuth/pull/450) 撤销沉淀流程。本文修改后台选取草稿与收尾的流程。文件名沿用原路径，正文不再采用「提 PR 即移入 `.done`」。只查面板操作时，读 [Copilot README](../dsh-plugins/dsh-sleuth-copilot/README.md) 即可。

## 动机

合入后的收尾缺少固定执行入口。PR 在 groom 会话结束后合入，草稿可能继续留在 inbox。下一轮再次评估这些草稿，会重复比较与确认；评估记录和快照也可能积压。

台账缺失还有另一种后果。main 的 `groom_close_draft.unmerged_prs` 跳过未登记的 key，收尾可能把漏登记误当成无 PR 的本地沉淀。两类问题都需要后台报告原因，不能靠维护者记住上轮进度。

Copilot 已经把草稿、评估记录、PR 台账、trace 与收尾日志合成一个事项。`sediment_state.collect` 将「PR 已合入且已有成功收尾日志」转入历史；详情从 `.groom/assessments/` 读取评估。提前移动记录并写成功收尾日志，会改变面板的完成判定。

## 目标

提 PR 后保留待办；确认合入并完成本地收尾后，事项按 Copilot 现有规则进入历史。

- 同一份内容已经提交、评估仍有效时，不重复启动语义比较与人工确认。
- 用户在 Copilot 查到合入后，同一次操作触发收尾与清理。下一轮 groom 通过同一份 PR 台账接手未完成的事项。
- 会话级自动任务每天触发一次同一套收尾，合入后不必等人点面板或等到下一轮 groom。
- 台账缺失、证据不足、部分执行失败均可见；批处理中不丢失失败项。
- 收尾与恢复能够重试，保留人决定与评估依据。

本方案对应 [设计原则](../docs/spec/design-principles.md) 中的「不变量写进结构」「建议与决定分离」「变更可逆」。固定执行入口、保留批准绑定、恢复文件清单分别落实这三条。

## 非目标

- 本稿定义查合入后的触发条件和后台流程。Copilot 的按钮、进度、刷新和失败提示由 owner 设计。
- 不引入 `advanced_at` 作为第二套完成条件，也不扩展 `submitted` 的含义。
- 不提前把待合入草稿移入 `.done`，避免面板把出队误读为完成。
- 不新增平台 webhook，也不自动开 PR、自动合入。允许独立插件 `dsh-sleuth-autoclose` 内一个可开关的常驻定时器触发幂等 sweep；插件关闭或 DSH 未启动时，由手动流程与 groom 开场兜底。
- 不把「远端有同名 case」或「内容相同」替代 PR 合入确认。
- 不改跨机恢复与正式知识的生命周期；本轮也不提前删除仍被流程使用的快照。

## 方案

### 1. 保持 Copilot 的状态含义与文件位置

以 main 的 `sediment_state.py`、`groom_status.py` 与 `trace-status.yaml` 为行为基准。实现分支中要求面板适应提前出队的改动，不属于本版设计。

| 阶段 | 草稿与评估记录 | trace 沉淀状态 | Copilot 的行为 |
|---|---|---|---|
| 待评估或待决定 | inbox 与 `.groom/assessments/` | `submitted` | 评估、确认或重新评估 |
| 已提 PR，open / unknown | 保留原位置 | `submitted` | 查合入；评估过期时按既有规则提示 |
| PR 已合入，尚未收尾 | 保留原位置 | `submitted` | 已合入、待收尾 |
| PR 关闭但未合入 | 保留原位置 | `submitted` | 继续 groom；没有提前移动就不需要恢复 |
| 已完成本地收尾 | 草稿进入 `.done/<key>/` | `knowledge` 或 `archived` | 按现有规则进入历史 |
| 未登记 PR，主动撤销沉淀 | 草稿进入 `.undone/`，评估删除 | `none`（能写回来源 trace 时） | 草稿退出待办，诊断状态保持不变 |

`new_pattern` 与 `variant` 的终态为 `knowledge`；`covered` 的终态为 `archived`。`close-log.jsonl` 的成功收尾记录继续使用 `status: closed`，只在 trace 处理与草稿出队完成后追加。不得用它表示「PR 已提交」。

trace 处理沿用 main：外部来源没有 session 时跳过写回；有 session 但文件缺失时记录 `trace-missing`，允许出队并报告原因。实际写回报错时保留草稿，不写成功收尾日志。

### 2. Copilot 与 groom 通过 PR 台账交接

Copilot 现有的单条和批量「查合入状态」通过 `pr_status.py` 查询平台并写入共享台账。本轮联动在用户发起的查询确认某项已合入、且该项成功写入台账后，直接调用后台收尾。同一次操作继续完成 cleanup，无需用户再执行收尾指令。批量查询根据最终结果逐项判断，进度事件只用于展示。其他项查询失败时，已确认合入且成功写入台账的项仍可收尾。

后台按第 4 节核对证据。证据不足时保留「已合入 · 待收尾」，返回缺少的证据。收尾失败或 cleanup 未完成时返回对应步骤和原因，供手动入口或下一轮 groom 重试。台账写入失败时沿用现有回退指令，缺少写权限时由具备权限的会话接手。打开面板、刷新列表和手动改状态沿用现有行为。

在 `skills/knowledge-groom/SKILL.md` 的开场同步与候选生成之间加入收尾检查。

1. 读取共享 inbox 与 PR 台账，将已记录 `merged` 的事项列为待收尾。复用 `pr_status.py` 查询仍为 `open` / `unknown` 的记录，并加入本轮确认合入的事项。
2. 对待收尾事项按第 4 节核对合入证据。台账状态用于选择事项，收尾和 cleanup 仍需通过各自的检查。
3. 检查 open / unknown 的记录是否需要重复评估。
4. 将其他待处理草稿交给既有候选生成流程。

查询失败时保留 PR 身份与其他项已查结果，失败项沿用 main 的 `unknown` 与错误字段，报告需要补查的 key。台账写入失败时，区分本次查询结果与已保存状态；不得把失败解释为未合入、已合入或没有 PR。

`pr_status.py` 的业务失败可能仍退出 0，调用方必须检查结构化结果，不能只看进程退出码。

知识同步继续区分 `sync.remote` / `sync.branch` 与 `target.remote` / `target.base`。每份评估沿用 main 的 `provenance.target_ref` 解析规则；遇到目标变化、ref 缺失或不可比较，沿用现有错误与提示，不静默回退到 `origin/main`。

Copilot 查询后的自动触发、手动收尾指令与 groom 开场共用 `groom_close_draft.py`。后台负责证据检查、收尾、清理与重试，并返回逐项结果。多个入口处理同一份草稿时，按第 6 节核对已完成的步骤，只补剩余动作。

自动收尾做成独立插件 `dsh-sleuth-autoclose`，挂在 DSH 上，不依赖某个会话：

- 形态：独立插件包，与 `dsh-sleuth-copilot` 平级，不互相 import；只依赖 DSH 的 `shell` 服务与仓库脚本。
- 开关：插件设置 `enabled`，默认开；关闭后立即清定时器，手动流程不受影响。
- 定时器：`apply(ctx)` 里用 `ctx.effect` 注册，默认 24 小时；插件卸载或重载时自动清掉（含已排好的单次 timeout 与 30 秒配置轮询）。插件是 profile 级常驻，跨会话。
- 安装即用：`repo` 留空时按当前会话 `cwd` → 插件自身检出 → 进程 `cwd` 自动发现，并用 `git rev-parse --git-common-dir` 归到主检出；`python` 留空时探测 `python3` / `python` / `py -3`。默认 `runOnStart: true`，安装后重启 DSH 即跑一次，把本地已合入待收尾的 PR 处理掉。
- 可用性检查：缺检出或 Python 时在状态里写原因，不算连续失败；发现后 30 秒内补跑。不静默空转。
- 任务内容：只调 `groom_sweep.py --repo <发现的检出> --apply --fetch`，不携带流程知识。shell 的写入根取主检出，worktree 检出也能把状态写进共享 inbox。
- sweep 步骤：读台账 → `pr_status --check-all`（不可用时用 git 判断）→ 对 merged 且未收尾的取证并调收尾入口 → 对已收尾但 cleanup 未完成的补清 → 输出一屏逐项结果。
- 取证：收尾标记以本地评估记录为准，PR body 只作可选核对；合入 SHA 优先取平台适配器返回的 merged 结果，平台不可用时才用 git 推断（只认提交标题结尾的 PR 编号，仓库不一致不猜，远端引用必须用完整 `refs/remotes/...`）。平台明确返回 open/closed 时停止，即使显式开启 git 模式也不覆盖；整轮部分查询失败时按每条 PR 的结果决定是否回退，已确认 open/closed 的那条不回退。平台确认 merged 并给出 SHA 才自动写；只有 git 推断时默认只报告疑似合入，需显式开启。适配器只需状态与合入提交，不要求 body；当前只有 GitHub 适配器实现 fetch，GitLab 仍只查状态。
- 结果与失败：每次运行追加一行到 `.groom/sweep-log.jsonl`（触发源、检查数、收尾数、失败项、耗时）；连续失败 3 次自动暂停并提示。写日志前就失败的轮次（台账锁、Python、shell）不产生日志行，插件把 `lastFailure` 与连续失败次数写进 `autoclose-state.json`，面板据此兜底显示失败项与最近运行。
- 安全边界：不自动合入、不自动开 PR、证据不足不写状态、不替代人决定。
- 兜底：插件关闭、DSH 未启动或自动任务暂停时，仍用 Copilot 的「已合入 · 待收尾」指令与 groom 开场手动收尾。

主面板（ascend-sleuth）新增「自动收尾」tab，读同一个读模型（台账 + `sweep-log.jsonl` + 插件状态 `autoclose-state.json` + 插件配置），不复制 Copilot 队列：

1. 顶部：开关、下次运行、上次结果、连续失败次数。
2. 待收尾清单：台账里 `merged` 未收尾的项，每项标证据状态（合入提交可用 / 本地评估齐全 / 缺哪一项）。
3. 失败与待人工：按查询、取证、收尾、清理四段分开列，每项给「重试」与「生成手动收尾指令」。
4. 运行记录：`sweep-log.jsonl` 最近若干条，带触发源。

待处理只算有本地草稿的项；台账里有 `merged` 但本地没有草稿的单独提示，不混进待处理。累计合入/累计出队只作背景，已出队读 `.done` 与 `cleanup-log`，清理未完成的单独标出。

首装首轮 dry-run，面板确认后才 apply；运行记录和「最近清理」（删了什么、保留什么、为什么）可展开；「立即运行一次」与「恢复调度」分开。

面板直接读台账、`sweep-log.jsonl`、`cleanup-log.jsonl` 与插件状态文件（同一个读模型），不再维护单独的投影脚本。打开 tab 时跑一次只读体检（主检出路径、`python3`、`gh`、台账、锁），结果直接显示可用或降级。

`sweep` 先按 `--apply` / `--dry-run` / `--json` 三档实现。实现顺序：先做 sweep（已完成），再写独立插件与开关，最后接主面板 tab。

联动默认接在 Copilot 宿主 `lib/index.js` 的 `prTarget()` 查询返回处。单条查询调用 `pr_status.py --check`，批量调用 `--check-all --json-lines`。查询脚本继续返回平台状态，宿主在确认台账写入成功后调用统一收尾入口。groom 开场直接复用该收尾入口。

批量最终结果为 `E_CHECK_PARTIAL` 时，已落盘且查询成功的 merged 项可继续。`E_CAS` 表示台账被其他写者修改，`E_LEDGER` 表示写入失败，这两种结果均停止本轮自动收尾。执行前重新核对所选项的 PR 身份、目标与评估，期间换绑到另一个 PR 就停止该项。

`--check-all` 当前只查询 open / unknown。联动层还须选取已有 merged 记录中尚未完成收尾或 cleanup 的事项，按同一证据规则重试。选取范围为本次单条查询对应的 PR，或批量查询覆盖的共享台账。查询整体落盘失败时保留这些事项，待下次成功操作或 groom 开场接手。

结果分别携带查询、收尾、清理的逐项状态与失败原因。收尾失败后，已保存的 merged 状态继续有效。宿主按阶段区分权限与超时，现有查询限时为单条 30 秒、批量 180 秒，收尾阶段另行配置。超时或切换会话后，后台可能已经完成部分动作，重试先检查持久化记录。具备查询写台账权限，也仍须检查草稿、trace、评估与快照的写权限。

### 3. 避免重复评估，但不隐藏待办

重复评估检查放在后台选择本轮草稿的步骤，不能通过删除草稿实现。`find_drafts` 与面板继续看见所有 inbox 草稿。

本轮查询确认已登记的 PR 仍为 `open` 时，以下条件均成立才复用评估：

- 既有评估、人决定与当前草稿内容仍绑定，批准有效。
- 按 `groom_status.py` 判断无需重跑，目标 ref 没有未解决的问题。
- 当前 PR 的最新提交与已批准内容的绑定仍有效，且没有明确的重评要求。

首次核对通过后，保存 PR 身份、最新提交 SHA、`assessment_id`、批准的内容指纹、人决定与候选 case。当前查询接口未返回最新提交 SHA，实现需按该 PR 身份补取，扩展后的查询若已提供则复用。上述值均与已核对的记录一致时，复用此前的提交内容检查。

提交、决定或候选 case 变化时，从明确的 Git commit 读取产物，重新核对评估标记（marker）与批准内容。只有无法从本地取得本次所需的提交或标记时，才补取远端证据。当前提交无法确认时，将该事项列为待查。合入后仍按下一节核对最终证据。

PR 为 `unknown` 时，仍检查本地评估的新鲜度与批准绑定。草稿变化或评估失效时进入重评。本地评估仍有效时保留待查，暂不重复比较。查证前暂停再次提 PR 与收尾。

跳过报告带 key、PR 地址与原因。草稿变化、批准失效、知识变化或审阅要求修改时，重新进入评估；PR closed 时继续既有 groom 流程。不得仅因存在 PR 就永久跳过，也不得把 `status_rows` 的粗粒度变化检查擅自放宽。

候选生成入口需要提供显式重评方式，供 agent 根据审阅要求使用。参数在实现时统一定义；本稿不把尚未实现的开关写成可执行命令。

### 4. 合入后核对证据，再收尾与清理

保留「确认 PR 合入」这一前置。内容指纹只用于检查本次产物，不建立独立的合入判定。

收尾需要确认 PR 已合入、取得合入提交、并核验本地评估（assessment_id、内容指纹、人决定）。评估本身就在本地 sidecar 里，PR body 只是给评审看的副本；实现不要求从平台取 body。只提供状态的适配器仍可查询，合入提交拿不到时保留 inbox 草稿与评估记录。

不依赖 body 后，平台只回答「合入没有」与「合入提交是哪个」。合入提交优先由 git 给出（squash 提交信息按 PR 号匹配，或 head 已并进 base）；git 匹配不到时再调平台 CLI。本地评估的绑定核验不变，来源字段不能仅凭 body 中的文本决定。

对目标远端同步成功后，固定完整 commit SHA。读取该提交中的文件，不读取当前工作树，也不在同一轮中反复读取可变分支引用。目标 ref 必须与本次 PR 对应，不能使用其他草稿的目标或全局默认替代。

| 决定 | 核对内容 | 成功后写入 |
|---|---|---|
| `new_pattern` / `variant` | 从提交产物的 `cases:` 中按最终 ID 提取单条 case；核对评估、批准、marker 与提交内容绑定，再验证目标分支中的内容 | `knowledge` 与最终 case ID |
| `covered` | 核对本次提交的转正 postmortem 路径与全文；改名后须显式指定实际路径 | `archived` 与覆盖它的 case ID |

case 复用 `canonical_content_sha`。postmortem 对统一换行后的全文算 SHA-256。参考内容必须取自本次明确的提交，不得先对旧工作树内容算指纹，再用远端旧内容证明成功。

内容在后续提交中再次变化时，保留待收尾并报告需要核对。普通 merge / squash 的 `groom_recheck.py --post-merge` 使用已确认的合入提交及其第一父提交，保留内容绑定与索引检查，跳过合入后的评估过期检查。不要用当前目标分支头充当合并前 base。

普通 merge 和 squash 须确认平台返回的提交确为本次合入产物。rebase / fast-forward 涉及多条提交时，须取得覆盖本次 PR 的完整 base/head 区间，不能只比较最后一条提交与其父提交。区间不能确认则保留待收尾。复核使用该固定版本的隔离检出：收尾入口在共享 inbox 的 `.groom/tmp` 下用 `git worktree add --detach <merge>` 建临时检出，按固定内容重建索引，再跑清理；当前开发工作树的修改与生成物都不参与判断。

核对通过后，执行顺序为：准备恢复所需的文件清单 → 写回 trace → 移动草稿 → 写成功收尾日志 → 清理评估记录和无引用快照。清理仍使用 `groom_cleanup.py --post-merge`，不改成合入前模式。

同一个 PR 可以包含多份草稿。cleanup 按整份 PR body 的 marker 处理，因此先确认该次 cleanup 涉及的草稿全部收尾成功，再按 PR 调用一次。只完成其中一部分时保留评估并报告待补项，重试补齐后再清理。

按平台主机、仓库与 PR 编号归组，核对完整 marker 集合。单条查询只收尾当前选中的草稿，只有其余 marker 对应的草稿也已有匹配的收尾记录时，才清理整个 PR。批量处理同一 PR 时只取一次证据。marker 中存在本机缺失的草稿、缺失评估或不同 PR 的绑定时，报告具体项并暂停该 PR 的 cleanup。已完成且记录匹配的项可跳过。

trace 已写而移动失败时，沿用 main 的 `done` 与 `draft_left_behind` 提示；这表示知识已落地、草稿尚未出队。后台仍按未完成的文件清单与缺失的成功日志重试，不能把面板的 `done` 单独当成本地收尾全部完成。

清理失败不回退已经完成的知识状态。下一次 groom 从台账、成功收尾日志与残留评估中选出补清理项，继续执行；面板仍按现有完成规则显示历史，不新增「清理中」状态。

### 5. 快照与评估记录分开处理

本地快照是固定 commit 的独立工作目录。每轮开始 fetch，再固定本轮比较版本；评估期间远端前进不改变本轮输入，后续按既有新鲜度检查决定是否重评。

评估记录保存人决定、内容绑定、比较 commit 与目标 ref，无法从 git 重建。快照目录与索引可在原 commit 可用时重新生成，两者不能按同一种清理规则处理。

正常 PR 流程保留 main 的清理时机。合入并收尾后，再删除本次评估记录与无引用快照。主动撤销按第 7 节处理。提前释放快照可另行评估，但必须先核对候选生成、marker 生成、复核等消费者的路径依赖。

合入后 cleanup 依赖以下证据与保护条件。

- 调用流程已确认 PR 合入，并完成本地收尾。`--post-merge` 只选择合入后的复核规则，不能替代平台查证。
- 合入提交可确认（git 或平台），且本地评估的 assessment_id、内容指纹、人决定与收尾对象一致；`groom_recheck` 的内容绑定与索引检查通过。
- marker 与本地评估的身份、内容指纹、人决定一致，批准允许清理。旧 PR 的 marker 不能删除重评后的记录。
- 删除快照前检查剩余评估的 commit 引用，并保留现有的最近快照使用保护。评估读不出时保留快照，拿不到目录锁时停止清理。

本轮继续调用 `groom_cleanup.py --post-merge`，通过 `.groom/cleanup-log.jsonl` 记录结果。该脚本不负责判定面板完成，也不清空整个 `.groom/`。除本次 marker 覆盖的产物外，本轮新增受保护的全局回收：没有任何评估或工作单引用、且超过 24 小时的无主快照；`.groom/` 下的 `*.tmp` 与 `.groom/tmp/` 超过 24 小时的内容；`.groom/runs/` 超过 1 天的目录与文件；评估已归档到 `.done/` 的残锁。保护规则：评估、工作单或 `latest.json` 读不出时整轮不删无主快照；`latest.json` 指向的快照不删；有 sidecar 的锁与 `.guard.lock` 不删；在途 run 由 1 天窗口保护。接上每天自动执行后，删除规则与手动执行相同，只是触发更勤。

快照定位沿用创建时的目录与分支，恢复清单在删除评估前保存这些信息。cleanup 默认 `branch=main`，多目标场景须传入实际值。同一 PR 涉及不同快照目录或分支时，清理入口需支持逐快照定位。路径来源不明或定位不一致时保留待查，不能将默认路径不存在视为已清理。

清理结果须检查 `kept_reasons` 与 `skipped_snapshots`。评估不匹配时保留新记录，报告旧操作的冲突。最近快照受保护或仍有其他评估引用时，记录本次操作尚未回收的快照，供下一轮检查。只在匹配路径确已不存在或删除成功时记为完成。此类补清理记录只服务后台重试，面板仍按既有收尾规则进入历史。

需要重评时使用本轮新同步的固定版本；复查历史评估时才按原比较 commit 重建。旧 commit 不可用就报告历史无法复原，不拿最新版本替代。

### 6. 中断恢复与无 PR 部署

`groom_close_draft.py` 的重试同时检查 inbox 与 `.done`。不能仅凭目录或两份记录存在就返回成功，也不能只扫描 inbox 而漏掉部分移动的草稿。

- 移动前记录实际文件清单；平铺草稿的 `.case.yaml` 与可选 `.md` 分别核对，目录形草稿保留完整目录内容。
- 同 key 的目标文件已经存在时，比对内容与评估身份；相同则继续，冲突则报错，不覆盖。
- 写评估、撤销、收尾与清理共用 `assessment_guard(inbox)` 目录锁。拿锁后重新核对草稿、评估身份与 trace，锁不可用就停止该项。收尾释放目录锁后再调用 cleanup，由 cleanup 自行加锁，避免嵌套调用争用同一把锁。
- 任一项失败都进入批次结果；其余项可继续，整批返回非零。成功日志不得先于实际完成。

恢复清单须在首次改文件前保存 PR 身份、固定证据、评估身份与文件清单。评估删除后、cleanup 日志写入前中断时，靠这份记录与实际文件核对恢复。已有同 key 的新评估时保留新记录。清理结果中的 `ok` 仍须结合逐项保留原因判断，当前脚本可能在保留不匹配评估时返回 `ok: true`。

台账没有对应记录时，要求显式 `--no-pr`，不能把漏登记视为本地沉淀。该选项只用于无 PR 部署，仍须核对落点与批准；`covered` 仍写 `archived`。台账存在 open / unknown / closed 记录时，`--no-pr` 不得绕过它。

无 PR 收尾完成后保留评估与快照，返回保留原因。该路径缺少 PR body 和合入区间，不能套用本稿的 `--post-merge` 清理调用。

不引入 `--submitted` 收尾路径。旧 `--allow-open-pr` 不再允许提前写知识终态；保留参数解析并明确报错，提示先确认合入。Copilot 现有正常收尾指令不依赖该开关。

`scripts/groom_close_draft.py` 的 `blocked_reason()` 与 `skills/knowledge-groom/SKILL.md` 现有提示都写着"确实要提前收尾时加 `--allow-open-pr`"；改成报错后这两处要同步改掉，不能留一条已经不生效的旁路提示误导人。

### 7. 与撤销沉淀共存

沿用 `sediment_undo.py` 的产品边界（含 main 已合入的 #459）。草稿仍在 inbox、来源 trace 未升格时，允许主动撤销；PR 已关闭（`closed`）也允许撤销，并清掉该 key 在台账里的记录，避免残留记录把草稿永久挡在撤销之外。`open` / `unknown` / `merged` 记录仍阻止撤销。执行前在同一目录锁内重读台账与评估身份：建计划之后新增 PR、改写评估或换绑 PR 时停止，不覆盖新记录。平台建 PR 与本地登记之间仍有时间窗口，同一 key 的建 PR 与撤销须串行编排，不承诺本地锁覆盖外部平台事务。

本轮拟收紧 `--keep-trace` 的旁路。main 当前会用它跳过来源歧义与已升格检查，改后仅跳过回写。来源歧义或 trace 读坏时仍拒绝，来源明确且 trace 存在时仍检查 `knowledge` / `archived`。外部来源或 trace 缺失继续按现有规则跳过回写并报告原因。

撤销把草稿移入 `.undone/`，删除评估，向 `.groom/undo-log.jsonl` 写入摘要。来源 trace 可写时，`sedimented` 回到 `none`，清除原落点字段。诊断 `status` 保持不变，继续定位仍由诊断面板的「重新打开」触发。`reject` / `defer` 继续保留草稿与评估。

候选扫描、补收尾与旧数据迁移均排除 `.undone/`。主动移回的草稿需要重新评估与批准，undo-log 的摘要不能恢复旧评估或授权收尾。缺少评估不能单独作为成功 cleanup 的证据，须结合对应收尾记录与清理记录判断。

并发保护属于本次实现范围。撤销与 `--no-pr` 收尾须在同一目录锁内重验后执行，后取得锁的一方发现草稿已移走或身份变化就停止。PR 登记与撤销也须协调本地写入，统一锁顺序，在写入前重读台账。仅在撤销建计划时查一次台账不足以阻止计划之后新增 PR 的情况。平台建 PR 与本地登记之间仍有时间窗口，同一 key 的建 PR 与撤销须串行编排，不承诺本地锁能覆盖外部平台事务。

面板与撤销脚本已调用 `groom_close_draft.source_session_of(draft)`。重构收尾时保留其返回的 session、原因、歧义标志，来源判定继续共用这一入口。

## 替代方案

提 PR 后把草稿与评估移入 `.done`，可以提前清空 inbox，但需要同时修改面板的完成判定、详情取数、恢复指令与历史计数。它不满足以 Copilot 为准的范围约束，本轮不采用。

仅按远端内容一致推进，可以减少平台查询，却不能证明指定 PR 已合入，也会增加第二套完成依据。保留内容核对作为合入后的证据检查，不单独推进状态。

会话级定时扫描可以缩短等待，但依赖会话存活、平台凭据与失败通知；任务失效后仍要 groom 开场或面板兜底。本轮采用它作为「更及时」的触发点，不承诺无人值守。

维持手动收尾无需改后台，但重复评估与积压仍依赖维护者记忆，不能达到目标。

也可在 `pr_status.py` 中增加显式启用的收尾模式，成功保存台账后再调用统一收尾入口。这需要新增参数与分阶段输出，同时处理 JSON Lines 完成事件、超时和导入依赖。当前 `groom_close_draft.py` 已导入 `pr_status`，实现时须避免顶层互相导入。本稿优先采用宿主串联两个阶段，复用现有查询接口。

## 代价与缺点

- 等待合入期间保留草稿、评估与被引用快照，占用本地空间。该成本换取面板兼容与原地重评。
- 自动查合入优先用 git；git 匹配不到时依赖平台适配器与凭据。都不可用时沿用手动查证，不用内容相同替代。
- 用户未发起查合入或手动收尾时，事项等下一轮 groom 接手。
- main 的评估过期检查可能触发重评；本轮只跳过仍有效的评估，不承诺消除所有重复工作。
- 文件移动、trace 写入与日志追加不是单一事务。中断后可能暂时显示中间结果，重试必须收敛；不承诺任意断电时面板始终无中间态。

在现有模块中补充以下反例，期望命令全部通过：

| 场景 | 预期 |
|---|---|
| open PR，最新提交未变，评估仍有效 | 复用提交内容检查，跳过重复比较，草稿与评估留在原位置 |
| PR 最新提交变化，或当前提交无法确认 | 变化时重新核对内容绑定。无法确认时列为待查，暂停再次提 PR 与收尾 |
| 同一次评估改判或更换候选 case | 重新核对评估标记与提交内容，旧检查结果失效 |
| unknown PR，评估已过期 | 重新评估，查证 PR 前暂停再次提 PR 与收尾 |
| 合入提交无法确认（git 与平台都失败） | 保留待办与文件，报告缺失证据。通过既有手动入口补证后继续，禁止自动认定合入 |
| Copilot 单条查询确认合入并写入台账 | 同一次操作触发收尾，成功后执行 cleanup，无需另发指令 |
| Copilot 批量查询结果混有合入、未合入与查询失败 | 只处理确认合入且成功写入台账的项，逐项返回结果 |
| Copilot 查询确认合入，但证据不足或台账写入失败 | 证据不足时保留待收尾并报告缺失项。写入失败时沿用回退指令，两种情况均不执行 cleanup |
| Copilot 已写入合入状态，但收尾或清理中断 | 下一轮 groom 接手，重试只补未完成步骤，草稿与成功日志各处理一次 |
| 同一 PR 有两份草稿，一份收尾成功，另一份失败 | 保留两份评估并报告待补项，全部收尾成功后按 PR 清理一次 |
| 批量部分查询失败，但台账已成功保存 | 继续处理成功确认合入的项，保留每项查询与收尾结果 |
| 批量已发出 merged 进度事件，最终台账写入冲突或失败 | 本轮不触发收尾或 cleanup，返回写入失败 |
| 台账已是 merged，但上次 cleanup 失败，再点批量查询 | 联动层补选未完成项并重试，即使查询脚本未再查询该 PR |
| 查询结束后同 key 换绑到另一个 PR | 执行前重验身份，停止旧请求 |
| 单条查询对应的 PR 含本机缺失或尚未收尾的其他 marker | 只处理选中项，报告其余项，暂停整份 PR 的 cleanup |
| 查询返回 merged，但 git 与适配器都拿不到合入提交 | 保留待收尾并报告缺失证据 |
| rebase / fast-forward 合入多条提交 | 使用完整 PR 区间复核，区间不明时保留待收尾 |
| 查询可写，但后续目录不可写，或收尾阶段超时 | 保留已查状态和已完成步骤，返回对应阶段，重试核对记录 |
| 评估删除后日志写入前中断，或随后出现同 key 新评估 | 从恢复清单核对旧操作，保留新评估，不凭文件缺失判成功 |
| `--no-pr` 收尾成功 | 保留评估和快照并说明原因 |
| cleanup 返回 `ok=true`，但有保留评估或受保护快照 | 逐项报告冲突或待重试，下一轮仍能找到未完成的快照清理 |
| 同一 PR 的快照使用不同目录或分支 | 按创建记录逐一定位，参数不明时报待查 |
| 当前工作树有修改，或合入提交的生成索引尚未更新 | 在固定版本的隔离检出生成校验用索引，复核结果与开发工作树无关 |
| 草稿变化、批准失效、目标变化或显式重评 | 不因已有 PR 跳过；保留 main 的对应提示 |
| merged，但证据不足，尚未写 trace | 不改文件、不写成功日志；面板保留待收尾事项 |
| trace 已写、草稿移动失败 | 沿用 main 的 `done` 与 `draft_left_behind` 提示；重试补齐出队与成功日志 |
| 草稿已移动、成功日志未写 | 从文件清单与两处文件恢复；不依赖面板是否仍列出该项 |
| merged 且收尾成功 | trace 与决定对应，草稿出队，面板按现有规则进入历史 |
| 外部来源无 session，或来源 trace 缺失 | 沿用 main 的跳过写回或 `trace-missing` 处理，报告原因；实际写回错误才阻止出队 |
| variant 的旧 case 已存在、本次修改未落地 | 不提前写 `knowledge` |
| covered 改名、目标文件不存在或内容不符 | 要求明确路径或补证据，不写错误终态 |
| 目标不是 origin/main，或多个事项目标不同 | 每项读取对应目标的固定 commit；同步失败不使用旧引用冒充成功 |
| 批次中一项未登记 PR 或失败 | 报告包含全部 key 与原因，整批返回非零 |
| 加 `--allow-open-pr`，PR 未合入 | 报错并说明该旁路已不支持；不收尾、不移动草稿、不写 trace |
| 台账已有 open / unknown / closed 记录，调用方传 `--no-pr` | 拒绝执行并提示台账已有记录；不得用 `--no-pr` 绕过 |
| case 已移动、postmortem 未移动，或 trace/日志/清理中断 | 重试核对两处文件并完成剩余动作，不漏文件、不覆盖冲突 |
| 快照仍被使用、评估记录读不出或写锁不可用 | 不误删；解除条件后可重试 |
| 旧设计多份提前归档记录恢复 | 每份评估回到各自规范化路径，互不覆盖 |
| 未登记 PR 的草稿撤销后再次运行 groom | `.undone/` 不被扫描或自动恢复，诊断状态保持不变 |
| 已撤销草稿手动移回 inbox | 重新评估与批准，不复用撤销前的检查缓存或决定摘要 |
| 台账含任一状态记录，或台账读不出 | 撤销停止，关闭 PR 也不自动获得撤销资格 |
| `--keep-trace` 遇到已升格、来源歧义或损坏的 trace | 仍拒绝撤销，该参数只跳过回写 |
| 撤销与 `--no-pr` 收尾同时执行 | 共用目录锁，后执行方重验后停止，不把同一草稿同时记为撤销与完成 |
| 撤销建计划后新增 PR 记录或改写评估 | 执行前拒绝旧计划，保留草稿与新记录 |
| 撤销删除评估后，快照仍被其他评估引用 | 后续 cleanup 保留快照，撤销不触发全局回收 |
| 收尾成功后调用 cleanup，或 cleanup 中断后重试 | 无嵌套目录锁争用，只清理匹配记录，不把撤销造成的缺失算作成功收尾 |
| 重构来源判定入口 | 面板与撤销脚本仍取得一致的 session、原因、歧义标志 |
| sweep 连续跑两次 | 第二次没有新的删除或收尾动作，结果一致 |
| 无 PR body | 用本地评估收尾并清理，评估文件被删除 |
| 台账 open、无适配器 | git 匹配到合入提交后进入收尾 |
| PR #7 与 #70 | 不把 #70 的提交当成 #7 的合入提交 |
| 正文或标题中间提到 (#7) | 不是合入证据 |
| 只有 git、台账 open | 默认只报疑似合入，不自动出队；显式开启才写 |
| 平台返回 merged 与合入 SHA | 默认流程直接收尾，不停在疑似 |
| 台账 closed、残留旧 SHA | 跳过，不据此删除 |
| 目标远端引用缺失 | 报缺证据，不回退 fork 本地分支 |
| 平台明确返回 open/closed | 停止，即使 `--allow-git-only` 也不覆盖 |
| 含斜杠的分支名（release/v1） | 同样要求匹配 remote 的完整跟踪引用，简写不命中本地分支 |
| 整轮 part 失败（E_CHECK_PARTIAL） | 按每条结果判断，已确认 open/closed 的不回退 Git |
| 同一 PR 多份草稿、其中一份查到 open | 整组保留（默认写入与 git 回退都不写） |
| 同一 PR 的 URL 查询参数不同 | 按主机、完整仓库路径与编号归为一组 |
| PR 查询参数里出现另一个平台域名 | 按解析后的主机选适配器，并核对证据属于同一 PR |
| 台账编号与登记链接编号不一致 | 在台账 SHA、平台、git 三个分支之前停止 |
| 组内第二份草稿编号与链接不一致 | 整组停止，不出队任何一份 |
| 台账仓库与链接仓库不一致 | 停止，不用台账 SHA |
| 归组编号 | 用链接路径里的编号，台账编号只用于核对 |
| 归组键 | 优先用登记链接的主机、完整仓库路径与编号；台账字段只做组内校验 |
| 组内 closed 保护记录字段冲突 | 也参与身份校验，冲突时整组停止 |
| 链接查询参数里带另一个编号 | 只从 URL 路径取编号，查询参数不算 |
| 平台返回链接的编号不同 | 视为不属于同一 PR |
| 平台别名（gitlab / glab） | 归组只用主机、仓库与编号，不拆组 |
| remote 的 push 与 fetch 指向不同仓 | 只用 fetch URL 选远端 |
| 同一主机下不同子组项目 | 按完整仓库路径区分，不串台 |
| GitHub/GitLab 同路径同名仓库 | remote 需同时匹配主机与完整仓库路径，不串台 |
| 旧收尾日志的合入 SHA 与本次不同 | 不复用，不据此清快照 |
| 插件关闭 | 定时器被清掉，不再触发；手动收尾仍可用 |
| 插件开启时缺 Python 或路径不可用 | 显示降级原因，不空转、不写状态 |
| 连续失败 3 次 | 自动暂停并提示，恢复需手动 |
| 主面板 tab | 待收尾清单与台账一致，运行记录与 `sweep-log` 一致 |
| 台账没有 open / unknown 且无未清项 | sweep 输出「无事可做」并退出 0 |
| 部分收尾失败后重跑 | 只补未完成的草稿与步骤，已成功的项不重复写 close-log |
| 清理失败后重跑 | 下一轮补清未删的评估与快照，不重复删已删项 |
| 两个入口同时处理同一 PR | 后到者按已完成步骤只补剩余动作，不重复写 trace 与日志 |
| 空轮后第二天有新 PR | 任务仍在，下一轮能接着处理 |
| 任务绑定的主检出路径被移动或删除 | 执行前验仓库身份失败，报告并停该项，不按相对路径误处理别的仓库 |
| 工作单或 `latest.json` 读不出 | 本轮不删无主快照，报告读不出的文件 |
| 会话级任务提示词 | 只含 `groom_sweep.py --apply` 与结果转述，不含流程分支 |
| 合入提交无法确认 | 保留待收尾并报告缺哪一项，不写状态 |

文档更新后，Copilot 现有「提 PR 后停止」「合入后收尾」「恢复草稿」指令应仍可执行。新增测试需要验证行为，不仅检查 prompt 中出现脚本名。

## 未决问题

本节不构成实现依据。

Copilot 如何呈现查询、收尾与清理的进度和失败，由 owner 决定。候选选择的显式重评参数、收尾证据的脚本参数与恢复日志格式，由后台实现按既有接口确定，并补齐命令帮助与测试。

平台适配器是否保留 body 支持：A 方案下收尾不依赖 body，适配器可只实现状态与合入提交；body 仅用于人工核对。

24 小时是否合适：PR 合入多在工作时间，固定 24 小时可能滞后一整天；是否改成每 12 小时，或只在工作时段跑。

面板开关的写权限：tab 里的开关只展示插件状态，还是允许在面板里直接开关；后者要写插件配置，需要与插件设置页共用一份存储。

## 先例

无外部先例作为实现依据。本方案沿用仓库已有的 PR 台账、合入后复核与可恢复出队机制；相关入口为 `pr_status.py`、`groom_recheck.py --post-merge`、`groom_close_draft.py`，面板读侧以 main 的 `sediment_state.py` 为准。
